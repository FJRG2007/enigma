# Multi-account (tool-agnostic, enigma-as-launcher)

- `src/accounts.ts` manages multiple logins per tool by giving each account its own config dir and injecting the tool's config-dir env var. The OS-agnostic switch is NOT shell aliases (what the reference blogs do, per-shell/per-OS) but enigma spawning the tool as a child with that env injected - one `child_process.spawn` path for macOS/Linux/Windows. Surfaces: `enigma <tool> [account]` (launch) and `enigma account <list|add|use|login|run|remove> [--tool <name>]` (manage), dispatched in `cli.ts` (`runAccountCli`); plus the unified Accounts & profiles panel in the hub TUI.
- ALL THREE tools are wired in the `TOOLS` registry (accounts.ts): claude (`CLAUDE_CONFIG_DIR`), codex (`CODEX_HOME`, `loginArgs:["login"]`, email decoded best-effort from the `auth.json` id_token JWT payload - email claim only, tokens never surface) and opencode (NO single config var: managed accounts get a private `XDG_DATA_HOME`/`XDG_CONFIG_HOME` pair under the account dir, but `envFor(defaultDir)` returns `{}` so the default account never touches the user's real env; identity = provider keys of auth.json as `displayName`). `enigma <tool>` and `--tool` light up automatically from `TOOL_NAMES`. Do NOT hardcode "claude" in new code - go through `getTool`/`isToolName`.
- PROFILES (1.8.0): registry (`~/.enigma/accounts.json`) gains `profiles: {active, items[name][tool]=account}`. Launch resolution order in `launchTool`: explicit arg > active profile mapping (`resolveLaunchAccount`, skipped if the pinned account vanished) > tool active > default. `removeAccount` scrubs stale profile mappings. CLI: `enigma profile <list|add|use|set|unset|remove>` ("none" deactivates). TUI (1.11.0): accounts and profiles share ONE "Accounts & profiles" sidebar entry/panel split by ACCOUNTS/PROFILES section headers - a single flat cursor (`idCursor` over `idRows`, accounts first then profile rows incl. the synthetic "(none)") walks both, and keys dispatch on the row KIND under the cursor (enter activate both; `c` connect account-only; `e` edit profile-only; `a`/`r`/`d` per kind). Mouse wheel scrolls every list (sidebar, panels, overlays) via the `wheel()` helper, sharing the exact arrow-key setters. Profile rows: enter activates, `a` add via name input, `e` edit = searchable tool selector then searchable account selector incl. "(unpin)", `d` remove with confirm. The add-account flow is two steps - a SEARCHABLE selector (`renderSearchSelect` + `filterItems` over generic PickItems; filter input via OpenTUI `onInput`; navigation/enter handled in the GLOBAL key handler because `useKeyboard` fires regardless of input focus - do not also pass onSubmit or selection double-fires) then the name input.
- Updating from INSIDE enigma locks the running `enigma-bin.exe` (Windows cannot unlink a running exe -> npm "warn cleanup EPERM" + orphaned `.enigma-cli-*` staging dirs). `parkRunningBinary` (update.ts) fixes it: a running exe CAN be renamed, so before `npm i -g` it moves itself to `%TEMP%\enigma-old-binaries\` (strict `enigma-bin*` basename guard - never node/bun) and sweeps old parked copies + stale staging dirs. Self-healing if npm then fails: the launcher lazy-downloads a missing binary.
- Each tool's existing config dir is a synthetic, non-removable `default` account (never stored, never deleted); new accounts live under `~/.enigma/<tool>/<uuid>/` (an opaque `randomUUID()` segment, NOT the account name), indexed in `~/.enigma/accounts.json` shape `{tools:{<tool>:{active,accounts[]}}}` where each account persists its `dir`. DIRECTORY IS DECOUPLED FROM THE NAME (so `renameAccount`/`renameProfile` are metadata-only - they never `renameSync` a dir, so a rename can't fail or collide on disk): `addAccount` writes `join(accountsBase, randomUUID())`; `renameAccount` only flips `account.name` + the active pointer + profile mappings. RETROACTIVE: accounts created before this (legacy `dir = base/<name>`) keep their persisted name-based path and keep working - rename just stops matching the segment to the name, which is fine since the segment is opaque. The ONLY consumer that displayed the dir basename as the account label is `usage.ts claudeSources` (the dashboard "By Account" panel); it now maps the basename back to the display name via `managedClaudeNames()` (reads `accounts.json` directly - usage.ts stays light, no accounts.ts import - falling back to the basename for legacy/unknown dirs). `claude-usage-api.ts credSources` globs the same base but only to FIND dirs to read `.credentials.json`, so its `account` label being a UUID is harmless (never displayed). `readRegistry` MIGRATES the legacy flat `{active,accounts}` (1.5.0 claude-only) into `tools.claude` on read. `removeAccount` only `rm -rf`s a dir inside the tool's base (a tampered registry can't point removal elsewhere). `accounts.ts` is Node-builtins-only (no clack); the CLI wrapper prints/prompts. Test: `tests/accounts.test.ts` (UUID dir on add, rename moves nothing + follows active/profile pointers, legacy name-based dir preserved).
- Windows spawn: a `.cmd` shim or bare name needs `shell:true`; `spawnInherit` quotes args (`quoteWinArg`) and uses `shell:false` with the resolved absolute path for `.exe`. Binary resolved via `tool.binEnv` (e.g. `ENIGMA_CLAUDE_BIN`) -> `resolveBin(tool.bin)` (full-path PATH/PATHEXT resolver in `util.ts`, which `isOnPath` delegates to). `--` ends enigma arg parsing; everything after is forwarded verbatim to the tool - and it cannot be the only way in, because Windows PowerShell drops a bare `--` before the process is spawned (`enigma claude -- --version` arrives as `claude --version` and printed ENIGMA's version). So a launch line (tool name or pack id) owns no flags of its own beyond `-h`/`--help` and a pack's `-t`/`--tool`: at its FIRST flag the rest of the line is forwarded verbatim. Forwarding from that point rather than flag by flag is what keeps a flag's value with it (`--resume <id>` would otherwise leave `<id>` behind as the account name) and keeps agent flags off the shared parser, which owns `-c`, `-p`, `--model` and more. Pinned by `tests/cli-dispatch.test.ts` against a stand-in binary wired through `ENIGMA_CLAUDE_BIN` that echoes its argv.
- ACCOUNT DEPLOYMENT SYNC: a managed account's config dir is what the tool actually reads with the env injected (claude: skills/, CLAUDE.md memory AND settings.json all under CLAUDE_CONFIG_DIR), so the hardcoded `~/.claude` targets in agents.ts/claude.ts never reach it - launching an account without this gave NO skills/memory/bypass (the original bug). Fix: `ToolSpec.accountTarget(dir)` (accounts.ts) maps each tool's in-account skills/memory destinations (codex has NO per-account skills - it reads the shared `~/.agents/skills`; opencode's live under `<dir>/xdg-config/opencode`), `syncAccount` (skills.ts, shares the `syncTarget` core with `syncDeployed`) deploys skills+memory there, and `mirrorAccountSettings` (permissions.ts) mirrors the enigma-managed native knobs FROM the global/default config on every sync, presence AND absence (claude settings.json: bypass defaultMode/attribution/statusline/feedback-survey-env via `mirrorClaudeSettings` in claude.ts; codex config.toml: approval_policy+sandbox_mode; opencode: the `"*":"allow"` catch-all). Wiring in cli.ts: `syncForLaunch(tool, account)` replaces autoSyncForLaunch (account resolved BEFORE launch so sync and spawn agree), `seedAccount` runs on `account add` (CLI + TUI callback), `loginWithSync` covers login/connect. Consent: account dirs are enigma-created, so a MISSING deployment is seeded even with autoSync off (else it would never get one - `enigma install` does not target account dirs); refreshes respect the toggle, and tampered-skill/user-edited-memory rules match syncDeployed. Layering: skills.ts now imports accounts.ts (fine - accounts.ts only imports util). Tests: `tests/account-sync.test.ts` (bun, temp HOME set before import - skills.ts resolves STATE_FILE at module load).
- IDENTITY DISPLAY: `listAccounts` surfaces the signed-in email per account via `ToolSpec.accountInfo(dir)` (claude reads `oauthAccount.emailAddress` from `<dir>/.claude.json`; no tokens are read), plus the tool label. Shown in `enigma account list` and the TUI Accounts panel. Accounts not yet logged in show "(not logged in)".
- SESSION REUSE / TRANSFER (`src/claude-oauth.ts`, the ping-pong fix). PROBLEM: the SAME Anthropic OAuth login stored in two Claude config dirs (a managed account dir AND a pack context - see the packs SEEDING note) fights itself. Anthropic ROTATES the refresh token on every refresh and invalidates the previous one, so whichever dir refreshes last keeps working and the other's refresh token goes stale -> Claude Code eventually BLANKS that dir's `.credentials.json` (a silent logout, `expiresAt:0`, empty tokens). Symptom reported: `enigma claude` (launches the ACTIVE account dir) showed "signed out" while `enigma helio` (its isolated pack context) still worked, both on the same login. KEY INSIGHT: the problem is the REFRESH token, not the access token - as long as a dir holds a valid refresh token, Claude Code refreshes the access token itself, so "moving a session" is just copying `.credentials.json` (+ aligning `.claude.json` identity/onboarding so the target isn't sent through onboarding) - NO network call, NO re-login. Studied `references/repos/{claude-swap,teamclaude,kmj-claude-gist}` (gitignored): claude-swap carries its own OAuth refresh (POST `platform.claude.com/v1/oauth/token`, public client id `9d1c250a-...`) but we DELIBERATELY do NOT port that (avoids enigma making auth calls); the kmj gist confirms the naive "separate CONFIG_DIRs" model only works for DIFFERENT emails. `claude-oauth.ts` is a LEAF (node builtins only, never logs a token): `sessionState(dir)` = `ok|refreshable|expired|empty|absent` (refreshable = access expired but refresh present = still usable), `isUsableSession`, `transferSession(fromDir,toDir)` (copy creds + `alignIdentity` allowlist oauthAccount/hasCompletedOnboarding/userID, preserving the target's projects/mcpServers; atomic temp+rename write), `copyIfFresher(fromDir,toDir)` (the lockstep primitive: copies only when the source is strictly fresher via a `freshnessScore` = has-refresh biased then expiresAt, so a newer token is NEVER overwritten by an older one). PACK LOCKSTEP (`packs.ts` `reconcilePackSession` + copy-back in `launchPack`): before launch, converge the context and its MANAGED seeding account on the fresher token in EITHER direction (seed a fresh account token in, or HEAL a blanked/stale account from the still-live context); after the pack exits, `copyIfFresher(contextDir, accountDir)` propagates any refresh done during the session back. Restricted to Claude MANAGED accounts (the synthetic `default` = the user's own `~/.claude` is NEVER written). This makes `enigma claude <acct>` and `enigma <pack>` reuse ONE shared session instead of fighting - the "reutilizar" the user asked for. SURFACES: CLI `enigma account sessions` (list reusable Claude logins = account dirs + `packSessionSources()` pack contexts, healthiest-first) + `enigma account transfer <target> [source-id]` (source-id `account:<name>`/`pack:<id>`; auto-picks the freshest usable source when omitted). Dashboard: `dashboard-accounts.ts` gained `sessionSources` in the payload + an `account.transfer` op (`sessionSourceDir` maps the id to a dir, Claude-only guard); index.html shows a "Reuse session" button on a signed-out Claude account -> an icon picker of usable sources -> `account.transfer` (dashboard `0.1.72`; demo-mock stubs `sessionSources`). Tests: `tests/claude-oauth.test.ts` (state/transfer/copyIfFresher, pure temp dirs, in ci.yml) + heal-back/push/`packSessionSources` cases in `packs.test.ts` + an `account.transfer` case in `dashboard-accounts.test.ts`. NOTE the shipped binary predates this - a user on <=1.25.8 heals via `npm run enigma -- account transfer` from source, or after the next release; but once a dir's `.credentials.json` is healed, even the old `enigma claude` works (it just reads the file).
- TUI CONNECT + ADD: the Accounts panel can connect/log in an account (`c`) and CREATE one (`a`), not just list/activate(`enter`)/remove(`d`). Add opens an OpenTUI `<input focused onSubmit>` overlay (JSX tags `input`/`select`/`tab-select` are exposed by `@opentui/react`, installed workspace-local under `packages/enigma-cli/node_modules`); `useKeyboard` is a GLOBAL listener that fires regardless of the focused input, so the key handler MUST short-circuit while `adding` (only Escape) or typed letters (q/s/x) would trigger hub actions. On submit it calls the `HubContext.addAccount` callback (returns `{ok,error?,accounts}` so the renderer shows inline validation errors without importing `accounts.ts`), then shows a "connect now?" prompt; Yes exits via the `HubExitAction` connect path. Only Claude is registered so there's no tool `<select>` step yet (the elements exist for when there's >1 tool). Headless-verifiable: `@opentui/core/testing` `testRender` + `createMockKeys` (`pressKeys`/`KeyCodes`, `captureCharFrame`) run under BUN (not Node - native core). Connecting can't happen inside the TUI (launching the tool needs the terminal the TUI owns, and login is the tool's own interactive flow), so the panel exits the hub returning a `HubExitAction` (`{type:"connect",tool,account}`); `cli.ts` runs `loginTool` in the freed terminal and reopens the hub in a loop. activate/remove stay as in-TUI `HubContext` callbacks (now keyed by `(tool,name)`) that return the refreshed list. `opentui.ts` renders purely from `HubContext` and never imports `accounts.ts`. `add` is still CLI-only (needs a name input).
