# Monorepo + CLI layout

- Workspaces monorepo. Publishable package: `enigma-cli` under `packages/enigma-cli` (command `enigma`). Source is TypeScript in `src/` (entry `src/bin/enigma.ts`; modules: cli, agents, skills, security, guard, config, claude, util). DISTRIBUTION MODEL (SINGLE npm package; opencode's *mechanism* but NOT its per-platform packages). The app is a Bun-compiled standalone binary per OS (`scripts/build-binaries.ts` -> flat `dist-bin/enigma-<os>-<arch>[.exe]` + `.sha256`), but the binaries are NOT npm packages - they are uploaded as assets on the GitHub Release `v<version>` and fetched at install time. The main package's `bin` is a thin Node launcher (`bin/enigma.mjs`). Three shared bin scripts (Node-builtins only) drive delivery: `bin/platform.mjs` (platform key + `assetName()` + `binTargetPath()` + `loadChecksums()`), `bin/download.mjs` (HTTPS download from the release, SHA256-verify against `bin/checksums.json`, atomic install to `bin/enigma-bin[.exe]`), `bin/postinstall.mjs` (best-effort at install; never fails `npm install`; skips when no checksums.json = source checkout). The launcher resolves `ENIGMA_BIN_PATH` -> installed binary -> lazy download (covers `npm i --ignore-scripts`). Integrity chain: npm tarball (provenance-signed) -> `bin/checksums.json` (inside it) -> downloaded binary. WHY NOT per-platform npm packages (the old v1.4.0 attempt): npm spam-detection blocks brand-new unscoped `enigma-cli-<plat>` names, and the user wants only `enigma-cli` to exist. `bin/checksums.json` is generated by CI from the `.sha256` sidecars and shipped ONLY in the tarball (gitignored; npm's `files` allowlist still packs it - verified via `npm pack --dry-run`). tsup builds ONLY `dist/guard.js`. `dist/` and `dist-bin/` are gitignored. Build: `npm run build` (guard via tsup), `npm run build:binaries` (host binary via Bun). Full dev/build/publish guide: `docs/developers/`.
- CURL-PIPE INSTALL NEEDS A REAL TTY, AND THE CLI MUST NOT ASSUME ONE (the "install.sh does nothing on macOS" report). Two independent halves of the same failure. (1) SCRIPT: `scripts/install.sh` tested `[ -e /dev/tty ]` before running `enigma install </dev/tty`. The file EXISTS on every Unix even when the process has no controlling terminal, and the open then fails with ENXIO (macOS words it "Device not configured"), so the test passed and the redirect blew up - with `set -e` the script died before installing anything. It now TRIES the open in a subshell, `if (exec </dev/tty) 2>/dev/null`: the subshell contains a failed open (a redirection error on `exec`, a special built-in, exits a non-interactive shell outright) and a failure falls back to `install --all --yes`. Reproduced under WSL with `setsid` (no controlling terminal): the old script printed "cannot open /dev/tty: No such device or address" and installed nothing, the new one deploys the defaults. The same pass added two npx fallbacks, both hit on macOS with a system Node: a global install that fails for want of sudo, and a package installed into a prefix that is not on this shell PATH. (2) CLI: `cli.ts` computed `interactive` from `process.stdout.isTTY` ALONE. A prompt also READS, so with a non-tty stdin every clack prompt gets EOF, which reads as a cancel - and installSkills first select treats a cancel as "Aborted." and returns having installed nothing. That is why the selector looked broken while `--all --yes` worked. `interactive` now requires stdin.isTTY too, so a stdin-less run takes the non-interactive path (scope=global plus detected agents) instead of giving up. Lesson for any future prompt gate: check the END YOU READ FROM, not just the one you write to.
- The compiled binary cannot see on-disk files via `import.meta.url` (its `__dirname` is Bun's virtual fs). The launcher passes `ENIGMA_ASSETS_DIR` (assets/), `ENIGMA_GUARD_PATH` (dist/guard.js) and `ENIGMA_VERSION` from the main package; `security.ts`/`cli.ts` read those env-first with the `__dirname` path as the dev/tsx fallback. If you add a new on-disk asset the binary needs, wire a matching env override. ASSETS are the exception and resolve DISK-first through the single `assets-dir.ts` (`ASSETS_DIR`, used by skills/autoskills/autoskills-install/command-deploy): env-first is only safe where nothing is on disk, and because the launcher stamps `ENIGMA_ASSETS_DIR` unconditionally, every shell and tool an enigma spawns inherits it - so an enigma running FROM SOURCE inside one (the repo's own `npm run check`/`seal`, or any agent shell) read the OTHER install's assets and `enigma check` failed with 20 spurious `stale cliVersion (<installed> != <repo>)` problems the moment the two versions diverged. On-disk assets beside the code always win; the env value is the binary-only fallback. The launcher SETS these unconditionally (`=`, not `??=`): shells/tools spawned by an older enigma inherit the old values, and honoring them made a nested `enigma` report a stale version after an update (the "Update available 1.6.8 -> 1.9.0 while 1.10.0 is installed" bug). The only honored override is `ENIGMA_BIN_PATH`. Corollary: the compiled binary cannot run `node -e` scripts either (its execPath IS the binary; `-e` parses as a CLI flag), so the update notifier's detached child re-invokes the CLI with the hidden `__update-check` command (handled in cli.ts BEFORE parseArgs); only the node/tsx dev path keeps the classic update-notifier `-e` child, and bun-on-source re-runs `argv[1]`. If you add another self-spawning background job, use the same hidden-command pattern, never `-e`.
- Skills/memory are authored once under `packages/enigma-cli/assets/{skills,memory}` and deployed to every agent. Never create per-agent copies of a SKILL.md.
- After editing any SKILL.md or skill.json content, run `npm run seal` (or `enigma seal`) to refresh the `sha`, or the installer will not detect the change. Bump the skill's `version` for real content changes.
- DELIVERY TO EXISTING USERS IS `enigma update`, and the assets are bundled INTO the binary, so the ordering matters: `runUpdateCli` syncs deployments and only THEN lets npm replace the binary - that sync therefore deploys the OUTGOING version's skills, memory and commands. The new ones land via the hidden `__sync` command (cli.ts, dispatched before parseArgs like `__guardrails-hook`), which `runUpdateCli` spawns on the freshly installed `enigma` when `runUpdate()` reports success; `runUpdate` returns a boolean for exactly that. Without it a user who updates and then launches their agent DIRECTLY (not through `enigma <tool>`, which syncs on every launch) runs the new CLI against the previous release's policies until something else triggers a sync. Guardrail RULES need no such step - they are code inside the binary, so they are live the moment npm finishes - but a repo's committed `.githooks/guardrails.mjs` backstop is a snapshot and only refreshes when `enigma security` runs there again. Covered by `tests/update-sync.test.ts`, which runs `__sync` against a temp HOME with a fabricated deployment and asserts the deployed SKILL.md is byte-identical to this version's asset.
- Validate with `npm run check`; preview installs with `npm run enigma -- install --local --all --yes --dry-run` (runs the CLI from TS via tsx; must list claude, codex, opencode, kimi). To exercise the BUILT binary end-to-end (launcher -> compiled binary -> env-asset wiring), `npm run build:binaries` then `npm run dev -- --built install --local --all --yes --dry-run`.
- INSTALLING WITH NO NETWORK, AND PINNING WHAT GETS INSTALLED. Three outbound calls used to be unavoidable on a fresh install inside a closed runner: the Bun binary download from the GitHub Release (`bin/download.mjs`, lazily on first run when install scripts were skipped), the remote-skill check, and the background repo star + update notice. `ENIGMA_BIN_PATH` already covers the first (and `ENIGMA_DOWNLOAD_BASE` points the download at a mirror); `install --offline` now covers the rest. It works by publishing `ENIGMA_OFFLINE=1` into the process environment (`isOffline()` in `util.ts`) rather than threading a parameter, because most of what it has to stop is a DETACHED CHILD - `spawnLinterInstall`, `spawnDashboardPkgInstall`, `scheduleUpdateCheck`/`performUpdateCheck`, `starRepoInBackground` - which inherits the variable and stands down on its own; a parameter would have to reach every spawn site and would still miss the second-order ones. `shouldCheckRemote` returns false under it even with `force`. Setting `ENIGMA_OFFLINE=1` in an image therefore holds for every enigma command in it, not just the install. `install --assets-from <dir>` reads skills/memory/commands from a staged tree instead of the bundled `assets/` and IMPLIES offline (overlaying a GitHub cache on a deliberately staged tree defeats the point). OFFLINE STOPS REQUESTS, NOT THE CACHE, AND THE TWO ARE NOT THE SAME GATE. `--assets-from` names a tree, so that tree is the whole source and `resolveSkills()` skips the overlay outright once `useAssetsFrom` has moved the assets root. `isOffline()` does NOT touch the overlay: the cache is local state, and the same `resolveSkills()` feeds `syncDeployed`->`currentSkillSet`->`syncTarget`/`computePrune`, so hiding it under a container-wide `ENIGMA_OFFLINE=1` DOWNGRADED every adopted remote skill to its bundled version and PRUNED every remote-only one from the deployment - a destructive local change out of a flag that only stands outbound calls down. The provenance problem that motivated the gate is solved by REPORTING instead: the "Skills source" line is derived from `adoptedRemoteSkills()` (what the plan took), never from the cache directory or the stamp. Mechanically: `skills.ts` held `ASSETS`/`SKILLS_ROOT`/`MEMORY_ROOT`/`COMMANDS_ROOT` as module consts evaluated at import, which a flag cannot move; they are now a mutable `assets` plus `skillsRoot()`/`memoryRoot()`/`commandsRoot()` accessors, with `useAssetsFrom()` validating that the tree actually has a `skills/` directory before adopting it (a silently-empty install is the failure mode to avoid). `assets-dir.ts` is untouched - it still resolves the DEFAULT root, and `ENIGMA_ASSETS_DIR` still exists only for the compiled binary.
- WHICH SKILLS A RUN ACTUALLY USED (`--ref`, and the printed origin). Skills update from the repo without an npm release, so a pinned CLI version does NOT identify the skill set: two runs of the same image can install different skills as `main` moves. `install --ref <tag|sha>` / `update --ref` pin the source ref (it also beats `ENIGMA_SKILLS_REF` and stops the discovery manifest from relocating the ref - `pinnedRef`/`refIsPinned` in `skills-remote.ts`), and a pinned install forces the check rather than obeying the 10-minute throttle. A PIN DECIDES WHAT IS ADOPTED, not only what is READ: `refreshRemoteSkills` bypasses the strictly-newer version gate (and `inspectSkills` lets the cache win outright) when `refIsPinned`, because pinning to an equal or older tag is the ordinary reproducibility case and "fetched nothing" is the wrong answer to it. Unpinned runs keep the gate - that is what stops an install going backwards. The cache and its stamp are SCOPED PER REF (`skills@<readable>-<sha8>/`, `remote@<readable>-<sha8>.json`) so a pinned install cannot leave its older skills where a later unpinned run would pick them up, and the CLI publishes the pin as `ENIGMA_SKILLS_REF` for the same reason it publishes `ENIGMA_OFFLINE` - every read of the cache has to see it, not just the fetch that filled it. The suffix must be INJECTIVE, not merely filename-safe: `/` is legal in a ref, so the original lossy `replace(/[^A-Za-z0-9._-]/g,"-")` mapped `release/1.0` and `release-1.0` onto ONE tree, and under a pin the cache wins outright - the run would have adopted the other ref's skills. Hence readable-form + `sha256(raw).slice(0,8)`. `refDirSuffix` is built from the RAW pin and never validates it, because these are local paths (the replacement already removes every separator) and `refreshRemoteSkills` is documented as never throwing; validation lives in `pinnedRef`, called where the value reaches a URL and on the commands that take `--ref` (install, update). It is deliberately NOT run per-process in `run()`: a bad `ENIGMA_SKILLS_REF` in a shell profile would then break `statusline` and `version`, which never read a skill. `pruneRefCaches` caps ref trees at `MAX_REF_CACHES` (5, LRU by stamp mtime, the default ref exempt) so a harness pinning per commit does not accumulate one tree per build. Every install prints one line to record, derived from `adoptedRemoteSkills()` so it can neither over- nor under-report: `Skills source: <repo>@<ref> (commit <sha7>), N skill(s) over the bundle, CLI <version>` when something was adopted at a known commit, `<repo>@<ref> from the local cache (commit unknown), N skill(s) over the bundle` when the tree outlived its stamp, `bundled with enigma-cli <version> (nothing adopted from <repo>@<ref>)` when nothing was, or the staged tree under `--assets-from`. `skillsOrigin()` produces the origin with no network from the cached manifest plus the refresh stamp, and the stamp records the REF alongside the commit so a pinned run is never shown a commit that was fetched at a different ref.
- A HOOK IS WIRED BY ONE BINARY AND RUN BY ANOTHER, which is not a rare edge: nvm keeps a separate global `node_modules` PER NODE VERSION, so a machine that switches runtimes per project has an independent enigma install for each, at whatever version it was last updated to. `enigma install` writes the hook command as a bare `enigma __<something>-hook`, resolved through PATH at fire time - so a session under the older runtime runs a hook naming a command that binary never had. Observed with `__codegraph-hook` on 1.35.7 while 1.36.1 wired it: `parseArgs` printed `Unknown command: __codegraph-hook` and exited 1, which the harness reports as a hook failure on EVERY turn of every session in that runtime, forever, with nothing the user can act on in the message. `parseArgs` now exits 0 in silence for any unrecognised `__`-prefixed command (`tests/cli-dispatch.test.ts`): those names are machine-written into hook configs and never typed, so the safe reading of one this binary does not implement is "a newer enigma wired it", not "the user made a mistake". An ordinary unknown command still errors. NOTE WHAT THIS DOES NOT DO: the fix has to be IN the old binary to help, so it closes the class going forward and does nothing for an install already behind - that one is repaired by updating it (`npm i -g --prefix <nvm>/<version> enigma-cli@latest`, since `npm i -g` only ever reaches the ACTIVE runtime).
