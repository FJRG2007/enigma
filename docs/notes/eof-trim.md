# EOF trimming: the blank line agents leave behind (`src/trim.ts` + post-edit hook + pre-commit step)

- WHAT/WHY: every coding agent's write tool tends to end a file with an extra empty line, so a repo slowly fills with files whose last line is blank. Core-engineering-policy already SAYS "no blank last line" and it is skipped like any other skill rule, so this is the deterministic answer (same doctrine as guard/guardrails: `rules-are-persuasion.md`). Config `trim` (config.ts), default ON/opt-out, the `guardrails` precedent rather than the opt-in `autoLint`.
- THE RULE IS DELIBERATELY CONSERVATIVE (user-specified): a file is changed ONLY when it has at least one line of REAL CONTENT followed by one or more blank lines at the very end. Left untouched: an empty file, a file of only blank lines (some fixtures must look exactly like that), and a last line with content but NO closing newline. A CONTENT line is never rewritten either - `"a   \n"` keeps its trailing spaces, because trailing-whitespace trimming is a different convention and doing it here would edit a line the user may have meant. Blank lines INSIDE the file are the author's; only the run at the end goes.
- COST is the design point (user: "que no consuma apenas recursos ni tenga apenas latencia", small commits AND enormous ones). The check never reads a whole file: `stat` for the size, ONE positional read of the last 4 KB, and when there is something to remove `ftruncate` - no read of the body, no rewrite, no temp file. A 200 MB file therefore costs the same as a 200 byte one, and a clean file costs one read and nothing else. Files run through a bounded-concurrency queue (32 in flight, `trimAll`); no worker threads, because the work is filesystem I/O which Node already runs off the main thread. A blank run longer than the window doubles the read up to 1 MB (`MAX_TAIL`) rather than reading the file.
- BYTES, NOT CHARACTERS. The tail is decoded `latin1` so one char is one byte and string offsets ARE byte offsets - decoding utf8 would collapse multi-byte characters and truncate at the wrong point, cutting a `é` in half. Line endings survive for free: the fix only ever REMOVES bytes from the end, so the `\r\n` that terminates the last content line is simply kept. A NUL anywhere in the tail means binary and the file is skipped.
- THREE ENTRY POINTS, one core (`trimFile`): (1) `enigma __trim-hook` - the PostToolUse hook, trims the one file just written, ALWAYS exits 0 (a silent tidy, not a gate); (2) the pre-commit step, on the staged files; (3) `enigma trim --all`, the retroactive sweep over every tracked file. The hook is where the problem is cheapest to fix - in the same turn, long before a commit - and the commit step is the backstop for edits enigma never saw (a teammate's editor, a generator, a merge).
- PARTIAL STAGING IS THE ONE SUBTLE CASE. The pre-commit step fixes the worktree file and re-stages it, so the fix lands in the commit being made. But a file that is staged AND has further unstaged edits is deliberately fixed and NOT re-staged: `git add` would pull those unrelated edits into the commit, which is a far worse surprise than one blank line surviving. Those files are reported by name and the next commit picks them up. One extra `git diff --name-only` gets the set.
- IGNORE LIST (`.githooks/enigma-trim.json`, `{ "ignore": ["<glob>"] }`, same shape/location as the guard's `enigma-guard.json`) plus built-in skips: fixture/snapshot dirs, build output, and VENDORED trees (`vendor`, `third_party`, `node_modules`, `dist`, `build`, `coverage`, `.next`, `.venv`), plus the extensions where a trailing blank line is data (`.patch`, `.diff`, `.snap`) and the obvious binaries. WHY THIS EXISTS, learned the hard way here: the first `--all` sweep of this repo found 89 files, ALL of them under `assets/skills-registry` - vendored community skills whose per-file `sha256` and `bundleHash` are RECORDED in `registry.json` and VERIFIED by `autoskills-install.ts`. Trimming one byte changes the hash and the skill then fails integrity verification on install (measured: `metadata.json` f999316... -> 6b83bc8...). So the sweep would have silently broken the autoskills install path. `.githooks/enigma-trim.json` ignores `assets/skills-registry/**`; with it, enigma's OWN source is already clean and the retroactive sweep is a no-op.
- WIRING mirrors guardrails exactly, file for file: engine `src/trim.ts` (self-contained, Node builtins only, bundled into the CLI AND built to `dist/trim.js` by tsup, copied into a repo's `.githooks/trim.mjs` by `security.ts`; self-exec footer guarded by basename so the bundled copy stays inert; `globToRegExp` duplicated from guard.ts and marked `enigma:` to stay import-free). Deploy `src/trim-deploy.ts` (Claude PostToolUse hook via `applyClaudeHook`, opencode plugin `plugins/enigma-trim.js`, `applyTrimWiring`/`mirrorTrimWiring`/`setTrim`; Codex skipped, no per-edit hook). cli.ts: hidden `__trim-hook` dispatched before parseArgs + `trim` in COMMANDS + help. skills.ts: `applyTrimConfig` next to `applyGuardrailsConfig`, `mirrorTrimWiring` in syncAccount. settings-registry.ts `trim` toggle (General). security.ts copies `trim.mjs` and adds a shim line that IGNORES its exit code (it must never block a commit). dashboard-status.ts `trim` in the Enigma Systems panel. `ENIGMA_TRIM_PATH` in `bin/enigma.mjs`.
- NOT IN `npm run verify`. verify is a read-only gate; a step that rewrites files does not belong in it. The repo runs the trimmer from its own `.githooks/pre-commit` (last, after guard/guardrails/lint, so it only tidies what those already approved) and exposes `npm run trim` for the sweep.
- TESTS: `tests/trim.test.ts` (the rule and every shape it must not touch, line endings, multi-byte tails, binary/vendored skips, the widening re-read, the large-file path, the ignore list) and `tests/trim-deploy.test.ts` (hook add/remove/idempotent, COEXISTENCE with the guardrails hook - both are PostToolUse groups with the same matcher, so a group-identity bug would show as one overwriting the other - unparseable settings, opencode plugin). Both in ci.yml.
