# Secret protection: granular guard + prompt secret guard

- GRANULAR GUARD CONFIG. The guard's `~/.enigma-guard.json` (and per-repo `.githooks/enigma-guard.json`) gained THREE user lists ON TOP of the 6 boolean protections: `blockPaths` (extra globs to block), `allowPaths` (allowlist - skip ALL checks for matching files, evaluated FIRST so it wins over every rule), `secretPatterns` (extra secret regex sources). Schema/metadata/writer live in `src/guard-config.ts` (`GuardLists`, `GuardListMeta`, `GUARD_LISTS`, `setGuardList`; `readGlobalGuard` defends array fields; the writer now persists protections THEN lists so a protection toggle never drops the lists, and vice-versa). The self-contained `src/guard.ts` consumes them: `globToRegExp` (own glob->regex: `**` crosses `/`, `*` within a segment, no-slash glob matches basename), allowlist `continue`, blockPaths block, custom regexes folded into `scanSecrets`. guard.ts STILL imports nothing from enigma (keeps `dist/guard.js` standalone) but now EXPORTS the detection primitives (`SECRET_PATTERNS`, `buildSecretMatchers`, `findSecrets`, `redactSecrets`, `SecretMatcher`, `globToRegExp`) so other modules reuse ONE detection source.
- PROMPT SECRET GUARD (the "not only for git" part). Config `promptSecretGuard` (default OFF/opt-in) + `promptSecretMode` (`redact`|`reject`, default `redact`) in `config.ts`. When on, `accounts.ts launchTool` starts the proxy for Claude even if the measuring `proxy` flag is off (condition is `cfg.proxy || cfg.promptSecretGuard`) and passes scan options. `src/proxy.ts` `startMeasuringProxy(options)` gained `{scanPrompts, mode, extraPatterns}`: with `scanPrompts`, POST `/v1/messages` bodies are BUFFERED (the one place it is no longer a pure pass-through - default-off keeps it byte-faithful), scanned via guard.ts matchers (built-ins + `readGlobalGuard().secretPatterns`), then either redacted (placeholder, content-length rewritten, forwarded) or rejected (Anthropic-style 400, upstream never hit). New stats `redacted`/`rejected`/`lastBlockedAt` in `ProxyUsage` via `recordBlock`. The proxy `forward()` helper was factored out so both the streaming pass-through and the rewritten-body path share the upstream+measure logic. WHY the proxy (not a hook): the secret must be stopped BEFORE it leaves the machine to the model; the proxy is the only point that sees the outgoing request.
- LIST-SETTING UI (full visual editing in BOTH surfaces). `settings-registry.ts` `Setting` gained `kind:"list"` + `listValues`/`addItem`/`removeItem` + `itemHint` (cached/busted by `withReadCache` like the other accessors). `guardListSetting` builds one per `GUARD_LISTS` (globalOnly); the prompt-guard toggle + `prompt-secret-mode` choice live in a new "Prompt secret guard" category, the 3 lists are appended to "Commit guard". Bridged to the dashboard by `dashboard-settings.ts` (UiSetting `kind`/`items`/`itemHint`; `applySetting` handles `{op:"add"|"remove", item}`); the dashboard `index.html` renders chips + add-input (event delegation on `#settingsBody`, reloads on change). The TUI (`tui/opentui.ts`) adds a `listEdit` overlay (plain list view, single-letter keys: `a` add via the nested `listAdd` input overlay, `d`/delete remove, enter/esc done, mouse-click removes) - mirrors the identity-panel + add-input pattern; activating a `kind:"list"` row opens it instead of cycling. CLI: `enigma config <list-key> add|remove <entry>` (key alone lists) in `settings.ts`, before the boolean/choice path.
- TWO-VALUE CHOICE = SELECT, NOT SWITCH (gotcha). The dashboard/TUI render a choice as a SWITCH when `choices.length===2 && choices.indexOf(offChoice)!==-1`, else a SELECT. `enigmaChoice` ALWAYS sets `offChoice`, so a genuine two-action choice built with it (e.g. `prompt-secret-mode` = redact/reject, where neither value is "off") wrongly rendered as an on/off toggle. FIX: inline the `Setting` with `choices` but NO `offChoice` (so `offChoice` defaults to the sentinel "off", which is not in the list -> SELECT), exactly like `skill-update-policy`. `prompt-secret-mode` now does this; the boolean `read`/`write` face stays as a fallback (reject<->redact). When adding a 2-value choice that is NOT an on/off pair, do NOT use `enigmaChoice` - inline it without `offChoice`.
- DASHBOARD PORT (numeric, customizable from the dashboard). `dashboardPort` (config.ts, default 0=auto) is the dashboard's preferred bind port, a NUMERIC knob OUTSIDE the boolean/choice registry (same pattern as token-price/token-speed/plan limits): CLI `enigma config dashboard-port <0-65535>` (numeric branch in settings.ts), and a dedicated `POST /api/dashboard-port` route (writeDashboardPort, origin-guarded, validates 0..65535). `listenWithFallback` (dashboard.ts) tries the configured port FIRST when >0, then falls back to 80 -> 24282 -> ephemeral, so the dashboard always opens; the bound port is tracked in module `boundPort` and surfaced (with the configured `dashboardPort`) in the `/api/settings` GET payload. The dashboard `index.html` renders a static "Dashboard port" panel below `#settingsBody` (number input + Save -> `/api/dashboard-port`), populated by `renderDashPort(data)` from that payload; changing it needs a dashboard RESTART to rebind (the running server can't move ports live). Round-trips via config export/import (`dashboardPort` added to `NUMERIC_KEYS` in dashboard-config-io.ts). Test: `tests/dashboard.test.ts` covers the payload fields, prompt-secret-mode being a SELECT, the valid/invalid/cross-origin port writes. (dashboard 0.1.38.)
- INSTALL RECOMMENDATION. The git-hooks offer (`maybeOfferGitHooks`, security.ts) is now default-yes "(recommended)". `resolveSecretGuard` (skills.ts, after `resolveDashboard`) offers the prompt guard at install - default NO (the user required it off by default); honors `--prompt-secret-guard` (CLI flag + `InstallOptions.promptSecretGuard`). Status: `dashboard-status.ts` exposes `promptSecretGuard`/`promptSecretMode` + the block stats; the dashboard "Enigma Systems" panel renders state + measured redacted/rejected counts. Tests: `tests/guard.test.ts` (glob/matcher/redact + list persistence) and `tests/proxy.test.ts` (redact strips the key from the upstream body, reject 400s before upstream, clean body byte-identical). Test fixture credentials are built by string CONCATENATION at runtime so the repo's own commit guard does not flag the test files.
- SCAN MODES AND MACHINE OUTPUT (`--range`, `--json`, exit codes). `runGuard` used to take one boolean (`all`) and answer from two file lists: staged (`git diff --cached`) or every tracked file. Neither works POST-COMMIT: in a pre-push hook or a CI job on a branch nothing is staged, so the guard exited 0 having checked nothing, and `--all` reported pre-existing findings the change never introduced. `--range <base>..<head>` is the third mode - `git diff --name-only --diff-filter=ACM <range>` for the file list, and content and sizes read at that head through one `git cat-file --batch` / `--batch-check` over just the paths the range touched (a full-tree `ls-tree` plus one `git show` per file was a repo-wide walk and N spawns per pre-push; anything the batch does not answer for falls back to a single `git show`, so behaviour is unchanged), so it scans the COMMITTED blob rather than whatever the working tree holds now (a secret committed and then edited out of the worktree is still caught). `parseRange` normalizes `a..b`, `a...b` and a lone ref (`<ref>..HEAD`), and rejects a value with no non-dot character so `...` is a usage error, not an empty-sided range git silently matches nothing for. Findings are now structured first (`GuardFinding{severity, rule, file, line?, detail}`, `formatFinding` derives the text lines from them, so text and `--json` can never disagree); `--json` prints `{tool, ok, exit, mode, range, files, error, findings[]}`. Exit codes split: **0 clean, 1 blocking findings, 2 the guard could not run** - not a git repository (previously 0, i.e. "checked nothing" read as a pass), an unresolvable range, a git failure. `git` is spawned with `stdio: [ignore, pipe, pipe]` so git's own "unknown revision" splash no longer prints ahead of the guard's message and reads as two failures. Flag parsing lives in `parseGuardArgv`, the ONLY parser for the guard's flags: `cli.ts` dispatches `guard` by `argv[0]` (before `parseArgs`, the same early-dispatch as `gate` and `ssh`, with `--help` left to fall through to the command help page) instead of re-parsing them, because a second parser is how the CLI ended up honouring a flag the hook rejected. A `--range` with no usable value is a usage error (`usageError` -> exit 2) on every entry point, never a fall-back to the staged scan: in a pre-push hook that reads as "0 file(s) checked" and exits 0, the exact useless pass the flag exists to eliminate. That covers the EMPTY STRING (`--range "$RANGE"` with the variable unset - the shape a CI script actually produces) and a following token that is another flag, not only a missing one. `cli.ts`'s `next()` applies the same rule to every flag it parses. `cat-file --batch` framing: a header carrying a size (`<oid> <type> <size>`) is followed by that payload WHATEVER the type, and only `missing`/`ambiguous` are payload-free - a submodule gitlink is listed by `--diff-filter=ACM` and answered with its commit object, so skipping only the header desynchronized the stream and attributed one file's bytes to another file's path, silently, inside a security check. A non-blob maps to `null` (nothing to scan) rather than falling back to `git show`. DRIFT: `.githooks/guard.mjs` in THIS repo is a copy of the built `dist/guard.js`, so it goes stale the moment `src/guard.ts` changes and nobody re-runs `enigma security` - the hook keeps passing while running an older engine. `npm run check:hooks` (`scripts/check-hook-drift.mjs`, wired into CI after the build) rebuilds from source and fails on a mismatch. It covers `guardrails.mjs` and `trim.mjs` on the same terms: they are the same kind of copy run by the same pre-commit, and the guardrails one had drifted 14 KB behind source while the check watched only the guard (see guardrails.md).
- PRIVATE TERMS (real people's data). Agents copied real handles, community and server names, and real log captures from chat, logs and the database into tests and docs. Nothing generic detects a real name, so the user keeps a list: `privateTerms` in `~/.enigma-guard.json` (`enigma config guard-private-terms add <term>`, also the TUI and dashboard list editors via `GUARD_LISTS`). It is read ONLY from the user-wide file (`readPrivateTerms`, private-terms.ts), never from the per-repo `.githooks/enigma-guard.json`, which is committed and would publish the list. One matcher (`privateTermMatcher`) serves the commit guard (rule `private-term`, checked on the lines a staged change or `--range` ADDS, so a term already in a file such as a LICENSE credit never blocks later commits; `--all` reads whole files) and the edit-time guardrail `sec-private-term` (diff stage), so they never disagree. Matching: case-insensitive via explicit `[xX]` classes (the `i` flag would break the lowercase lookahead), whole word with camelCase and trailing digits allowed (`ZephyrQuill42`, `moonhavenServer`), never inside a longer word (`Orla` vs `Gorlavsk`), any run of space/`_`/`-` between a term's words, URLs blanked first, terms under 3 chars dropped. The finding never echoes the term (terminal, CI log, transcript). The guardrail re-reads the list per call and recompiles only on change, so a term added mid-session applies on the next edit. A repo without enigma's git hooks still gets the edit-time rule; only the commit backstop needs `enigma security`.
- The same matcher has a third use: `redactPrivateTerms` (private-terms.ts) replaces every term with the neutral word "example" (URLs kept) in text enigma publishes on its own behalf, called through `redactPublished` (guardrails.ts, which also runs `redactOperatorHome`) from every PR title/body, gate commit summary and squash message - see gate.md's "Private terms go through the same two layers". The attribution-guard hook (verified-completion.md) refuses an agent-written `git commit` / `gh pr` message carrying a private term the same way it refuses the home path, without echoing the value.
- PRIVATE VALUES, LEARNED (private-values.ts, private-values-learn.ts). Report: an agent fixing a deployment opened a PR naming the domain and explaining the server's, the user's and the internal IPs; another committed a fix to a different project carrying the user's data; another wrote the user's private repository names into a public repo's notes as a measurement source. The private-term list could not have caught any of it, because nobody lists every value they will paste. So the values are LEARNED: the Stop hook (verify.ts, independent of the `verify` setting) extracts hosts, IPv4 addresses and emails from the user's last prompts INCLUDING pasted blocks, and IPs only from the agent's reply (an address read from `nslookup` and explained is the one that reaches a PR; the hosts a reply names are mostly documentation). Stored user-wide in `~/.enigma/private-values.json` (120-day TTL, 400 newest), never in a repo. A value the working repository already carried when it was learned is recorded as PUBLIC THERE (`git grep`, one call, only for new values), so fixing a project's own API client is never blocked; everywhere else it is refused by the same three channels as private terms - the commit guard on added lines, the `sec-private-term` guardrail, and the commit/PR message hook - never echoing the value. Consent: `enigma private-values forget <value>`, or `enigma:allow-private-value` on the line. EXTRACTION PRECISION, measured over 150 real sessions' prompts: hosts need a TLD from a closed list (so `index.js`, `user.name`, `prisma.plans` never match) and a non-numeric registrable label (`Checker$1.run`); public infrastructure hosts are excluded, but per-customer hosting subdomains (`*.vercel.app`) are deliberately NOT, since they are the value; loopback, documentation ranges and public resolvers are not addresses of anyone; and a four-part version after a version word (`Current: 1.10.0.1`, `java=21.0.13.1`) is not an IP - every IP false positive in the replay was that shape, and the word boundary matters (`server 84.21.7.19` is an address). PRIVATE REPOSITORY NAMES: `enigma private-values sync [path]` (detached from the Stop hook, at most hourly, names every 3 days, visibility weekly) reads the user's and their organizations' private repository names with `gh` and the working repo's visibility. A name is refused ONLY in a repository known to be PUBLIC (cross references between the user's private repos are legitimate; unknown visibility blocks nothing), only when distinctive (a hyphen/underscore/digit, or 7+ letters and not a generic word), and never as a package specifier (`from "x"`, `require("x")`, a manifest key) - the only two hits over a public repo's whole tree were a published npm package and a same-named Python library. `guard --all` skips both layers: they judge what an agent is adding, and an audit of whole files would turn every old mention into a block.
