# Rules are persuasion, not enforcement (enterprise)

- Skills/memory only persuade the model; for real safety, back critical rules with deterministic gates: Claude Code hooks (settings.json), pre-commit hooks (gitleaks, lint-staged, typecheck), and CI (lint, typecheck, tests, `npm audit`/SAST). security-policy and dependency-policy each end with a "make it mechanical" section pointing at these gates.
- Deterministic gates (tooling distributor, no app test suite): `npm run check` (syntax + skills sealed, catching silent seal-drift), `npm run guard` (`src/guard.ts --all` via tsx: secrets, .env, node_modules), `npm run verify` (typecheck + check + guard). CI: `.github/workflows/ci.yml`. Auto-publish to npm: `.github/workflows/publish.yml` (on GitHub Release; needs `NPM_TOKEN`, checks tag==version). This repo's pre-commit: `.githooks/pre-commit` (`git config core.hooksPath .githooks`).
- CIPHERA-STYLE GATE (changed-LINES ratchet). The Ciphera style skill is persuasion-only and gets skipped; the deterministic backstop is `@enigmax/linter` (already in-repo, AST-accurate, parses `.astro`/`.vue`/`.svelte`/`.ipynb`). WHY changed-LINES not changed-FILES: the repo carries ~142 pre-existing style warnings, so a file-level gate would block almost every commit on unrelated legacy findings and train everyone to `--no-verify`. `scripts/lint-changed.mjs` (run via tsx, imports the linter's `lintFiles` API) intersects the linter's findings with the ADDED/MODIFIED line numbers from `git diff -U0` and fails on ANY finding that lands on a changed line (severity-agnostic - style WARNINGS block too, which the CLI's default error-only exit would not). Modes: `--staged` (pre-commit) and `--range <a...b>` (CI). Wiring: root script `lint:changed` = `tsx scripts/lint-changed.mjs`; `.githooks/pre-commit` runs the guard THEN `npm run -s lint:changed -- --staged`; CI `linter` job (`fetch-depth: 0`) computes the PR/push range and runs `lint:changed -- --range "$range"`. The CLI also gained a standalone `--strict` flag (fail on warnings too, not just errors; linter `0.4.1`) used by the skill's self-check fallback, not by the line-gate. GOTCHA: `npm run lint` = `npm run -w @enigmax/linter dev --` cd's INTO the linter package, so repo-relative paths passed to it silently resolve to nothing ("no problems found" = a false pass); run from repo root (`lint:changed`, or absolute paths) instead. The ciphera SKILL.md gained a "Self-Check (Before Declaring Done)" line pointing at `npm run lint` / `lint:changed` / `npx @enigmax/linter --strict`. To make the gate whole-repo blocking later, fix the backlog first (`npx tsx packages/linter/src/cli.ts packages apps`), then add a whole-repo `--strict` lint to `verify`.
- AUTOFIX BEATS A GUARDRAIL FOR MECHANICAL STYLE (linter `0.5.0`). Ask: an inline type literal was written `{ url?: string }` and an import list ended with a trailing comma, both against Ciphera - "make the guardrails or the linter fix it, whichever costs least". The two channels are NOT interchangeable: a guardrail rule can only BLOCK (exit 2 + stderr), which spends model tokens and a turn on a fix the tool can compute itself, and at the time it had no fix path at all (`guardrails.ts` reported, never wrote). It has one now - `FIXERS`, added later, repairs a flagged LINE before anything is reported (guardrails.md) - but the argument stands where it was aimed: a fixer is bounded to the single line the rule pointed at, so a rewrite spanning a declaration is still the linter's job. The linter's `fixText` is the opposite - the auto-lint PostToolUse hook rewrites the file in place before the model sees anything, so a correct file costs ZERO tokens. So mechanical style with a provably meaning-preserving fix goes to `fixText`, and guardrails keep only what has no safe rewrite. `fix.ts` gained `fixPunctuation` (an AST pass sharing a new `applyEdits` helper): every interface/type-literal member gets its terminating `;` (a `,` separator is replaced, a missing one inserted) and a named import/export list loses its trailing comma. ORDER MATTERS: it runs BEFORE `sortImportGroups`, not after - stripping a trailing comma shortens a declaration by one char, so sorting first lets two declarations that tie only while the comma is there come out length-DESCENDING, i.e. `fixText` emitting text `length-sorted-imports` then flags and `fixText(fixText(x)) !== fixText(x)`. Type-member semicolons never sit inside an import declaration, so the punctuation pass cannot disturb the sort. TypeScript treats `;`, `,` and nothing as the same type-member separator and ignores the specifier trailing comma, which is what makes both safe to apply unattended. The detection half is `require-semicolons` (extended to type members) + the new `no-import-trailing-comma`, so the changed-line gate still catches it when auto-lint is off (default). BIGGEST GOTCHA - THE PRETTIER STAND-DOWN: in a project that already has Prettier (`usesPrettier` in `fix.ts` walks up from `resolve(file)` looking for `.prettierrc*` / `prettier.config.*` / a `prettier` key in a `package.json`, and STOPS at the first directory holding `.git` so a stray `~/.prettierrc` cannot disable the fix repo-wide), the punctuation fix does NOTHING and the two rules behind it (`require-semicolons` over type members, all of `no-import-trailing-comma`) report NOTHING - Prettier strips a single-line literal's terminator and defaults to `trailingComma: "all"`, so the two write-hooks would flip the same lines forever, and reporting what the fixer refuses to fix would block the hook (`exit 2`) on every edited file. The verdict is resolved once per file in `buildContext` and threaded through `RuleContext.prettier`, so an embedded block answers like its container and no rule touches the filesystem; verdicts are memoized per directory. Everything else (whitespace, blank lines, final newline, import order, statement semicolons, the audits) keeps running there. GOTCHA: `ts.isTypeElement` also returns true for a CLASS or object-literal accessor (`get x() {...}`), whose body already terminates it - `parse.ts`'s shared `isTypeMember` adds the parent check (`isInterfaceDeclaration || isTypeLiteralNode`), and a test pins it. MEASURED over `packages` + `apps`: 464 new type-member findings in 99 files (all genuine, all the LAST member of a single-line literal; 0 comma-separated members, this repo already uses `;` between them) and 8 trailing-comma findings. Backlog is untouched by design - the ratchet only gates changed lines - and `npx tsx packages/linter/src/cli.ts packages apps --fix` clears it in one sweep when someone wants the diff.
- `src/guard.ts` is a self-contained (Node-builtins-only) commit guard: it is BOTH this repo's CI/hook scanner (run via tsx, or as built `dist/guard.js`) AND the engine `enigma security` copies into any target repo (`setupGitHooks` in `src/security.ts` copies the guard to `<repo>/.githooks/guard.mjs` and writes `pre-commit` + `enigma-guard.json`, then sets `core.hooksPath`). It locates the guard via `ENIGMA_GUARD_PATH` (set by the launcher) -> `dist/guard.js`. Keep it dependency-free and free of cross-module imports (tsup bundles it standalone). Its module footer self-executes only when `argv[1]` basename matches `guard.*`, so the copy inlined into the compiled binary stays inert. Protections toggleable via `enigma-guard.json`; env allowlist = example/sample/template. Hooks also cover GitHub CLI (`gh`) commits, since gh uses git.

- THE STYLE OF THE REPLY IS GATED TOO, and it was the last always-on rule that was not: `enigma verify` now scans the final assistant message for the compression violations the output-style block bans (see verified-completion.md). Prose in the kernel asks; the Stop hook checks. Zero tokens when the reply is clean - it is a regex, not a model call.
- CONTEXT COST IS A GATE TOO. `enigma check` fails when a bundled memory file (`assets/memory/*.md`) exceeds `MEMORY_BUDGET_BYTES` (24 KB, skills.ts), and the `ctx-memory-budget` guardrail blocks an edit to any `CLAUDE.md`/`AGENTS.md` over 40 KB. Both exist because "keep the always-on channel small" was doctrine long before it was enforced, and the repo's own `CLAUDE.md` still reached 215 KB. The structural fix is the same one the rule's message prescribes: `CLAUDE.md` is an INDEX (12 KB budget) and every subsystem's detail lives in `docs/notes/<topic>.md`, read on demand.
- INSTALLING SKILLS WITHOUT INSTALLING HOOKS (`--hooks`, `--no-hooks`, `--no-statusline`). Every install re-asserted the whole hook set into the agent's settings: PostToolUse (guardrails, trim, lint) and Stop (the completion gate), plus `statusLine` and `permissions.defaultMode`. That is right for a person's machine and wrong inside a harness that owns those events - two Stop hooks each deciding whether the agent may finish is a loop neither of them can see, and the integrator's only recourse was to delete the entry enigma had just written. `InstallOptions.hooks` (`HOOK_CLASSES = post-edit | stop`, parsed by `parseHookClasses` from `all`/`none`/a comma list) gates the four `applyXWiring` calls through one `wires(cls)` predicate; `--no-hooks` is `--hooks none`, `--no-statusline` skips the statusLine entry, and `--no-bypass` (which already existed) is what leaves `permissions.defaultMode` alone. Null means "wire everything", so nothing changes for an ordinary install. SCOPE GOTCHA: this governs the install RUN only - `syncDeployed()` (via `enigma update` and the pre-launch auto-sync) re-asserts the wiring, so the durable answer is still `enigma config verify|guardrails|trim|lint off`, and the skip message says so.
- PER-COMMAND HELP (`enigma <cmd> --help`). `--help` set one flag and printed the whole manual whatever command preceded it, so `enigma install --help`, `guard --help` and `security --help` all answered the same thing and none of them listed that command's flags or exit codes - the gate subsystem was the lone exception (`gateSubcommandHelp`, `axiSubcommandHelp`). `COMMAND_HELP` in `cli.ts` holds one usage block per command and `printCommandHelp` serves it before the general help; launch commands (`claude`, `codex`, `opencode`, packs) share `launchHelp`, which is also where the `--` passthrough is documented. `enigma help <topic>` takes the same route. A command with no entry falls back to the manual, so adding a command never breaks help - it only makes it less specific.
