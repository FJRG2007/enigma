# Guardrails: deterministic convention enforcement (`src/guardrails.ts` + post-edit hook + commit backstop)

- WHAT/WHY: the deterministic-gate answer to "skills get skipped so conventions (UUID keys, Prisma-for-TS) are not applied". A DATA-DRIVEN rule engine runs as a post-edit hook: after an agent writes a file, matching rules scan it and a BLOCK violation is fed back (exit 2 + stderr) so the model self-corrects in the same turn - zero model tokens until a violation. Adding a rule = one data entry (built-in array or `~/.enigma-guardrails.json`), never code. This is the CONVENTION twin of the auto-lint (`lint.ts`) STYLE hook and reuses that exact delivery channel. Config `guardrails` (config.ts), default ON/opt-out (a baseline enigma behavior, unlike the opt-in `autoLint`/`compress`). Decisions (user): name `guardrails`, default ON, scope Claude + OpenCode + commit/CI backstop.
- ENGINE `src/guardrails.ts` is SELF-CONTAINED (Node-builtins only, NO enigma imports) exactly like `guard.ts`: BOTH bundled into the CLI (cli.ts imports `runGuardrailsHook` for the hidden `__guardrails-hook` command) AND built to `dist/guardrails.js` (tsup entry) copied standalone into a repo's `.githooks/guardrails.mjs` as a commit/CI backstop. Self-exec footer guarded by basename `/(^|[\\/])guardrails\.[mc]?[jt]s$/` so the bundled copy stays inert (same reason as guard.ts). `globToRegExp` is DUPLICATED from guard.ts (marked `enigma:`) to stay import-free. `GuardrailRule = {id,label,files[](globs),scope:"file"|"project",pattern?(regex src),flags?,check?(project-check id),message,severity:"block"|"warn",skill?}`; `Finding`. `checkFile(file,content,projectRoot)` runs file-scope regex rules (line-by-line, non-global regex) + project-scope checks; `PROJECT_CHECKS` (coded, keyed by `check` id - NOT user-authorable, needs logic) has `ts-relational-no-prisma`. `loadRules()` = `BUILTIN_RULES` minus `disabled` + custom `rules`, read INDEPENDENTLY from `~/.enigma-guardrails.json` (ENIGMA_GUARDRAILS_CONFIG relocates it - REQUIRED for tests, else they pollute the real `~/.enigma-guardrails.json` via homedir(), the github.test lesson). `runGuardrailsHook()` reads the Claude/opencode PostToolUse payload from stdin (`tool_input.file_path`), block->stderr+exit 2, warn->stdout+exit 0. `runGuardrailsScanCli(all)` = standalone git scan (full-file, NO changed-line intersection - matches guard.ts precedent; the plan's changed-line idea was dropped as over-engineering).
- RULE MODEL EXTENSIONS. `absent?: string`: a file-scope rule fires ONLY when `pattern` matches AND `absent` does NOT match anywhere in the file ("X without Y") - how "reads request input WITHOUT a schema" is detected; the absent set is deliberately BROAD (every common validator) so precision > recall. `excludeFiles?: string[]`: globs that exclude a file even when `files` matches (used to exclude test files from the backend rules). `flags` uses `?? "i"` (nullish) so an explicit `flags: ""` means case-SENSITIVE (needed to tell a lowercase DOM `<input>` from a capitalized `<Input>` component); undefined -> "i". checkFile SKIPS comment lines (`COMMENT_LINE` = `//`|`#`|`*`|`--`|`<!--`|`{/*`) so a pattern mentioned in a comment never false-positives.

The native-dialog rule pattern `\bwindow\.(alert|confirm|prompt)\s*\(|(?<![.\w])(alert|confirm|prompt)\s*\(\s*["']` = window.* (unambiguously browser, no FP in a Node file) OR a bare alert/confirm/prompt with a STRING-LITERAL arg only (a native dialog takes a string; CLI libs clack/inquirer and custom design-system dialogs take a `{config}` object; an AI `prompt` is a string that is passed, not called with a string literal). `(?<![.\w])` lookbehind excludes method calls (`toast.alert(`, `p.confirm(`) and identifier suffixes (`renderPrompt(`); case-sensitive excludes capitalized customs (`<Alert>`, `Confirm()`). Verified 0 FP on enigma (clack `p.confirm`), the CLI reference repos (inquirer/clack object-arg), and AI repos (bare `prompt` variables); the only wild hits were 2 real TPs in claude-mem (a `confirm('...')` in a React LogsModal + its minified bundle). Result: 0 findings on the FastAPI wrapper / headroom(1001) / helio / autoskills / caveman; the only wild findings were 3 db-ts-orm-prisma on claude-mem (TS+SQLite/Postgres, no Prisma - correct opinionated warn). Go AND Rust deliberately SKIPPED for input-validation: Go's manual validation (`if in.X == ""`) is idiomatic with no detectable signature, Rust's serde typed deserialization already enforces shape - a rule for either would false-positive (honors "los que detecte con precision"). Stack-specific optimistic-UI/caching heuristics (TanStack useMutation-sin-onMutate) were NOT added as rules - they belong to the memory kernel (semantic, no reliable signature). The obstacle was never the signature, it was that an edit-stage rule scans a whole file and would have fired on every legacy component; against the ADDED lines it measures to 0 false positives.

- NO TYPOGRAPHIC DASH IN UI COPY (`ui-no-em-dash`, BLOCK) + VISUAL DENSITY (skill-only). Two halves of one ask ("the UI must not use the AI em dash; less borders/cards, no cards inside cards"), routed by the three-tier doctrine. (1) The DASH is gateable, so it is a rule over UI-rendering files (`*.tsx/jsx/vue/svelte/astro/html/htm/ts/js/mts/cts`; markdown deliberately NOT scanned - prose files legitimately vendor and quote third-party text). Severity is BLOCK, not warn, because a warn exits 0 and is never fed back to the model - the whole complaint is that the model keeps writing them, so it has to reach the model. Precedent: `db-uuid-pk` is equally opinionated and blocks. PRECISION (measured over ~1100 real UI files in `references/repos` + packages + apps): the character must sit BETWEEN TEXT (`[A-Za-z0-9)\].,:%!?]\s*[dash]\s*[A-Za-z0-9(\["'\`]`) - that one requirement removed the ONLY real false-positive class, the STANDALONE GLYPH (`return "-"` for an empty table cell, `<span>-</span>`, a CLI bullet), which is a deliberate symbol and not copy (283 -> 225 hits, all remaining ones genuine prose dashes). The leading lookahead then drops DATA lines: a sanitizer (`.replace`/`normali`), a character/entity table (`mdash`/`ndash`/`fromCharCode`/an escaped `\u201x`), an `enigma:`-marked line, and a TRAILING comment (`(?<!:)//` so a URL does not silence the line; the engine only skips a line that STARTS as a comment, and a dash in a developer note is not UI text). Escape hatches: `enigma:` on the line, or `enigma:allow-dash` anywhere in the file (via `absent`) for verbatim quoted text. HTML entities (`&mdash;`) are deliberately NOT matched - to a line regex an entity table and an entity in copy are identical. The characters are written as backslash-u2014/backslash-u2013 regex escapes in guardrails.ts and built with `String.fromCharCode` in the tests, so neither file contains what it forbids (and the rule never self-flags). enigma's own 203 source files: 0 hits. GLOB LESSON (same class as the `**/*.prisma` gotcha above): `**/dist/**` does NOT match a ROOT-LEVEL `dist/main.js` - `**` maps to `.*` and the pattern still requires a leading `/` - so every generated/vendored tree is listed twice (`**/dist/**` AND `dist/**`). The older fe- rules still carry the one-sided form. (2) VISUAL DENSITY is NOT gateable and there is an explicit NOTE in guardrails.ts saying so: "card inside a card" and "border with no information" are RELATIONAL (a container is redundant only relative to its ancestor and the surrounding spacing; a border is legitimate on an input, a table edge, a flush row list), so any regex over `rounded-lg border` flags correct markup - it stays in frontend-policy's expanded "Visual Hierarchy & Layout Restraint" (one surface level; spacing -> background tone -> border, never two of the three on one boundary; one light source for shadows) with a short pointer in frontend-design's restraint section. Copy rule lives in technical-writing-policy ("never a typographic dash", with the dash-is-the-subject and verbatim-quote carve-outs).
- NO VISIBLE CONSOLE WINDOW (`proc-windows-hide`, BLOCK) + the sweep. Ask: "a terminal opened on Windows and closed again - enigma must not do that". CAUSE: on Windows a console child (git, tasklist, taskkill, powershell, npm through a shell) started by a process with NO console of its own pops a real console window and closes it with the child. enigma's daemons and hooks are exactly such parents (the dashboard daemon, the gate daemon, an editor's PostToolUse hook), so `gate/daemon/recover.ts`'s powershell probe, `agents.ts`'s tasklist, the gate's git calls and the generated opencode plugins were all flashing windows. `windowsHide: true` suppresses it, is inert on macOS/Linux, and is inert on Windows when the parent already has a console - so it is safe everywhere except a spawn that is DELIBERATELY opening a terminal (`accounts.ts` passes `windowsHide: false` for the login flow, which the rule reads as an explicit choice and skips). 25 call sites fixed across src, bin and scripts.
- THE RULE IS A CODED FILE CHECK, the third kind after PROJECT_CHECKS and the `maxBytes`/`maxNamedImports` branches, and it introduced `GuardrailRule.fileCheck` + a `FILE_CHECKS` registry so the next one is a map entry rather than a new field. It has to be code because a call's options object routinely spans several lines and a line regex cannot see it: `missingWindowsHide` finds calls to bindings ACTUALLY IMPORTED from child_process (which is what keeps `regex.exec(...)` and `db.exec(...)` out, aliases included), BALANCES PARENS to read the whole call, then reads to the end of the closing line so a trailing `// enigma:` note still counts. Three shapes are deliberately NOT flagged because the file does not prove a defect: `stdio: "inherit"` (the child runs in the user's own terminal on purpose), options passed as a variable (`spawn(bin, args, opts)` - unknowable here), and an object that spreads another (`{ ...spawnOpts, env }` - the spread may carry it). MEASURED over 832 files of `references/repos`: 70 hits, every one a genuine unguarded spawn (claude-powerline's statusline, caveman's hook, claude-mem's services, headroom's proxy manager are all the same latent flash); enigma's own 318 tracked files are at 0 after the sweep. BLOCK for the ui-no-em-dash reason - a warn exits 0 and never reaches the model - and the hit rate was accepted where a style rule's would not have been, because the fix is one key, is never wrong, and the symptom is INVISIBLE to whoever writes the code on macOS or Linux.
- MEMORY KERNEL (the SEMANTIC half). Convention items with no reliable syntactic signature (optimistic UI - SUPERSEDED IN PART, its clearest shape is now `fe-server-first-mutation` at the DIFF STAGE, see below; cache reads short-TTL/localStorage, real-time form validation, "validate every input with a schema discriminated by event") are NOT gateable by regex, so they live in the ALWAYS-ON deployed memory (`assets/memory/{CLAUDE,AGENTS}.md`) as a new `### Engineering Defaults (Always-On)` block (plain always-on text, NOT an enigma-marker toggle - it must always apply), generic + tool-per-language (Zod/TS, Pydantic/Py, ...). This is the tier-1 "restate the non-negotiable skill core in memory so it survives skill-skipping" pattern. So the guardrails feature now spans BOTH levers: guardrails = syntactic gate, memory kernel = semantic default. SCALABILITY RULE (user-mandated, supersedes the old "all semantic conventions -> memory" default): the always-on memory file is loaded EVERY session, so it does NOT scale - it is reserved for a MINIMAL set of TRULY UNIVERSAL, cross-cutting defaults that apply regardless of task domain (the input-validation / reusable-component / no-native-dialog / real-time-form-validation kernels already there). A convention scoped to ONE domain (a frontend display convention, a specific library recommendation, a UX pattern that only matters when doing UI work) lives ONLY in its DOMAIN SKILL, NOT the memory kernel - the skill is progressive-disclosure (loaded only when that domain is in scope = zero token cost otherwise), which is the scalable channel. So route by THREE tiers: (1) file-local regex signature, precise, low-FP -> a guardrail engine rule (token-free); (2) domain-scoped semantic, no signature -> the matching DOMAIN SKILL only (never duplicate its detail into memory); (3) truly universal semantic, no signature, must apply to every task -> the always-on memory kernel, kept minimal. NEVER put the same convention in both a skill AND the memory kernel (the duplication wastes always-on tokens and does not scale). Concretely: the real-time client-side uniqueness check and the `<relative-time>` date-display convention are domain-scoped (frontend) -> they live in frontend-policy/validation-policy ONLY; they were removed from the memory kernel after being briefly (mis)placed there.

- ICON ACTIONS, NOT WORDS (`fe-icon-action-button`, BLOCK) + the accessible-name half (skill-only). Ask: "copy/remove and friends in the frontend should be icons to cut text, with their alt, unless the design or the user asks otherwise". Routed by the three-tier doctrine, and it lands in tier 1 + tier 2 with NOTHING in the memory kernel (it is domain-scoped to UI work, so the always-on channel would pay for it every session). (1) The RULE fires on a button whose ENTIRE content is one bare action verb (`Copy|Remove|Delete|Edit|Rename|Duplicate|Download|Share|Refresh|Reload`) over `*.tsx/jsx/vue/svelte/astro/html/htm/ts/js/mts/cts` with the two-form generated/vendored excludes. PRECISION comes from three choices, measured over ~1100 real UI files (packages + apps + `references/repos`): 10 hits, ALL genuine text action buttons, 0 false positives. (a) `<(button)\b[^>]*>` forces the whole element onto ONE line with nothing but the word inside, so a button that already holds an icon never matches - its `<svg .../>` contains a `>` - which is what makes "icon plus label" (allowed) distinguishable from "bare word" (the defect); the same `[^>]*` still catches the string-concat form the dashboard is written in (`'<button data-id="' + esc(id) + '">Edit</button>'`), since that has no `>` either. (b) The verb set is limited to actions with a universally read glyph that REPEAT per row or card; `Save`/`Cancel`/`Submit`/`Add`/`Set` and every multi-word label ("Delete project") are deliberately excluded - those are primary buttons whose job is to be read, and a bare-verb match is what separates them. (c) Case-insensitive on the tag so a `<Button>` component matches, with a backreference pairing the closing tag. BLOCK for the ui-no-em-dash reason: a warn exits 0 and never reaches the model. Escape hatches: `enigma:` on the line, or `enigma:allow-text-actions` in the file (via `absent`) - that IS the "unless the design or the user asks for it" clause. Line-based engine, so a multi-line JSX button is out of reach by construction (accepted recall loss). (2) The ACCESSIBLE-NAME half is not gateable - a rule cannot tell whether an `aria-label` names the right thing, and requiring one on every icon button would flag correct code - so it stays in frontend-policy's new "Icon Actions" section (`aria-label` naming the action AND its object, `title` for the tooltip, `aria-hidden` on the glyph, `alt` for an `<img>` icon, ~44px target, press state) together with the keep-the-word carve-outs (no conventional glyph, primary/confirm button, state toggle, design says so), plus a pointer in frontend-design's restraint paragraph. Enigma's own dashboard was the first consumer: curl Copy (now an icon with a check-swap on success), skills Remove, memory Edit/reset, project-config reset, account/profile Rename, and the skill-creator `eval_review.html` row Delete.
- NO-OP SAVE: MEASURED AND REJECTED AS A RULE. Ask: "if the user does not change a value, or changes it and puts it back, do not enable Save". The convention was ALREADY in frontend-policy (No-Op Detection, with the x -> z -> x example and "disable the Save button"), so the only open question was tier 1. Answer: NOT gateable, and there is a NOTE in guardrails.ts saying so. Three independent reasons: the dirtiness normally lives in a parent/store/form library, so its absence from the edited file proves nothing; the policy explicitly ALLOWS an enabled Save that short-circuits on click, so a missing `disabled` is not evidence of the defect; and identical markup is correct on a create form, which has nothing to compare against. Measured: only 2 save buttons in 108 form-capable files across the corpus (no signal at all), and the one shape that WOULD be a precise signature - dirtiness asserted by INTERACTION, a `dirty`/`hasChanges` flag assigned a literal `true` - returned 0 real hits and 2 false positives (claude-mem's CLI uninstall tracking whether it rewrote a config). A rule with zero measured true positives has unknown FP behaviour, which is precisely what the precision-over-recall doctrine forbids. So the ask was spent on the skill instead: frontend-policy's Forms & Save gained "dirty means different, not touched" (never raise the flag from an onChange), "valid is not dirty", normalize-before-comparing (trim always, case-fold only where the field is case-insensitive), keep a disabled Save visible with its reason, the load/after-save states, and the same check for autosave/blur-save.
- PINNED SIDEBAR + LINKS IN COPY: MEASURED AND REJECTED AS RULES (skill-only, tier 2), with a NOTE in guardrails.ts saying so. Ask: "the sidebar scrolls away with the page - put it in the frontend skills and in the guardrails if possible", and "when the copy names a link, link it". (1) The SIDEBAR defect is a RELATION between three declarations - pinned (`position: sticky/fixed`), a height bounded by the viewport, and its own `overflow-y` - which real stylesheets spread over several lines of one block, and this engine scans line by line. The Tailwind one-line form would be the exception, but the whole corpus (this repo, apps/web, `references/repos`) holds exactly TWO real sidebars and neither is Tailwind: zero measured true positives, the same evidence that rejected the no-op-save rule. It is also not a defect until the sidebar's content outgrows the viewport, so a rule would flag correct short ones. (2) The LINK one cannot tell COPY from DATA: a URL inside a string is far more often an API endpoint, a default, or a docs reference than UI text, and nothing in the string says which. Both went to frontend-policy instead ("Persistent Chrome Stays Put", "Links In Copy Are Links"), nothing to the memory kernel (domain-scoped to UI work). The instances were fixed directly: `apps/web` DocsLayout's `aside` (sticky with `height: max-content`, so anything past the fold was unreachable) gained `max-height: calc(100vh - 72px)` + `overflow-y: auto` + `overscroll-behavior: contain`, with the cap lifted again at the stacked breakpoint; the dashboard gained `linkify` (escape FIRST, then match on the escaped string, so nothing can reintroduce markup) behind the settings hints.
- CONTEXT BUDGET (`ctx-memory-budget`, BLOCK, 40 KB over `CLAUDE.md`/`AGENTS.md` basenames). The rule that keeps an always-on memory file from turning into a knowledge base - the failure that produced a 215 KB repo `CLAUDE.md` here, paid on every session regardless of the task. Size has NO regex form, so `GuardrailRule` gained `maxBytes?: number` (file scope) and `checkFile` branches on it BEFORE the pattern branch; the finding appends the measured size to the message so the number is visible without opening the file. BLOCK, not warn, for the same reason as `ui-no-em-dash`: a warn exits 0 and never reaches the model that keeps growing the file, and the fix (index + on-demand `docs/notes/<topic>.md`) is mechanical. The message teaches the three-tier routing (guardrail rule / domain skill / memory kernel) and names `enigma guardrails disable ctx-memory-budget` as the escape, since a project may legitimately keep a large hand-authored memory file. Only those two basenames are in scope: every other doc is read on demand and costs nothing until opened. The twin gate for enigma's OWN shipped kernel is `MEMORY_BUDGET_BYTES` (24 KB) in `checkSources` (skills.ts), which fails `enigma check`/`npm run verify` when `assets/memory/*.md` grows past it.
- MOBILE DRAWER TAKES THE SCREEN (`fe-mobile-drawer-full-width`, BLOCK) + the modal half in frontend-policy. Ask: "unless the design or the user says otherwise, on mobile the sidebar takes 100% of the screen". Tier 1 + tier 2. The gateable slice is a UTILITY-CLASS panel: an off-canvas element (`fixed`/`absolute` plus `inset-y-0`/`h-full`/`h-screen`) carrying a desktop width with no full-width base, in either class order. The same defect in a STYLESHEET is out of reach by construction - it lives inside a `@media` block and this engine scans line by line - which is the same wall the pinned-sidebar rule hit, and why that one stayed skill-only while this one ships. PRECISION came from one measured bound: the width must be a PANEL width (>=100px, >=10rem, a Tailwind step of 40 or more, or a viewport fraction). - WIDE NAMED IMPORTS -> NAMESPACE IMPORT (`ts-import-namespace`, BLOCK, budget 9 bindings per internal module per file). Ask: a 13-symbol `import { readConfig, readGlobalConfig, CONFIG_DEFAULTS, ... } from "./config"` is unreadable and grows with every new export, so import the module as a namespace (`import * as conf from "./config"`, then `conf.readConfig()`). A COUNT has no regex form, so `GuardrailRule` gained `maxNamedImports?: number` (file scope, a third coded branch in `checkFile` next to `maxBytes`), backed by exported `wideNamedImports(content, max)`. Two design choices carry the precision. (1) AGGREGATION per module per FILE, not per statement: `settings-registry.ts` imported `./config` three times (13 values + 2 type imports), and a per-statement count would let any file dodge the rule by splitting the list - the helper therefore sums every statement, multi-line ones included (`[^}]` crosses newlines), and reports the first statement's line plus the module and the total in the message. (2) INTERNAL MODULES ONLY (`^\.`, `^#`, `^[@~]/`): a bare specifier is a fixed, universally known surface that the ecosystem writes as named imports (`import { readFileSync, writeFileSync, ... } from "node:fs"` appears in ~20 files here and is idiomatic), while a project module's export list keeps growing - counting bare specifiers would flag correct code, and converting them would have been ~40 more files of churn for no readability gain. The 25 refs were converted with a throwaway codemod; three failure modes it hit are worth knowing if it is ever repeated: a re-export line (`export { a, b } from "./store"` in `recall/index.ts`) must NOT be prefixed, an object-literal property KEY that happens to match an imported name must not either (`renameProfile: (...) =>` in cli.ts), and `...spread` prefixes need a lookbehind that allows `...` while still rejecting `x.name`. `tsc --noEmit` catches all three (they are syntax or unknown-identifier errors), which is why the sweep was safe; `tests/` are NOT in the typecheck's `include`, so the one test file converted was verified by `bun test`. - AUTO-FIX (`FIXERS`, keyed by rule id, applied by the hook before anything is reported). Origin: "estas pequeñas cosas que diferencian un desarrollo de un dev a un agente de AI... a ser posible mediante código para ahorrar tokens lo arreglen si es posible con fallback al agente". A violation code can repair costs the model nothing - no message, no turn, no tokens - so the hook repairs first and reports only what is left, then RE-CHECKS the file and returns the fresh findings (a fixer that did not actually clear its finding is reported, never trusted). CONTRACT is deliberately narrow: a fixer gets ONE line (the flagged one) and returns its replacement or `null` to decline, so it can never touch a byte the rule did not point at; declining is always safe, guessing is not. Coded here rather than declared in the rule data for the same reason as FILE_CHECKS/PROJECT_CHECKS - it needs logic, and a rule from `~/.enigma-guardrails.json` must never be able to REWRITE a file. The first fixer (`fe-name-input-capitalize`) inserts `autocapitalize="words"` straight after the tag name (valid wherever the tag is, and no guess about where a tag that may end three lines later ENDS), picks `autoCapitalize` in `.tsx`/`.jsx` and the lowercase attribute elsewhere, and declines a custom `<Input>`/`<TextField>`/`<Controller>` (it may not forward an unknown attribute, so the write would clear the rule and leave the field just as broken) or a line holding two `<input>`s. The commit backstop stays read-only on purpose: a gate that rewrites files at commit time is the trim step's job, not this one.
- WHY `fe-name-value-normalize` EXISTS NEXT TO `fe-name-input-capitalize`, and it is the lesson: `autocapitalize` is a KEYBOARD hint. A phone honours it; a physical keyboard ignores it completely. So the original rule was satisfiable by writing one attribute while "juan perez" typed on a laptop was still stored verbatim - which is exactly what the user reported seeing on a "Your name" field. The `absent` regex of one rule cannot express "attribute AND normalizer", so it is two rules over the same pattern: the second clears only on a real normalizer (`capitalizeWords`, `toTitleCase`, `startCase`, `charAt(0).toUpperCase`, ...) and its half is NOT auto-fixable - where the normalizer belongs (the shared Input, the blur handler, the server) is a judgement call, so it falls back to the agent. Together they are the shape of the whole feature: code fixes the mechanical half, the model handles the half that needs a decision.
- PASSWORD IS NOT THE IDENTITY (`sec-password-identity-match`, BLOCK) + the semantic half in security-policy/validation-policy/frontend-policy. Ask: "en el login no permitas contraseñas iguales al username o al email, incluso variando mayúsculas y minúsculas". Tier 1 + tier 2, nothing in the memory kernel (auth is domain-scoped). TIER 1 is the TWIN of `sec-password-breach-check` over the SAME selector (`autocomplete="new-password"`), for the same reason `fe-name-input-capitalize` and `fe-name-value-normalize` are two rules over one pattern: a single `absent` cannot express "breach check AND identity check", and a form that does one is routinely missing the other. - AN ICON DOES NOT SHRINK (`fe-icon-shrink`, BLOCK) + the mirror rule in frontend-policy. - ONE-TIME CODE AUTO-SUBMIT: MEASURED AND REJECTED AS A RULE (skill-only, tier 2), with a NOTE in guardrails.ts. - WHY THE HOOK AND NOT THE SWEEP, which is the reusable part. The first cut put the repair in the turn-end sweep, and that one placement produced four review findings by itself: the sweep reads files git may have nothing pending for, so a repair there rewrites ALREADY COMMITTED code, the working tree silently stops matching the commit every later gate step reads, and the "commit it again" notice then needs a gap of its own - which was routed through the unfixed-violation message (ordering the model to edit code that was already fixed, and offering it an escape-hatch marker that would have cemented the bug), was droppable by the loop-safety budget, and could not be re-raised by the next sweep because the file was dirty by then. The post-edit hook has none of that shape: the file it is handed was JUST WRITTEN, so it is dirty by construction, there is no commit for the working tree to disagree with, and the channel that announces fixes already exists there. The general rule - a component that WRITES to source belongs where the write is indistinguishable from the edit in flight, never at a turn boundary where it can straddle a commit. `scanConventions` is READ-ONLY, and a test pins that.
- HOW THE HOOK BOUNDS A DIFF-STAGE REPAIR: `changedLineFilter` asks git which of the file's lines differ from HEAD, and a diff-stage finding reaches the fixer only when it sits on one. It FAILS SAFE, because the caller rewrites whatever it admits - an untracked file is new in its entirety so every line qualifies (`--untracked-files=all`, or git collapses a wholly untracked directory to a single `?? src/` entry and a new component in a new folder repairs nothing), and anything that cannot be resolved (no repository, a git that failed, no HEAD to diff against) yields nothing eligible rather than everything. `applyFixes` also wraps its post-write re-check: the write has already happened, so an exception out of a hand-authored rule must not discard the `fixed` list and leave the file rewritten with nothing said about it anywhere.
