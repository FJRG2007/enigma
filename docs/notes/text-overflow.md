# Text overflow: the flexbox rule almost everyone (including this repo) gets wrong

- SYMPTOM that started it: the committed dashboard screenshot showed the "Local API server (OpenAI-compatible)" card pushing its value tag and agent icons OUTSIDE the panel. Cause: `.sys-item` is a grid item and its `.k`/`.v` are flex items, all at the default `min-width: auto`, and `.v` was additionally `flex: 0 0 auto` - so a long label/value could not shrink and widened the row past its track. Fix: `min-width: 0` on the item and both halves, `flex-wrap: wrap` so the value drops to its own line, `overflow-wrap: anywhere` on the label, `flex: 0 1 auto` on the value.
- THE RULE, precisely (CSS Flexbox 4.5): a flex/grid item's automatic minimum size applies ONLY while its computed `overflow` is `visible`; any other value resolves it to 0. Consequence that cost a wrong guardrail rule here: Tailwind's `truncate` sets `overflow: hidden`, so `<div class="flex-1 truncate">` ALREADY shrinks and ellipsizes and does NOT need `min-w-0`. A `fe-flex-truncate-min-width` rule was written flagging exactly that, with three tests asserting the wrong behavior; the gate's reviewer caught it and a browser measurement confirmed it (`flex-1 truncate` fits; `flex-1` + nowrap with visible overflow does not; a flex item with visible overflow WRAPPING a truncating child does not). The rule was deleted - the real defect spans parent and child, so it has no single-line signature and stays in frontend-policy as guidance. `guardrails.ts` carries a NOTE where the rule was, so nobody re-adds it.
- WHAT IS GATEABLE, and the line it falls on: the LAYOUT half is not (it is a relation between an ancestor's overflow and a child's), the CLIPPING half is (the element that clips is the element that hides the value, so that one element answers "can the user still read this?"). Two rules: `fe-ellipsis-without-overflow` (text-overflow:ellipsis with no overflow value is inert - unambiguous) and `fe-truncated-value-unreachable` (a clipped dynamic value with no `title`/`aria-label`/tooltip on it or its wrapper). Everything else about variable-length text is semantic and lives in frontend-policy's "Text That Does Not Fit" section (domain-scoped = zero tokens unless doing frontend, per the 3-tier routing doctrine; it is NOT memory-kernel material).
- THE CLIPPING RULE AND ITS FIXER, and why this one is worth the volume. Report: "a card with a user's data deforms when the name is long, the buttons get squashed, the text drops half a line". The layout half of that was already all measured and rejected above; what had NEVER been gated is the OTHER consequence, which is that the value becomes unreadable with no way back. MEASURED with the shipped rule (not the helper - `checkFile`, so the rule's own `excludeFiles` apply) over 9370 UI files of 15 real product repositories (7494 `.tsx`, 1490 `.vue`, 325 `.html`, 55 `.astro`, 3 `.jsx`, 3 `.svelte`): 3489 lines declare a single-line clip - 3013 in `.tsx`, 460 in `.vue`, 10 in `.html`, 6 in `.astro` - and 1490 of them (43%) hide a dynamic value with the full string reachable nowhere. Nearly half of every line that clips, which is what forces the DIFF stage - an edit-stage rule would report those 1490 pre-existing lines on any unrelated edit to their files, forever - and makes the FIXER the point rather than a nicety: 1208 of the 1490 (81%) are repaired by code with no message, no turn and no tokens, and only the remaining 282 reach the model. The findings themselves land in `.tsx` (1444) and `.vue` (46), but the figure that tells the sigil exclusion below apart from silencing three dialects is the DIFFERENTIAL one, because a post-exclusion zero is exactly what silencing them would also produce: the number of template-dialect lines the PRE-exclusion child pattern would have flagged and the post-exclusion one does not is 0, so the exclusion removed no corpus finding at all - it removed a shape this corpus does not contain and a probe found. With 3 `.svelte` files the corpus can say nothing about Svelte either way, which is precisely why the `{#if}`/`{#each}` false positive had to be found by probing. The fixer copies the child expression into `title={...}` and declines everything it cannot copy safely - `{children}` and friends bare or dotted (not text, renders `[object Object]`), a fallback expression (`{host ?? "Not recorded"}` - copying `host` drops the fallback), a call, a capitalised component that may not forward the attribute, two elements on one line, and any non-JSX file. It builds its replacement out of the file's own source, so it passes a replacer FUNCTION to `String.prototype.replace` - a `$&`/`` $` ``/`$'`/`$$` in an attribute value is otherwise re-read as a substitution token and the "repair" corrupts the line. `line-clamp` is deliberately out of scope: a two-line clamp is body copy and a tooltip on a paragraph is not the convention.
- THE FALSE POSITIVE THE FIRST CUT SHIPPED, worth keeping because the shape recurs: `DYNAMIC_CHILD` was `/>\s*\{/`, which also matches the `> {` of an ARROW FUNCTION body - so `const truncate = (s, n) => { ... }` or a `useMemo(() => { ... truncate(x) ... })` was a BLOCK finding, the fixer correctly declined it, and the turn was denied over code that clips nothing with no exit but a marker on an unrelated line. Anchored with a lookbehind excluding every operator that ends in `>` (`=>`, `<=`, `>=`, `!=`, `-->`, `>>`). It removed no corpus finding, which is the lesson: a corpus scan measures VOLUME, not correctness - the shape was rare in product code and common in the code an agent writes, so only a probe found it. Any rule keyed on a bare `>` needs the same anchor. THE SECOND CUT SHIPPED THE SAME DEFECT ONE DIALECT OVER, found by probing again and not by counting: `>{` also opens a Svelte/Astro CONTROL BLOCK, so `<div class="truncate">{#if loading}...{/if}</div>` and its `{#each}`/`{/if}`/`{:else}`/`{@html}` friends were BLOCK findings in exactly the files the fixer declines by design - a denied turn with no repair available at all. The brace must open a VALUE, so the four sigils are excluded by lookahead (`>\s*\{(?![#/:@])`); a sigil is never the first character of an expression, which is why excluding the sigils is safer than enumerating the constructs. BOTH false positives removed zero corpus findings, which is the same evidence twice: a corpus scan measures volume and cannot validate correctness, so it can never be the thing that clears a pattern change.
- THE ENGINE CHANGE IT NEEDED, which is reusable: fixers ran ONLY at the EDIT stage, so a diff-stage rule could not have one. `applyFixes` now takes the stage its re-check runs at (re-checking at the edit stage would drop every diff-stage finding from `remaining` and report a failed repair as a success), and the POST-EDIT HOOK repairs at both stages while still reporting only at the edit one. It repairs a diff-stage finding only on a line git says differs from HEAD, and fails safe when it cannot tell. Pinned by a test that leaves a committed clipped line untouched while the line the same edit added is repaired. The placement is the load-bearing part and is written up in `guardrails.md`: the first cut put the repair in the turn-end SWEEP, where a file may be wholly committed, so the repair straddled a commit - working tree quietly disagreeing with the code every later gate step reads - and the notice that was supposed to cover for that had three ways to be lost. A component that writes to source belongs where the write is indistinguishable from the edit in flight.
- REJECTED WITH IT (measured over the same corpus, and the reason is always the same - whether a value is BOUNDED is not in the line): `whitespace-nowrap` on a dynamic value with no clipping (91 hits, majority correct - dates, amounts, durations, short type labels are what nowrap is for), a fixed-width box holding an unclipped value (207, same), and a translated string inside a hard box (10 candidates, about half `sr-only` spans or an input placeholder). The i18n question the report raised - "is this string translated? then its length is variable" - is a DESIGN-TIME check with no signature, so it went to frontend-policy as two questions to answer before laying anything out.
- VERIFY LAYOUT BY MEASURING, not by looking: `scripts/dashboard-preview.mjs` + Playwright (present in node_modules, CI-only as a dep) measuring `scrollWidth > clientWidth` and bounding rects against the container, across 1440/1024/768/390 AND with deliberately long text injected. Always confirm the check FAILS on the pre-fix CSS before trusting a pass - the first run here passed on both, which would have been a vacuous test. Regenerate the committed preview with `node scripts/screenshot.mjs` after a dashboard UI change.
