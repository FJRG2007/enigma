# Text overflow: the flexbox rule almost everyone (including this repo) gets wrong

- SYMPTOM that started it: the committed dashboard screenshot showed the "Local API server (OpenAI-compatible)" card pushing its value tag and agent icons OUTSIDE the panel. Cause: `.sys-item` is a grid item and its `.k`/`.v` are flex items, all at the default `min-width: auto`, and `.v` was additionally `flex: 0 0 auto` - so a long label/value could not shrink and widened the row past its track. Fix: `min-width: 0` on the item and both halves, `flex-wrap: wrap` so the value drops to its own line, `overflow-wrap: anywhere` on the label, `flex: 0 1 auto` on the value.
- THE RULE, precisely (CSS Flexbox 4.5): a flex/grid item's automatic minimum size applies ONLY while its computed `overflow` is `visible`; any other value resolves it to 0. Consequence that cost a wrong guardrail rule here: Tailwind's `truncate` sets `overflow: hidden`, so `<div class="flex-1 truncate">` ALREADY shrinks and ellipsizes and does NOT need `min-w-0`. A `fe-flex-truncate-min-width` rule was written flagging exactly that, with three tests asserting the wrong behavior; the gate's reviewer caught it and a browser measurement confirmed it (`flex-1 truncate` fits; `flex-1` + nowrap with visible overflow does not; a flex item with visible overflow WRAPPING a truncating child does not). The rule was deleted - the real defect spans parent and child, so it has no single-line signature and stays in frontend-policy as guidance. `guardrails.ts` carries a NOTE where the rule was, so nobody re-adds it.
- WHAT IS GATEABLE, and the line it falls on: the LAYOUT half is not (it is a relation between an ancestor's overflow and a child's), the CLIPPING half is (the element that clips is the element that hides the value, so that one element answers "can the user still read this?"). Two rules: `fe-ellipsis-without-overflow` (text-overflow:ellipsis with no overflow value is inert - unambiguous) and `fe-truncated-value-unreachable` (a clipped dynamic value with no `title`/`aria-label`/tooltip on it or its wrapper). Everything else about variable-length text is semantic and lives in frontend-policy's "Text That Does Not Fit" section (domain-scoped = zero tokens unless doing frontend, per the 3-tier routing doctrine; it is NOT memory-kernel material).
- THE CLIPPING RULE AND ITS FIXER, and why this one is worth the volume. Report: "a card with a user's data deforms when the name is long, the buttons get squashed, the text drops half a line". The layout half of that was already all measured and rejected above; what had NEVER been gated is the OTHER consequence, which is that the value becomes unreadable with no way back. THIS BULLET IS THE CANONICAL COPY OF THE MEASUREMENT and the only place a figure from it belongs: the `truncatedValueUnreachable` JSDoc and `guardrails.md` state the conclusion and point here, deliberately, because keeping three prose copies of one figure set in agreement is what let two of these drift out of it - a per-extension split left behind at an old width, a denominator left behind at an old pattern. A new or corrected number goes HERE and nowhere else. MEASURED with the shipped rule (not the helper - `checkFile`, so the rule's own `excludeFiles` apply), every figure below taken in ONE run over ONE file set: 9074 UI files of 15 real product repositories, across all seven extensions the rule scans (7202 `.tsx`, 1490 `.vue`, 321 `.html`, 55 `.astro`, 3 `.jsx`, 3 `.svelte`, 0 `.htm`). At the CLIP-PATTERN width, 3474 lines match (2998 `.tsx`, 460 `.vue`, 10 `.html`, 6 `.astro`); at the DYNAMIC-VALUE width, 1699 of those clip a value (1649 `.tsx`, 49 `.vue`, 1 `.html`), and 1490 of THOSE - 88% - hide it with the full string reachable nowhere (1444 `.tsx`, 46 `.vue`). EVERY FIGURE COMES FROM ONE RUN OVER ONE FILE SET AND SAYS WHICH WIDTH IT WAS TAKEN AT - each half of that sentence is a mistake this paragraph already made. Both halves of the 88% are measured through `DYNAMIC_CHILD`; the file count comes from the rule's `files`/`excludeFiles` globs, and a per-extension split carries the width of the total it belongs to. `CLIP_ONE_LINE` alone also matches the remaining 1775 lines, which render no value at all, so a denominator counted at that wider width mixes two measurements and understates the ratio to 43%. And a per-extension breakdown carried over from an earlier run - taken at that wider width, over the RAW walk of 9370 files before `excludeFiles` removed the test and spec ones - summed to 3489 and so exceeded the corpus-wide total standing two sentences above it. Two sums are what make either slip visible, which is why they are written down: 1699 + 1775 = 3474, and every per-extension split adds up to its own total. THE 1775 ARE NOT ONE CATEGORY. Only the `truncate` helper definition and its call sites are the arrow-function false positive below, the `=> {` the lookbehind exists to exclude; static copy and CSS carry no `>{` at all, so no version of `DYNAMIC_CHILD` ever matched them and they are out because they render nothing, not because a false positive was avoided. At 88% a clipped value hiding its own text is the DEFAULT in real code rather than an occasional slip, which is what forces the DIFF stage - an edit-stage rule would report those 1490 pre-existing lines on any unrelated edit to their files, forever - and makes the FIXER the point rather than a nicety: 1208 of the 1490 (81%) are repaired by code with no message, no turn and no tokens, and only the remaining 282 reach the model. WHERE THE FINDINGS LAND SAYS NOTHING ABOUT THE SIGIL EXCLUSION BELOW; the figure that tells it apart from silencing the dialects that split reports none in is the DIFFERENTIAL one, because a post-exclusion zero is exactly what silencing them would also produce: measured CORPUS-WIDE, over every extension the rule scans rather than the template dialects alone (the lookahead applies to all of them), the number of lines the PRE-exclusion child pattern would have flagged and the current one does not is 0. WHAT THAT ZERO ESTABLISHES IS NARROWER THAN IT LOOKS, and claiming more of it was the last correction this paragraph needed: it says the exclusion suppressed nothing the rule was already reporting anywhere in the corpus, so it is not silently hiding findings elsewhere. WHAT IT SAYS ABOUT FREQUENCY SPLITS THE FOUR SIGILS IN TWO, and collapsing them into one set was the correction before last. `#`, `:` and `@` are SVELTE-only, and naming Astro beside it - as the original report did, and as three rewrites of this bullet then repeated - is itself a claim wider than the evidence: Astro's template is JSX-EXPRESSION based (`{cond && <p/>}`, `{list.map(...)}`) and its control features are ATTRIBUTE DIRECTIVES (`set:html`, `client:load`, `is:raw`), not brace blocks, so an `.astro` file can no more write `>{#`, `>{:` or `>{@` than a `.vue` one (which interpolates with `{{ }}` and branches with `v-if`) or a plain `.html` one (which has no brace syntax at all). The rule scanning those three extensions for the shape is harmless; their clip counts are simply no evidence about it. That leaves 3 `.svelte` files, which is not a thin base but effectively none: the corpus can say NOTHING about how often those three sigils occur, and the exclusion for them rests entirely on the probe - which is precisely why the `{#if}`/`{#each}` false positive had to be found that way. `/` is not in that position. A JSX COMMENT child opens `>{/*`, so `<span className="truncate">{/* ... */}</span>` matches the clip pattern and the PRE-exclusion child pattern and is dropped by the lookahead - verified against the shipped rule, which returns 0 for it and 1 for `{user.name}` on the same element. There the corpus is not thin at all: 7202 `.tsx` files, 2998 of them carrying a clip-declaring line, and a corpus-wide zero across that IS a result for this sigil - not one line in the dialect that dominates the corpus changed verdict, so the exclusion is demonstrably not suppressing findings where the findings actually live. A comment is no more a value than a control block is, so dropping it is the same lookahead doing the same job one dialect over rather than a concession made to the template dialects. The fixer copies the child expression into `title={...}` and declines everything it cannot copy safely - `{children}` and friends bare or dotted (not text, renders `[object Object]`), a fallback expression (`{host ?? "Not recorded"}` - copying `host` drops the fallback), a call, a capitalised component that may not forward the attribute, two elements on one line, and any non-JSX file. It builds its replacement out of the file's own source, so it passes a replacer FUNCTION to `String.prototype.replace` - a `$&`/`` $` ``/`$'`/`$$` in an attribute value is otherwise re-read as a substitution token and the "repair" corrupts the line. `line-clamp` is deliberately out of scope: a two-line clamp is body copy and a tooltip on a paragraph is not the convention.
- THE FALSE POSITIVE THE FIRST CUT SHIPPED, worth keeping because the shape recurs: `DYNAMIC_CHILD` was `/>\s*\{/`, which also matches the `> {` of an ARROW FUNCTION body - so `const truncate = (s, n) => { ... }` or a `useMemo(() => { ... truncate(x) ... })` was a BLOCK finding, the fixer correctly declined it, and the turn was denied over code that clips nothing with no exit but a marker on an unrelated line. Anchored with a lookbehind excluding every operator that ends in `>` (`=>`, `<=`, `>=`, `!=`, `-->`, `>>`). It removed no corpus finding, which is the lesson: a corpus scan measures VOLUME, not correctness - the shape was rare in product code and common in the code an agent writes, so only a probe found it. Any rule keyed on a bare `>` needs the same anchor. THE SECOND CUT SHIPPED THE SAME DEFECT ONE DIALECT OVER, found by probing again and not by counting: `>{` also opens a SVELTE CONTROL BLOCK (Svelte's alone - Astro's template is JSX-expression based and its control features are attribute directives), so `<div class="truncate">{#if loading}...{/if}</div>` and its `{#each}`/`{/if}`/`{:else}`/`{@html}` friends were BLOCK findings in exactly the files the fixer declines by design - a denied turn with no repair available at all. The brace must open a VALUE, so the four sigils are excluded by lookahead (`>\s*\{(?![#/:@])`), `/` covering the JSX comment child as well; a sigil is never the first character of an expression, which is why excluding the sigils is safer than enumerating the constructs. BOTH false positives removed zero corpus findings, which is the same evidence twice: a corpus scan measures volume and cannot validate correctness, so it can never be the thing that clears a pattern change.
- THE ENGINE CHANGE IT NEEDED, which is reusable: fixers ran ONLY at the EDIT stage, so a diff-stage rule could not have one. `applyFixes` now takes the stage its re-check runs at (re-checking at the edit stage would drop every diff-stage finding from `remaining` and report a failed repair as a success), and the POST-EDIT HOOK repairs at both stages while still reporting only at the edit one. It repairs a diff-stage finding only on a line git says differs from HEAD, and fails safe when it cannot tell. Pinned by a test that leaves a committed clipped line untouched while the line the same edit added is repaired. The placement is the load-bearing part and is written up in `guardrails.md`: the first cut put the repair in the turn-end SWEEP, where a file may be wholly committed, so the repair straddled a commit - working tree quietly disagreeing with the code every later gate step reads - and the notice that was supposed to cover for that had three ways to be lost. A component that writes to source belongs where the write is indistinguishable from the edit in flight.
- REJECTED WITH IT (measured over the same corpus, and the reason is always the same - whether a value is BOUNDED is not in the line): `whitespace-nowrap` on a dynamic value with no clipping (91 hits, majority correct - dates, amounts, durations, short type labels are what nowrap is for), a fixed-width box holding an unclipped value (207, same), and a translated string inside a hard box (10 candidates, about half `sr-only` spans or an input placeholder). The i18n question the report raised - "is this string translated? then its length is variable" - is a DESIGN-TIME check with no signature, so it went to frontend-policy as two questions to answer before laying anything out.
- VERIFY LAYOUT BY MEASURING, not by looking: `scripts/dashboard-preview.mjs` + Playwright (present in node_modules, CI-only as a dep) measuring `scrollWidth > clientWidth` and bounding rects against the container, across 1440/1024/768/390 AND with deliberately long text injected. Always confirm the check FAILS on the pre-fix CSS before trusting a pass - the first run here passed on both, which would have been a vacuous test.
