# Autoskills: detect a project's stack and install matching skills (`enigma autoskills`)

- WHAT: a native port of the DETECTION core of `midudev/autoskills` (study clone `references/repos/autoskills`, MIT). `enigma autoskills [path]` scans the project, maps the detected technologies to community skills, and installs them SEPARATE from enigma's policy skills. These are DISTINCT skill kinds: policy skills (enigma's own, in `assets/skills`, global, sealed/provider'd) vs stack skills (third-party, project-local, fetched on demand). They never mix.
- DATASET (bundled, small): `assets/autoskills/skills-map.json` (~43KB, 98 technologies + 25 combos + frontend bonus + agent folders), GENERATED from the upstream `skills-map.ts` by a one-off tsx converter (RegExp->source string, Set->array). Rides the existing `ENIGMA_ASSETS_DIR`/`assets`-in-`files` wiring; `src/autoskills.ts` resolves it env-first exactly like skills.ts. Detection MUST be offline, so the map is bundled (never fetched). To refresh the map: re-run the converter against an updated clone.
- DETECTION (`src/autoskills.ts`, zero-dep, faithful port of upstream `lib.ts`): `detectTechnologies(projectDir)` scans npm/deno packages (`dependencies`+`devDependencies`+`npm:`/`jsr:` imports), `configFiles`, `fileExtensions`, Ruby `gems` (Gemfile), and `configFileContent` patterns (incl. `scanGradleLayout`/`scanDotNetLayout` multi-module scanning), across pnpm/npm/deno WORKSPACES, with per-dir caches. Returns detected techs + cross-tech `combos` + `isFrontend`. `collectSkills` flattens to deduped `owner/repo/skill` refs (+frontend bonus). `detectAgents` lists agents by their skills folder. Tested network-free in `tests/autoskills.test.ts` (synthetic temp-dir fixtures; in ci.yml).
- CONTENT ORIGIN = midudev's registry, fetched ON DEMAND (NOT vendored - 40MB/219 skills/~100 authors would bloat git + drag licensing). `src/autoskills-install.ts` `installStackSkills` fetches `index.json` from `raw.githubusercontent.com/midudev/autoskills/main/packages/autoskills/skills-registry` (cached 24h at `~/.enigma/autoskills/index.json`, `ENIGMA_AUTOSKILLS_DIR` override), resolves each skill NAME (last path segment) -> registry entry, downloads each file, verifies per-file `sha256` AND the whole-skill `bundleHash`, caches under `~/.enigma/autoskills/cache/<bundleHash>/<skill>`, then copies into the project's per-agent skill dirs (`AGENT_DIRS` map: `.claude/skills`, etc.; defaults to `.claude` = enigma's primary). Tracks installs in `<project>/.enigma/autoskills-lock.json` (carries no enigma provider, so enigma's own sync/prune ignores them). FAULT-TOLERANCE: a missing entry/failed download/hash mismatch fails only that one skill (reported), never throws out of `installStackSkills`; offline degrades to a stale cache. Verified e2e against the live registry (bun project -> the `bun` skill).
- WIRING: `autoskills` in the `COMMANDS` set + dispatch in `run()` + `printHelp`; `runAutoskillsCli` (cli.ts) prints detected techs/combos/skills, honours `--dry-run` and `-a <agent>`, then calls the installer. Web: docs page `apps/web/src/content/docs/autoskills.mdx` (order 2.5, between Commands and Configuration) + a `commands.mdx` entry + a landing card; the README "Privacy & productivity defaults" card was REPLACED by an "Auto-detect skills by stack" card (per user; privacy defaults still live in configuration docs). UPGRADE PATH (deferred): a shared top-level skills dir consumed by both CLI build and web, and a web catalog page reading the map.
- DASHBOARD AUTOSKILLS IS A DETECT -> PICK -> INSTALL FLOW (not one-shot; dashboard `0.1.54`). The project Skills view's "Detect skills" button no longer installs everything blindly. `dashboard-projects.ts` exposes TWO ops (the old `autoskills` install-all op was removed): `autoskills-detect` (`runAutoskillsDetect`) returns `{ detected: "<tech list>", skills: AutoskillItem[] }` where `AutoskillItem = {ref, name, sources}` (name = `parseSkillRef(ref).skillName`, sources = the techs/combos that matched), NO install; and `autoskills-install` (`runAutoskillsInstall`) which takes the user-selected refs. SECURITY: install RE-DERIVES the matched set from a fresh `detectTechnologies`+`collectSkills` and intersects with the selection, so a client can never inject a skill ref the project's stack did not actually match (it returns "None of the selected skills match this project's stack."). `applyProjectAction`'s return type was widened with `detected?`/`skills?`. UI (`index.html`): `autoskillsFlow()` calls detect, then `openAutoskillsModal(detected, skills)` shows a checkbox list (ALL checked by default) with Select all / Clear + Install selected / Cancel (resolves to chosen refs or null), then posts `autoskills-install`. The modal reuses `.modal.wide` + new `.as-*` styles. demo-mock stubs both ops. Test: `tests/dashboard-projects.test.ts` "autoskills-detect lists the stack's skills; install only accepts detected refs".
- POLICY SKILLS ARE READ-ONLY IN PROJECT SCOPE (dashboard `0.1.56`). The project Skills view ("Policy skills" section) used to render clickable per-app deploy chips (`data-pskill` -> op `skill` -> `setProjectSkill`). But enigma's policy skills are managed at GLOBAL scope and an agent reads BOTH global and project skills, so deploying a global policy skill per-project is redundant/confusing. So in `skillRow`'s `skillScope === "project"` branch the chips are now rendered DISABLED (no `data-pskill`), showing presence only (green = also in the project folder) with the tooltip "policy skills are managed at Global scope"; the dead `data-pskill` click handler in `onProjectControlClick` was removed and the section blurb updated. The BACKEND op `skill`/`setProjectSkill` is intentionally KEPT (CLI/API + `tests/dashboard-projects.test.ts` still use it) - only the dashboard UI made it read-only. Project-specific skills come from autoskills (community/stack), NOT per-project policy-skill deployment. If a future project-scope list shows non-policy skills, gate the disable on `source === "enigma"`.
