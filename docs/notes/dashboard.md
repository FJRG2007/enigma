# Local savings dashboard (`src/dashboard.ts` + `assets/dashboard/index.html`)

- A dependency-free (`node:http`) browser dashboard that VISUALIZES the compression savings. Data source is the SAME `~/.enigma/ccr/stats.json` plus a NEW append-only `~/.enigma/ccr/history.jsonl` (added to `ccr.ts`: `recordStats` now also calls `recordHistory({t,b,a})`; byte-size trim to `HISTORY_KEEP_LINES`; `readHistory()` exported via the compress barrel). No time-series existed before - the cumulative `CcrStats` alone can't draw a graph, so the JSONL is what makes the "saved per day" chart real. The HTML buckets points by day CLIENT-side.
- CONFIG `dashboard` (config.ts `DashboardMode = off|on-demand|always`, default `off`/opt-in). Default-when-enabled is `on-demand`, NOT a daemon: the server runs ONLY while `enigma dashboard` (alias `dash`) is open, so idle cost is zero. `always` keeps a lightweight detached daemon. This is a CHOICE setting but NOT `enigmaChoice` - it needs a side effect (hosts entry + daemon), so it's a custom `Setting` in `settings-registry.ts` whose write/writeChoice call `setDashboard` -> `setEnigmaValue` + `applyDashboardMode`. It lives in its OWN "Local dashboard" TUI category. Install prompt: `resolveDashboard` (skills.ts, after `resolveMinimalCode`) + `--dashboard <mode>` flag on `InstallOptions`.
- REACHABILITY (the headroom-divergent part): instead of `localhost:PORT`, map the bare hostname `enigma` to loopback in the OS hosts file (`ensureHostsEntry`, needs admin/root once - best-effort, reports `needsAdmin` so the caller prints the one manual line) and bind `:80` on 127.0.0.1 when free, so the user types `http://enigma`. Windows has NO privileged-port restriction, so binding :80 needs no admin there (only the hosts edit does). `listenWithFallback` tries `[80, 24282, 0]`; `dashboardUrl(port)` returns `http://enigma` (port 80 + hosts entry), else `http://enigma:PORT` / `http://localhost:PORT`. ALWAYS loopback-bound (never network-facing).
- IDLE COST is controlled the headroom way (studied in `references/repos/headroom/headroom/dashboard`): the HTML pauses polling while `document.hidden` (the `setInterval` fires but returns early), and the server serves a short-TTL (1s) cached `statsPayload` snapshot so concurrent polls never rebuild it. The browser dashboard never costs anything when the tab is not visible.
- DAEMON (`always`): `spawnDashboardDaemon` re-invokes the hidden `enigma __dashboard-serve` command DETACHED, copying update.ts's exact runtime branching (compiled binary re-invokes itself; node/bun re-run `argv[1]`). The child runs `serveDashboardDaemon`, which binds a port and writes the pidfile `~/.enigma/dashboard.json` `{pid,port,url,startedAt}` - so we track the CHILD's real pid, never the spawn pid (matters on Windows where a `.cmd` shim would otherwise hide it). `runningDaemon()` is a signal-0 liveness probe (EPERM=alive) that cleans a stale pidfile. The detached child inherits `ENIGMA_ASSETS_DIR` from the parent's env (set by the launcher), so the compiled binary finds `assets/dashboard/index.html` - same wiring as skills/commands, NO launcher change needed (`assets` already in package.json `files`). A `FALLBACK_HTML` constant covers a missing asset.
- `enigma dashboard` ALWAYS works on request regardless of the config value (the config only governs the background daemon); in `always` mode with a live daemon it just opens the existing URL instead of starting a second server. Tests: `tests/dashboard.test.ts` (bun; temp HOME; server routes + payload + stale-pidfile cleanup; wired into CI). It also DELETEs `ENIGMA_ASSETS_DIR` and `ENIGMA_VERSION` before importing: the stats payload reports the version installed on disk (manifest beside `ENIGMA_ASSETS_DIR`, falling back to `ENIGMA_VERSION`) and both are stamped by the launcher, so running the suite under an installed enigma would report that install instead of the version handed to `startDashboardServer`. To extend the dashboard data: add a field to `statsPayload` and render it in the HTML's `render()`; the asset is read env-first so no rebuild wiring changes.
- CHARTS: the per-day "tokens saved" graph uses a vendored charting library (Lightweight Charts v5 `AreaSeries`, `chart.addSeries(LC.AreaSeries, ...)`), shipped as a DE-BRANDED static asset `assets/dashboard/lib/chart.min.js` (renamed from the upstream filename) and served by the loopback server at `/lib/chart.min.js` (`dashboardLib()` cached read; 404 -> cards still render). NOT a CDN at runtime, NOT an npm runtime dep - a local file in the tarball (`assets` in package.json `files`), read env-first via `ENIGMA_ASSETS_DIR`. A native SVG was tried but looked worse for sparse data (a line/area needs >=2 points -> a single day rendered nothing); the user chose the library's look. DE-BRANDING (user request: no TradingView references, no watermark): the attribution logo is suppressed with `#tv-attr-logo { display:none !important }` in our CSS; the asset filename and all comments/docs/test strings avoid the vendor name; the ONLY retained reference is the Apache-2.0 `@license` header INSIDE chart.min.js, which the license legally requires and which is invisible to dashboard users - do NOT strip it (that would breach Apache-2.0). The HTML buckets history into ascending unique-per-day `{time:'YYYY-MM-DD', value}`, a 7D/30D/90D/All switcher drives `timeScale().setVisibleRange`/`fitContent`, and `subscribeCrosshairMove` shows a date+value tooltip. To bump the lib: re-download the same upstream standalone build, re-save as `chart.min.js`. The 196 KB minified blob passes `npm run guard`. UI text is Title Case (wordmark "Enigma"); footer/social logos live in the header `.nav` (GitHub/Discord/Ko-fi).
- BY-SOURCE PANEL: "Savings By Source" renders `stats.bySource` (see the compression-engine note's SOURCE ATTRIBUTION bullet) as one bar per origin sorted by tokens saved, with `prettySource` friendly labels, a `$` column and a calls count, via the generic `renderBreakdown(el, map, label, money)`. "Savings By Content Type" reuses the same helper over `stats.byType` (no `$` column).
- MONEY + EXTENDED METRICS (modeled on headroom's dashboard, but enigma is NOT a proxy so per-model/provider/cache/rate-limit/latency are impossible - it only sees the content + the calling app; review clone at `references/repos/headroom`). What IS feasible was added: (1) `recordStats(before, after, source, type)` now also keeps `byType` (per content-type json/log/text/code/diff/markdown) and `best` (max single saving) in stats.json, and history points carry `s` (source) so per-day $ is attributable; (2) MONEY is ESTIMATED client-side because enigma can't know the real model: `PRICE_1M` map (USD per 1M input tokens) keyed BY SOURCE (claude-code/claude->3, codex->2.5, default 3), overridable globally via `enigma config token-price <usd>` (`EnigmaConfig.tokenPrice`, default 0=use per-source; numeric setting handled by a dedicated branch in settings.ts `runConfigCli`, NOT the boolean/choice registry; surfaced in the `/api/stats` payload as `priceOverride`). `$ = savedTokens * priceFor(source) / 1e6`; "Money Saved" card + `$` per source + per-day `$` in the chart. (3) Cards expanded to 6 (Money/Tokens/Rate/Compressions/Avg-per-call/Best) in an auto-fit grid. (4) The per-day chart gained two button groups beside the range switcher: METRIC (Tokens|$) and MODE (Daily|Cumulative); `seriesValues()` derives the LC series from `dailyData` ({time,tokens,usd} per day) for the active metric+mode (cumulative = running sum), `redraw()` re-`setData`s + swaps the `priceFormat` formatter (`fmt` vs `fmtUsd`). Everything stays client-side over the existing payload (only `priceOverride` was added server-side).
- HISTORY-DERIVED PANELS (the "section B" of the headroom review - everything headroom shows that does NOT need a proxy): (1) "Recent Compressions" table (newest 20 history points: time, type, source, before->after, saved%); history points now also carry `c` (content type) for it. (2) "Savings History" table with a Daily/Weekly/Monthly `histToggle` (`periodKey` buckets history; ISO-ish week key), plus an "N active days · avg X/day" header stat (`renderHistory` keeps `lastHistory` so the toggle re-renders without a poll). (3) "Reversible Cache (CCR)" panel from a new `cache` payload field (`ccrCacheStats()` in ccr.ts: count + disk bytes of `*.txt` originals + the `MAX_ENTRIES`=500 cap). (4) Before/After panel gained Removed / Reduction (% of input sent) / Compression ratio (before:after). The proxy-only headroom features (rate-limit windows, native-cache analytics, per-model/provider, cost projection, output shaping, latency/throughput) remain out of scope by design.
- DASHBOARD UI IS AN ON-DEMAND PACKAGE (`@enigmax/dashboard`, `packages/dashboard`). The browser UI (page + the ~196 KB vendored chart lib) is NO LONGER bundled in enigma-cli: it was the only heavy, cleanly-separable part (the server/daemon/hosts/config/settings-bridge are tightly coupled to enigma internals and STAY in enigma-cli). Modeled on the `@enigmax/linter` on-demand pattern. The package is ASSET-ONLY (`files: ["assets","README.md","LICENSE"]`, no build/tsup/dist - just `assets/index.html` + `assets/lib/chart.min.js`, moved out of `enigma-cli/assets/dashboard` via `git mv`). `src/dashboard-pkg.ts` (Node-builtins only, no enigma imports -> no cycle) owns delivery: managed dir `~/.enigma/dashboard` (`ENIGMA_DASHBOARD_DIR` override), `isDashboardPkgInstalled()`, `ensureDashboardPkgInstalled()` (sync npm i @latest), `refreshDashboardPkg()` (force @latest), `spawnDashboardPkgInstall()` (detached via hidden `__dashboard-install` command, same runtime-dispatch as `__lint-install`), and `dashboardAssetsDir()` resolver with order: `ENIGMA_DASHBOARD_ASSETS` override -> managed install (`<dir>/node_modules/@enigmax/dashboard/assets`) -> DEV workspace (`<src>/../../dashboard/assets`, which is why the bun tests resolve assets with NO install) -> null. dashboard.ts reads HTML/lib via `assetPath()` and caches ONLY a successful read (so the background install replaces the FALLBACK_HTML without a restart); FALLBACK_HTML now auto-refreshes (`<meta refresh>`) while the bundle is being fetched. WIRING: `applyDashboardMode` (enable) calls `spawnDashboardPkgInstall()`; `runDashboardCli` (cli.ts) does a SYNC `ensureDashboardPkgInstalled()` before serving (so the first open shows the real page); `runUpdateCli` calls `refreshDashboardPkg()` ONLY when already installed (keep-updated = enigma's job, but never fetch for a user who doesn't use it). PUBLISH: `publish.yml` gained a version-new-guarded `npm publish --workspace @enigmax/dashboard` step (asset-only, no build) so the on-demand fetch + update always find the latest UI; the UI/server `/api/stats`+`/api/settings` contract is version-coupled and they release together from the monorepo (defensive HTML JS tolerates minor drift). The compiled binary NO LONGER needs `ENIGMA_ASSETS_DIR` for the dashboard (dashboard-pkg resolves independently); `assets/` still ships skills/memory/commands. To bump the UI: edit `packages/dashboard/assets/*`, bump its `version`, release. WHY only the assets moved (not the server): the server is enigma-coupled; moving the 196 KB bundle is the whole point (footprint off the base package for non-users).
- DASHBOARD SELF-UPDATE + AUTO-RELOAD (the page keeps itself current with no restart). TWO reload signals now ride `/api/stats`: the pre-existing `boot` (SERVER_BOOT, changes on a server restart) AND a NEW `ui` = `installedDashboardVersion()` (the served `@enigmax/dashboard` bundle version). The HTML `render()` records `loadedBoot`/`loadedUi` on first poll and `location.reload()`s once either changes - so when a background update swaps the bundle underneath an open tab, the tab reloads into the new UI. The GitHub CHECK is BROWSER-SIDE (the user asked for it "in the dashboard"; also the natural place - it can fetch GitHub and reload itself, and cross-origin client fetch is already used for `status.claude.com`): `checkDashboardUpdate()` fetches the raw `packages/dashboard/package.json` on `main` (`DASH_PKG_URL`, no API/auth/rate-limit), parses `.version`, and if `isNewer(latest, loadedUi)` POSTs the existing `/api/update` (which `refreshDashboardPkg()` to npm @latest + drops the html/lib cache); the reload itself is driven by the resulting `ui`-version change in the next stats poll, NOT an explicit reload, so a publish lag (npm behind the repo -> `changed:false`) simply retries next interval and there is ONE reload path. FAULT TOLERANCE (the explicit ask): an `AbortController` 8s timeout + try/catch swallow offline/timeout/CORS/bad-JSON and just retry on the 15-min interval; skipped while `document.hidden` and guarded by an `updating` flag + `loadedUi == null` (dev: no installed bundle -> `ui` null -> inert). Runs on load, every `UPDATE_CHECK_MS` (15 min), and on tab re-focus. WHY query the repo not npm: the user said GitHub; a repo rename 404s and degrades like any failure; gating the reload on the bundle actually changing absorbs the brief main-ahead-of-npm window. To change the source, edit `DASH_PKG_URL`. Test: `tests/dashboard.test.ts` asserts the `ui` key is always present in the payload (null when no bundle installed). Versions release together (dashboard `0.1.25`).
- STALE-CACHE BUG (why `enigma update` did NOT visibly update an open dashboard): `dashboardHtml()`/`dashboardLib()` cached the asset text in-process FOREVER on first read, so a running server/daemon kept serving the page it booted with even after `enigma update` (a DIFFERENT process) reinstalled the bundle on disk - the tab "reloaded" (via the `ui` change) but the server handed back the same old HTML. Fixed: `readAssetCached(cache, path, fallback)` keys the cache by the file's `(mtimeMs, size)` and re-reads when it changes, so an external bundle swap (or a dev edit of `packages/dashboard/assets/*`) is picked up on the next request with no restart. `serveUpdate` still nulls the caches for immediacy; the `(mtime,size)` key is the cross-process safety net `/api/update`'s same-process invalidation can't provide. The `installedDashboardVersion()` in `ui` is read fresh each snapshot, so the version bump that triggers the tab reload and the fresh HTML the reload then receives stay in lockstep. Test: `tests/dashboard.test.ts` "re-reads the page when the bundle changes on disk" rewrites index.html under `ENIGMA_DASHBOARD_ASSETS` and asserts the second GET returns the new content (different size so the key always differs regardless of mtime granularity).

- MEASURING PROXY + SYSTEMS OVERVIEW + UPDATE BUTTON + SECURITY VISIBILITY. (1) `src/proxy.ts` is an OPT-IN, default-OFF, Claude-Code-only measuring proxy (config `proxy`, `enigma config proxy on`). `launchTool` (accounts.ts) starts it when `toolName==="claude" && config.proxy && !env.ANTHROPIC_BASE_URL`, injects `ANTHROPIC_BASE_URL=http://127.0.0.1:PORT` for THAT launch only, and closes it in a `finally` on exit - so default-off behavior is byte-identical to before (the safety contract: it can't break anyone unless they opt in). It is a FAITHFUL pass-through (NOT headroom's transforming proxy - studied at `references/repos/headroom`, a huge Rust proxy I did NOT port): forwards method/path/headers(incl. auth)/body/stream verbatim to api.anthropic.com over HTTPS and streams the response straight back; the ONLY request change is dropping `accept-encoding` so `usage` is readable without gunzip. Upstream is hardcoded to Anthropic; `ENIGMA_PROXY_UPSTREAM` (http/https URL) overrides it for tests/mirrors (the e2e test points it at a fake local HTTP upstream). Tests: `tests/proxy.test.ts` (parseUsage cases + a real forward-and-record e2e), wired into ci.yml. - NO SIDEWAYS SCROLL AT ANY WIDTH (dashboard `0.1.95`). The rail change exposed a backlog the layout had carried for a while: at 390px the page scrolled sideways on accounts (+96px), skills/settings/resources (+69) and ssh (+55), and at 320px on savings (+61). VERIFY WITH THE LOOP, not by eye: `documentElement.scrollWidth - clientWidth` over all 12 views at 320/390/768/1024/1440/2560 - clean at every width, and the outermost offender is found by walking the DOM for `rect.right > vw` while skipping any element whose parent also overflows.
- TIME-SAVED CARD + REAL USAGE OBSERVER (the answer to "measure time saved, across all enigma systems, not just compression"). TWO additions, split by what is TRUTHFULLY measurable: (A) `tokenSpeed` config (CLI `token-speed`, default 0; numeric branch in settings.ts exactly like `tokenPrice`, NOT the boolean/choice registry; surfaced as `speedOverride` in `/api/stats`) drives a "Time Saved" card = `tokensSaved / tps()` where `DEFAULT_TPS=3000` (client-side in index.html). Labeled an ESTIMATE of *prefill* time (compression removes INPUT tokens), not generation. (B) `src/usage.ts` is the OBSERVER path: it reads the agent's OWN session transcripts for REAL token consumption + REAL prompt-cache savings, because that is the only enigma system whose effect does NOT flow through enigma's runtime (compression does; skills/output-style/minimal-code/commands deploy INTO the agent and enigma never sees the session). HARD HONESTY WALL baked into the design: a transcript records what WAS used, never the counterfactual, so usage.ts NEVER attributes savings to a skill/output-style (no baseline of "what it would have cost without them" exists) - that would be invented. It reports only measured facts (input/output tokens, `cache_read_input_tokens` = a genuine saving the tool already made) + per-day/per-model splits. CLAUDE CODE ONLY: reads `~/.claude/projects/<proj>/*.jsonl` (incl. nested `subagents/`); assistant lines carry top-level `timestamp` + `message.usage`{input_tokens,output_tokens,cache_read_input_tokens,cache_creation_input_tokens} + `message.model`. - DAEMON vs FOREGROUND (why a dashboard could end up unstoppable). `~/.enigma/dashboard.json` is written by BOTH the detached `always` daemon and a foreground `enigma dashboard` - deliberately, so a second invocation defers to the live server instead of fighting for the port. What was missing is WHICH one it is: `restartDashboardDaemon()` (run at the end of `enigma update`) read the record, killed the pid and respawned it DETACHED, so an update landing while a foreground dashboard was open killed the process the user's terminal was blocked on and left a background server in its place - the terminal came back, the dashboard kept serving, and Ctrl+C reached nothing (also silently turning `on-demand` into a permanent daemon). The record now carries `kind: "daemon" | "foreground"` (absent = daemon, which is what pre-existing records were) and `restartDashboardDaemon` no-ops on a foreground one. Regression test: `restartDashboardDaemon leaves a FOREGROUND dashboard alone` writes a record for a live spawned child and asserts both the return value and that the child survives.
- A PID IS NOT AN IDENTITY (why `enigma dashboard` "sometimes worked"). `runningDaemon()` decided a dashboard was alive from `process.kill(pid, 0)` alone, and a pid is just a number the OS reuses the moment the process dies - aggressively on Windows. So a leftover `~/.enigma/dashboard.json` whose server was gone kept resolving to whatever inherited the number, and the user got `already running (background) -> http://localhost:50325` pointing at nothing, with no way to tell it from a real one. REPRODUCED end-to-end: write a record naming any live unrelated pid, run `enigma dashboard stop`, and it reported "Stopped the dashboard" and KILLED that process. THREE parts to the fix: (1) the record now carries `beat`, refreshed every 20s by whoever is serving (`publishDashboard(rec)` replaces the bare `writeDaemon` in both the daemon and the foreground CLI and returns the teardown; the interval is `unref`'d so it can never be the reason a process lingers), and `runningDaemon()` rejects a record whose beat is older than 120s - a recycled process cannot forge it. A record with NO `beat` predates the field and keeps the old pid-only behaviour, so an upgrade does not orphan a dashboard that is still serving. (2) `liveDashboard()` (async) is the AUTHORITATIVE check and what the user-facing commands use: it asks the recorded port over `/health`, which now returns `service: "enigma-dashboard"` (so a foreign listener holding the port cannot pass for it) plus `pid` for same-machine callers only (so a recycled record pid is caught even when a DIFFERENT dashboard answers there). Probes `127.0.0.1:<port>` first, then the record's own URL - an exposed bind does not listen on loopback at all. `stopDashboard()` is the verify-then-kill twin; the sync `stopDashboardDaemon` stays only for `applyDashboardMode`, which is called from registry write paths that cannot await. (3) `restartDashboardDaemon` (run at the end of `enigma update`) now bails unless the mode is actually `always`: it only checked `isDaemonRecord`, so one leftover daemon record turned every update into a fresh detached server for an ON-DEMAND user, on an ephemeral port because the previous one still held 24282 - which is how one machine ended up with several dashboards and a different URL on every run.
- `enigma dashboard stop` (`runDashboardStopCli`) stops whatever is serving, daemon or foreground-whose-terminal-is-gone, and reports the url+pid. It exists because the only previous escape hatch was `enigma config dashboard off`, which also rips out the hosts entry and disables the feature; `stop` leaves the mode alone and says so when the mode is `always` (it will come back). `stopDashboardDaemon()` now returns the record it killed so the command can name it.

- RECALL BULK DELETE SILENTLY REJECTED (an allowlist that dropped a field, not a downstream bug). The Recall panel's multi-select posts `{op:"delete", ids:[...]}}`, but `writeRecall` (dashboard.ts) shapes every `/api/recall` POST body through an explicit per-field allowlist before handing it to `applyRecallAction`, and that allowlist carried `id` but not `ids` - so a bulk delete arrived downstream with no id in either shape and `dashboard-recall.ts` correctly answered `{ok:false,error:"missing memory id"}` for every selection, even though `applyRecallAction` already had full `ids[]` handling (`idList`-style int filtering, one `deleteRecallObservation` call per id) waiting for a payload that never carried it. Fixed by adding an `idList()` filter (`Array.isArray` + `Number.isInteger`) alongside the existing `strList()` one and threading `ids: idList(parsed.ids)` into the payload next to `id`. THE LESSON: an explicit per-field allowlist at a request boundary is exactly the shape that silently drops a field a client starts sending later - it fails closed (a validation error, not a crash), which is safe but easy to miss in review. Swept every other dashboard POST handler (codegraph, projects, packs, memory, skills, gate, resources, accounts, playground) for the same class of gap; none found. Regression test in `tests/dashboard.test.ts` drives the real HTTP API end-to-end (create three memories, delete one via `{id}`, the remaining two via `{ids}`, assert a body with neither shape still 400s) rather than unit-testing the allowlist function alone, so it fails the same way the original bug did.
