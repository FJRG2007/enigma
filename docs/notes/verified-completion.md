# Verified completion: the turn-end gate against false "done" claims (`src/verify.ts` + `enigma verify`)

- WHY: the reported failure was agents claiming a task/port/clone was finished when a whole module was missing or a complex implementation had been swapped for a regex. The persuasion layer ALREADY said this (the memory kernel's "as if lives depend on it" line predates the feature) and it still happened - which is the repo's own thesis restated: rules persuade, gates enforce. So the CLAIM is checked outside the model.
- MECHANISM (`src/verify.ts`, the third hook-delivery user after lint.ts and guardrails-deploy.ts): Claude Code's `Stop` payload carries `last_assistant_message`, so the gate reads the agent's OWN final message. `claimsDone(msg)` is the cheap pre-filter (one regex over one string) - a turn that claims nothing costs literally nothing, which is what keeps the feature token-free. Only on a claim does it scan EVIDENCE, matched against `INCOMPLETE_PATTERNS`, plus `verifyCommand` when set. Evidence + claim -> exit 2 (Stop hooks deny the stop and feed stderr back).
- STOP-SHORT is the SECOND face of the same failure, added after the reported case "¿Sigo con las tareas 5-8 en este orden, o prefieres otro?": the turn ends by ASKING permission to continue work the user already asked for. It is invisible to the claim path - the code it produced is clean, so `collectGaps` finds nothing and the claim check passes it - which is why `asksToContinue` runs FIRST in `runVerifyHook` and, unlike the claim path, reads NO git at all (the message announces the gap; there is nothing to corroborate). `CONTINUE_ASK_RE` only matches inside a sentence carrying a `?`, so "continuing with the CLI next" is a progress note, not a request. The asymmetry is INVERTED versus the marker scan: a missed ask costs one nagging question, a false block hits a question that HAD to be asked - so `LEGITIMATE_STOP_RE` is deliberately broad (credentials/access, destructive or irreversible verbs, business-legal-cost decisions, gate `ask-user` escalation, plan approval, "as you asked", plus `enigma:verify-ignore`), is matched over the WHOLE message, and doubles as the exit: naming the blocker clears the block on the first retry. Plan mode is exempt via `permission_mode` when the payload carries it. Loop safety reuses `mayBlock`/`issueKey` with a synthetic `kind: "stop-short"` gap whose detail is the question, so two identical asks stand the gate down while a different one gets its own budget.
- SKIPPED GATE is the THIRD face, and the most reported one of all: the AI quality gate is ON, the memory kernel says to drive it without being asked, and the turn ends with the work never sent through it. It arrives two ways and the module now checks both. (1) ANNOUNCED - `gateSkipped` reads the final message for the gate as SUBJECT (`GATE_TOPIC_RE`) plus either a not-run marker (`GATE_NOT_RUN_RE`) in the same sentence, or an offer (`GATE_OFFER_RE`) whose object is a RUN (`GATE_RUN_ACTION_RE`), with only the offer carrying the topic ONE sentence forward because that half is split by nature ("The gate has not run. Tell me if you want me to launch it."). No diff is read, exactly like the stop-short check. (2) SILENT - `gateGap` asks the run ledger whether any run has seen this repository since the newest commit ahead of the branch point.
- THE HOLE THAT LET IT THROUGH was in this file, not in the model: `LEGITIMATE_STOP_RE` carried a bare "enigma gate" alternative, meaning ANY message that named the gate was exempted from the stop-short check entirely - so the single phrasing the gate exists to catch ("el gate sigue sin ejecutarse ... dime si quieres que lo lance") was the one guaranteed to pass. The exemption is now the ESCALATION (`ask-user`) and the PR the run leaves ready for the user to review and merge, never the topic.
- FALSE-BLOCK CONTROL on the silent half is structural, because this one denies a stop over something that is not in the diff. Three conditions, each of which was a false block in its own right if dropped: the working tree must be CLEAN and only COMMITTED work counts (`preflightGuard` refuses a dirty tree outright, so a block there would order a run that cannot start, and the only way out would be a commit the user never asked for); only commits AHEAD of the branch point count (once the pipeline pushes, the branch stops being ahead and the finding clears itself); and the FIRST sighting of a repository only starts a watch (`gatewatch:<repo root>` in the state file) and never blocks, so a backlog that predates the check - or the gate being switched on - is never charged to the turn being judged. The watch is keyed by the REPOSITORY ROOT, not the payload's cwd, or a turn run from a subdirectory would collect a fresh first-sighting exemption for work already seen. `gateExpectedAt` also honors repo `gate: false` and `gateProtectedBranches`, which `axi run` refuses anyway. Consequence worth stating: a local-only repo on its default branch has nothing ahead of the branch point, so only the ANNOUNCED half covers it. That half deliberately keeps NONE of those conditions - a self-declared skip is a skip whether or not the tree is dirty, and it is the only cover in exactly the cases the silent half cannot see - so what it owes instead is a workable instruction: `gateMessage` names the commit-first step, because `axi run` refuses a dirty tree and committing what was just finished is part of finishing it, not a separate decision to hand back.
- THE ANCHORS MUST SURVIVE THE PRUNE, and did not at first: `mayBlock` caps `verify-state.json` at its newest 50 keys by insertion order, and that file is shared by every repository and session on the machine. `gatewatch:` (and the pre-existing `head:`) are written ONCE and never rewritten, so they were the first keys evicted - and an evicted watch re-arms at now, permanently exempting every commit made before that moment, which is the enforcement standing silently down. `ANCHOR_KEY_RE` holds them out of the prune, and BOTH are keyed by the repository root for it: `head:` was keyed by the payload's cwd, so exempting it traded a bounded file for one that grew by a permanent entry per directory a turn ever started in.
- THE TOPIC IS NOT ANY "GATE", and the first cut of it was too wide in exactly the repository that ships it: `the gate daemon`, `the gate view`, `the gate docs` are the daily vocabulary here, so a bare `the gate` read as the pipeline - plus an offer half that matches everyday closers (`let me know if`, `shall I`, `si quieres`) carried one sentence forward - classified ordinary prose as a skipped run ("Refactored the gate daemon ... Let me know if you want the docs note updated too."). Both halves were tightened together: a bare `the gate` only counts where the gate is the SUBJECT of what the sentence says it did (or the object of RUNNING it), and an offer only counts when what is offered is a run (`run it`, `que lo lance`). The not-run half no longer carries the topic forward at all - every real phrasing names the gate in the same sentence, while carrying it read "I skipped the flaky test" after any gate sentence as a skipped run. Two holes survived that first tightening and both were compound-noun holes wearing a verb: `ran the gate tests`, `restarted the gate daemon` matched the object-of-running alternative, which had no subject guard at all (and no `\b`, so `start\w*` matched inside `Restarted`) - `GATE_TAIL` now requires the clause to end after `gate` or to carry on ABOUT it. And the run-verb list was one list for both languages, so its Spanish stems spell English words (`corr\w*` = `correct`, `pas\w*` = `passed`): against the offer half's bare `it`, "let me know if you want me to correct it" became an offer to run the gate. `RUN_VERB_EN`/`RUN_VERB_ES` are separate now, and the pronoun only counts after `RUN_VERB_IT`, the verbs that cannot mean anything else.
- THE LEDGER OVERRULES THE MESSAGE on the announced half too (`gateValidatedHead`), for the phrasings that survive that precision: a report of a SUCCESSFUL run can still carry an offer to run it again, and blocking there would order a pipeline that had just run - with no phrasing left to clear it, since "it ran" is not one of the accepted reasons. A recorded run at least as new as the newest commit stands both halves down, and ONLY for the branch it ran on: the pipeline reviews, fixes and pushes one branch, so a run on `feature` vouching for commits sitting on `main` was the enforcement standing silently down over work nothing had seen. A record whose branch cannot be read is not held against it - the timestamp still decides there, because a false block is the worse failure. It does read the STATUS: a run that ended `failed` or `cancelled` cleared nothing, so `validatingRun` skips past it to the run it displaced - otherwise `axi run` then `axi abort` was a two-command way out of the check, since the ledger records terminal events exactly like every other state change.
- THE UPGRADE WINDOW IS A REAL FALSE-BLOCK SOURCE, so the silent check stands down until the ledger FILE exists (`gateLedgerReady`): the turn-end hook updates with the package while the RUNNING daemon does not, and a daemon that predates the ledger records nothing - which would read as "never validated" on every turn, including the one right after a successful run. The first recorded run anywhere on the machine turns enforcement on, and the announced half covers the gap meanwhile.
- `GATE_EXCUSE_RE` is the way out and mirrors `LEGITIMATE_STOP_RE`: the four reasons the kernel accepts (the user said to skip, repo `gate: false`, `gate-protected-branches`, nothing committed to validate) plus an `ask-user` escalation, the PR a finished run leaves for the user to review and merge (the same alternative `LEGITIMATE_STOP_RE` carries), and `enigma:verify-ignore`, matched over the whole message. Naming the reason clears it on the first retry - the message says exactly that, because a block with no stated exit is a trap. One exit is NOT a policy reason but a fact about the machine, and leaving it out made the block exactly that trap: `gate init` needs an `origin` remote (`gate/init.ts` throws without one) and the daemon can fail to come up, so a repo where the gate simply cannot stand up was blocked twice over an instruction that could not succeed, with no phrasing that cleared it. "No remote", an init or daemon failure, and `enigma gate doctor` are excuses now, and `gateMessage` names that exit alongside the other four.
- Its own budget channel (`gate:<session>`), for the same reason the convention sweep got one: sharing the completion-claim pool would let gate blocks spend it and silently stand the primary gate down for the rest of the session. The silent check runs LAST in `runVerifyHook` - after markers and the verification command - because a concrete finding about the code is the better thing to hand back first; the announced one runs early, beside stop-short, since a turn that hands the gate back will not be fixed by a note about a TODO.
- DELIBERATELY NOT GENERALIZED: the imperative offer without a question mark ("dime si quieres que siga", "let me know if you want me to continue") stays outside `asksToContinue`. Offering OPTIONAL extra scope is legitimate and reads identically, so the `?` requirement stays; the gate case is unambiguous only because an enabled gate is not optional scope.
- EVIDENCE SCOPE is ONE diff: `git diff --unified=0 <branchPoint>` (branch point vs the WORKING TREE, so committed and uncommitted work together) plus untracked files. Two mistakes were made here before landing on that, both caught by the gate's own reviewer: (1) diffing `HEAD` alone meant an agent that COMMITTED before ending the turn - the flow enigma itself prescribes - left an empty diff, so the gate found nothing and waved the claim through; (2) fixing that by UNIONing `HEAD` with `base..HEAD` then reported markers that had been committed earlier and since DELETED, blocking over work already fixed. A single diff against the branch point always describes the current state and needs no dedupe. `branchPoint()` resolves origin/HEAD -> origin/main -> origin/master -> main -> master and returns null on a detached HEAD / no remote / empty repo, where it falls back to `HEAD` (a turn-end hook must never break the turn). Still added-lines-only (the `lint-changed.mjs` ratchet), so pre-existing markers and anything already on the default branch never block.
- FIRST WIRING ANNOUNCES ITSELF: `applyVerifyWiring()` returns whether it changed the settings, and `syncDeployed` pushes a one-line notice when it actually installs the hook. Default-on + auto-sync means an existing user gets a BLOCKING hook on their next `enigma claude` without running an install (broader reach than guardrails, which only wires at install time); that reach is deliberate - an on-by-default gate that never reaches existing installs is off - but meeting it first as an unexplained blocked turn is not, so the one time it installs it says what it did and how to turn it off.
- IT MUST NOT FAIL OPEN QUIETLY - the failure it exists to prevent is a silent pass, so every degraded path is loud: a missing `last_assistant_message` falls back to `lastAssistantMessage(transcript_path)` (added to `claude-transcripts.ts`, which owns transcript reading - tail-reads 256 KB, since a transcript is unbounded but the last turn is at the end) and, failing that, writes one stderr line saying the check did not run; a cap that truncated the scan is reported by `VerifyScan.truncated` in both the CLI output and the block message. `runVerifyCommand` passes a 64 MB `maxBuffer` (Node's 1 MiB default KILLS a passing-but-verbose test suite and reports it as a failure - a false block, which is how a gate gets switched off) and inspects `result.error` so "could not run it" is distinguishable from "it failed" (a timeout also arrives as `result.error`, so it is told apart FIRST, else a merely slow suite sends the user hunting a typo). `readInto` checks BINARY-ness before size: a large image has no lines to miss, so calling that "only partially checked" would be noise in the one signal that is supposed to mean coverage was genuinely incomplete - only an oversized TEXT file sets `truncated`.
- `isVerifyOn()` (verify-deploy.ts) reads `readGlobalConfig()`, NOT `readConfig()`. The wiring it drives writes the GLOBAL agent settings and `syncDeployed` re-asserts it on every launch, so honoring a repo-local `verify:false` there would let launching from inside one project strip the hook for every other project (and flip-flop thereafter). The per-project opt-out belongs at RUNTIME, in `runVerifyHook` via `readConfigAt(cwd)` - which is what the test exercises.
- DISCLOSURE BEATS CLAIM, including WITHIN one sentence. "the port is complete except for two modules I could not finish" must NOT block - the gate targets SILENCE about gaps, never naming them. The first implementation evaluated `isClaim` first per sentence and mis-flagged exactly that case (caught by the test). `DISCLOSURE_RE` needs `(?<!no )falta` because "no falta nada" asserts the opposite and is a CLAIM.
- `stop_hook_active` is DELIBERATELY NOT honored (an early return on it was the first implementation and it was wrong). The flag stays true for every stop that happens while a turn continues because of a stop hook, so returning early capped the gate at ONE block per prompt and let an agent clear it by simply repeating "all done" with nothing changed - the exact behavior being gated - while making the whole `mayBlock`/`issueKey` machinery dead code outside tests. Loop safety is the evidence-keyed budget alone.
- GATE STEP AGENTS ARE EXEMPT: `runVerifyHook` returns 0 as its FIRST action when `isGateAgentRun()` (the `ENIGMA_GATE` marker `gate/agent/env.ts` stamps into every spawned step agent, upstream's `NO_MISTAKES_GATE`). A step agent answers with the structured JSON its step asked for, never a completion claim this gate could judge - and `claimsDone` matching a review finding that quotes "all done" would deny the stop, spending another agent turn inside a pipeline that already owns review, test, lint and its own approval gates. Measured cost of the hooks that did fire: ~260ms per hook process on top of a full-transcript `jq` slurp, per agent invocation, 6-12 invocations per run. The `PostToolUse` guardrails hook is deliberately still ON in gate agents: it enforces repo conventions on the files the gate is editing, which improves the fix rather than delaying it.
- LOOP SAFETY is structural, not hopeful: `mayBlock` counts blocks in `~/.enigma/verify-state.json`, standing down after 2. A Stop hook that can always re-fire is an infinite loop, so never rely on the model satisfying the gate. The key is `issueKey(session, gaps)` = session + a sha1 of the sorted finding identities (file + detail, NEVER the line number - editing above an untouched marker moves it and would hand the same unfixed finding a fresh budget forever), NOT the turn: keying it on `prompt_id` (not guaranteed in the payload) degraded to the session id, so two blocks anywhere silenced the gate for the REST of that session. Keyed by evidence, only a repeat of the same unresolved findings is capped - which is the only thing a loop can be - and a new problem gets a fresh budget. Per-findings alone is NOT enough, though: a model producing a slightly different finding set each round would earn a fresh budget forever, so `MAX_BLOCKS_PER_SESSION` (10, keyed `total:<session>`) is an absolute ceiling on top. `session` must never degrade to a shared constant - a payload with no session id falls back to the cwd, so two projects never share one budget.
- THE VERIFICATION COMMAND runs only when `scan.scanned > 0 && (all || hasNewWork(cwd))`. A turn that just answered a question must not pay for a 5-minute suite, and must never be blocked by a suite that was already red for unrelated reasons - that is a false block, and false blocks are how a gate gets switched off. `hasNewWork` = a dirty tree OR a HEAD different from `lastVerifiedHead(cwd)`: dirtiness alone skipped the command exactly when the agent had COMMITTED its work (the flow enigma prescribes), and the branch's line count is always positive on a branch with earlier commits, so every conversational turn paid. A pass calls `rememberVerifiedHead` (same `verify-state.json`, key `head:<repo root>` - the same checkout at the same commit, whichever subdirectory the turn ran from), so a passing suite is not re-run for a commit it already cleared.
- NOT A REPO = NOT A PASS: `gitOut` swallows git failures into "", so outside a repository every diff is empty and the gate would report clean. `inGitRepo(cwd)` (`git rev-parse --git-dir`) sets `VerifyScan.noRepo`, which the CLI reports as a failure (exit 1) and the hook states on stderr. Same class as the truncated-scan and missing-message cases: this feature's whole thesis is that a silent pass is the worst outcome, so EVERY degraded path has to say so.
- The `verify` setting is `globalOnly` in the registry: `setVerify` always wires from the GLOBAL value, so a local "on" would write the repo config, report success and install nothing. The per-project OFF still works (repo `.enigma.json` `verify: false`, honored at runtime by `readConfigAt(cwd)`), and that is the documented way. `readValue`/`dashboard-status` also read `readGlobalConfig().verifyCommand` - showing a merged one would advertise a command that can never run and let a cloned repo put alarming text on the settings screen.
- `eachAddedLine` only treats `+++ ` as a file header when the PREVIOUS line started with `--- `. An added content line beginning with `++ ` (patch fixtures, docs embedding diffs) otherwise hijacks the header and retargets every later finding to a path that does not exist. Same class of bug, same fix location: every git call passes `-c core.quotepath=false` (git escapes a non-ASCII path in the DIFF HEADER too, not just in `ls-files`) and the header strips a trailing `\t...` (git appends a tab + timestamp when the path contains a space). Both produce a path that cannot be opened, so findings point nowhere AND the `notNear` idiom exemption - which has to read the file - silently stops applying.
- A FRESH REPOSITORY IS NOT A TRUNCATED SCAN: before the first commit there is no HEAD to diff against, so `gitTry` returns null - which normally means "the diff failed, disclose incomplete coverage". `hasCommits(cwd)` (`rev-parse --verify HEAD`) tells the two apart; without it every brand-new repo reported "too large to scan in full" while its files were in fact all read as untracked.
- THREAT MODEL, stated honestly in the docs: both bypasses (`enigma:verify-ignore`, repo `verify: false`) are writable by the agent being gated. This stops ACCIDENTAL false claims - the thing that actually happens - and both leave a visible line in the reviewed diff; it is not a defence against a model actively evading it, and nothing running on the same machine could be.
- PRECISION (same doctrine as guardrails - a false block trains the user to disable it): doc extensions excluded (a plan legitimately lists TODOs), `enigma:verify-ignore` escape hatch, and a `notNear` lookback that reads the 5 preceding lines of the real file so a Python `@abstractmethod` raising `NotImplementedError` is not called a stub.
- PARITY (`src/verify-parity.ts`) is the half the gate CANNOT see - a module never written leaves no marker. It reuses codegraph's multi-language extraction via the NEW `scanFiles()` export (the read-only half of `indexProject`, factored out so parity never writes to the code-graph store) and matches symbols on a normalised name (`parse_config`/`parseConfig`/`ParseConfig` collapse), reporting per-source-module coverage; `absent` (0%) is the headline, `partial` (<60%) follows it, and both carry an `absentTotal`/`partialTotal` so a capped list never reads as the total. It is a COVERAGE signal only - a matched name never proves the behavior was ported - and both the report and the skill say so, because overstating it would recreate the exact problem. Same doctrine for a comparison that never happened: `empty` (no source symbols - mistyped path, unread language) and `truncated` (a scan cap left part of a tree unread) are reported as failures (`runVerifyCli` exits 1 on empty/truncated/absentTotal/partialTotal), because reporting an un-made comparison as 100% would turn the completion check into a rubber stamp.
- SECURITY: `verifyCommand` is read via `readGlobalConfig()` ONLY (never `readConfigAt`), because a repo-local `.enigma.json` is committable and travels with a clone - honoring one would make `git clone` + an agent run into arbitrary code execution. For the same reason it is in `NEVER_IMPORT` in dashboard-config-io.ts (a config bundle must not be able to plant a command). The `verify` TOGGLE is repo-local-readable (a repo disabling a gate is safe).
- CLAUDE ONLY, by capability not preference: Codex has no turn-end hook, and opencode's `session.idle` is fire-and-forget (cannot block or answer the model), so wiring either would only PRETEND to gate them. They get `enigma verify` + the memory rule, described as persuasion. `applyClaudeVerifyHook` also refuses to rewrite a settings.json it cannot parse (guardrails-deploy still overwrites in that case - fix it there if you touch it).
- SURFACES: `enigma verify [--all | parity <src> <dst>]` (exit-coded, so it doubles as a CI check), hidden `__verify-hook` (early dispatch + SYNCHRONOUS stdin read before the dynamic import, same reason as `__guardrails-hook`), registry settings `verify` (bool) + `verify-command` (`kind: "value"`, globalOnly), `applyVerifyConfig` at install + `mirrorVerifyWiring` in syncAccount, dashboard "Enigma Systems" row. Memory kernel gained the mechanical step (run `enigma verify`, and `verify parity` for a port) plus an explicit "never substitute a simplified stand-in" rule; task-completion-policy Phase 3 gained checks 4-5 and bumped to 1.3.0.
- DELIBERATELY NOT added to this repo's own `npm run verify`/pre-commit: `--all` reports every pre-existing TODO in the tree (including test fixtures that assert on the markers), so it would fail on day one and train `--no-verify`. Fix the backlog first if you want it blocking, exactly like the ciphera line-gate note above.
- CONVENTION SWEEP (`scanConventions`, gap kind `convention`), the third thing this hook checks and the first one that is not about a CLAIM at all. It runs the guardrails engine at its `diff` stage over the lines the change ADDED (guardrails.md) and denies the stop on a blocking finding. TWO HOLES IT CLOSES, both structural rather than accidental: the post-edit hook sees a WHOLE file, so a rule whose defect already exists in the codebase can never ship there (the optimistic-UI case: 116 of 140 mutating UI files in a real corpus), while the added lines carry no backlog; and a `warn` exits 0, printed to stdout where the model never sees it, so this is the ONLY channel that can reach it with one. SEVERITY IS NOT REDEFINED, deliberately - `block` findings deny the stop, `warn` findings ride along in the same message when something blocking already fired and are otherwise only recorded. Letting a warning stop a turn would have been trivial here and it is the wrong trade: a warn is advice by design (use fuse.js, consider AI Elements), and a gate that stops a turn over advice gets switched off, which costs the blocking rules too. A convention that must not be skipped is expressed the honest way, as a `block` rule - which the diff stage is what makes affordable. Checked BEFORE the claim path and independently of it: a broken convention is a defect whether or not the turn claimed anything, and the concrete fixable finding is the better thing to hand back first. Cost is one diff on a turn that produced code (the sweep returns immediately when there are no added lines), and the per-project `guardrails: false` stands it down. Findings go to the guardrails ledger with `blocked` or - when the loop-safety budget stands down, or the rule was only advisory - `warned`, so a rule the agent got away with skipping is still counted. THE BUDGET IS ITS OWN NAMESPACE (`mayBlock`'s `channel`, `conventions:<session>` beside `total:<session>`): sharing one per-session ceiling let a handful of heuristic convention findings spend it early and the completion-claim gate - the primary one - then stopped firing silently for the rest of the session, the exact failure this module exists against. ONE DIFF PER TURN: the hook computes `addedLines` once and hands it to both the sweep and `collectGaps` (`scanEvidence` takes the lines to reuse), and the sweep loads the rule set once for the batch and passes a null project root, so project-scope rules - whose findings carry no line and are dropped by the added-line intersection anyway - do not walk every file's ancestors. `capped` travels like the marker scan's: the model must be told its list was cut short, or it fixes everything it was shown and is blocked next turn by findings it never saw. `enigma verify` run by hand asks for the sweep (`conventions`) and prints the advisory findings too, without letting them touch the exit code.
- THE SWEEP READS AND NEVER WRITES, and that boundary was decided the expensive way. Guardrail FIXERS are real and a diff-stage rule can now carry one (guardrails.md), but they run in the POST-EDIT hook, not here. Repairing from the sweep was tried and reverted: this hook runs at a turn boundary, where a file may be wholly COMMITTED, so a repair rewrote code the commit still carries - enigma prescribes commit-then-validate, so every later gate step reads the unrepaired version while the working tree quietly disagrees with it - and the "commit it again" notice needed to cover for that could be dropped by the loop-safety budget, was written for unfixed violations (it told the model to edit code that was already fixed, and offered it an escape-hatch marker that would have cemented the bug), and could not be re-raised on the next sweep because the file was dirty by then. The post-edit hook has none of that shape: the file was just written, so it is already dirty, and the fixes are already announced there. THE RULE THIS LEAVES: a component that writes to source belongs where the write is indistinguishable from the edit in flight, never at a turn boundary where it can straddle a commit. `scanConventions` returning nothing but findings is pinned by a test.
- AN IDENTITY THAT CAME FROM NOWHERE (`unsourcedTrailers`, a fifth gap kind `source`, BLOCK). Report: "the agent invents data it does not know - I asked it to add me as co-contributor with my username and it wrote `Co-authored-by: FJRG2007 <team.fjrg2007@gmail.com>`; it does not know my email, and if I do not catch it, it ships". THE DEFECT IS NOT IN THE ARTIFACT, which is the whole reason this lives here and not in a commit hook: a correct address and an invented one are the same bytes, and a first-time co-author is legitimately absent from the repository's history, so a hook reading only the message must either miss the fabrication or block the honest case. What separates them is PROVENANCE, and the transcript is the only place that records it - the user either typed the address or they did not. So the check reads the session (`userTyped`, new in `claude-transcripts.ts`) and clears an address that appears in the repository's history, in `.mailmap`, in the local git identity, or in any of the USER's own messages. THE REPOSITORY SIDE IS READ THE WAY GIT READS IT, which took three corrections and is worth stating once: the history walk passes `--all` rather than defaulting to HEAD's ancestry, because a co-author who committed on another branch (main, while the work sat off it) has committed IN THIS REPOSITORY, which is all the rule asks - it is the same subprocess and the same `-n 20000` cap, and it cannot introduce a false clear that matters. The mailmap is read as `git show HEAD:.mailmap`, not `readFileSync(join(cwd, ".mailmap"))`, for two independent reasons. Git resolves it from the repository ROOT while `cwd` here is the Stop payload's, a directory the user freely sets to a monorepo package, so the path read found nothing there and denied the turn over an address the project had explicitly recorded - every other source was immune because `git log` and `git config` resolve upward on their own, and naming the file as a path into a commit hands that resolution back to git. And the COMMITTED tree rather than the checkout, because the block message tells the model to get the address from a source and writing the invented person into `.mailmap` reads like doing exactly that - the turn vouching for itself, the same class as a `tool_result`. THAT ONE IS NOT CLOSED, only raised: the bar is now "the turn wrote AND COMMITTED it", so an entry committed in the same commit as the trailer still clears the check (the existing mailmap test is exactly that shape and still passes, deliberately). The gain is that the entry sits in reviewable history instead of an unreviewed working-tree edit. `mailmap.file` and `mailmap.blob` are honoured too - they are the documented way a project relocates the file, and ignoring them left those projects falsely blocked for the same reason; they ride in one `config --get-regexp` with `user.email`, and `mailmap.file` is the one working-tree read left, kept because repointing it takes a config write rather than a file write. TOOL RESULTS ARE NOT A SOURCE and are excluded deliberately (only `text` blocks count): a `tool_result` is content this session produced, so reading one would let a value the agent invented three turns ago come back through its own `git log` output and vouch for itself - pinned by a test. A `user` RECORD IS NOT BY ITSELF A PERSON, which is the harder half and was nearly fatal: Claude Code stores a lot of non-human text under `role: "user"`, and the worst of it is THIS HOOK'S OWN FEEDBACK. The block message quotes the invented address verbatim (`credits <team.fjrg2007@gmail.com>`), the harness appends the Stop hook's stderr to `transcript_path` as a user record with STRING content, and the next turn read it back as the user having supplied the value - so the check cleared the exact fabrication it had just blocked, and the trailer shipped on turn two. The tool_result exclusion was guarding a hypothetical channel while the primary one stood wide open. `userTyped` therefore skips `isMeta === true` and `isSidechain === true` records (harness text and prompts the agent wrote for a subagent) and strips the synthetic tag blocks, listed in `claude-transcripts.ts` because that module is the leaf both sides can depend on. Measured against the transcripts on disk, BOTH filters are load-bearing: hook feedback and `<local-command-caveat>` carry `isMeta: true`, but `<task-notification>` (226 of the user text blocks, the LARGEST single channel), `<command-name>` (208), `<local-command-stdout>` (17) and `<command-message>` (11) carry neither `isMeta` nor `isSidechain`, so a flag check alone would have let a slash command's own `git log` output - or a background agent's own report of the commit it just made - vouch for an address. The blocks are STRIPPED rather than used to reject the record, because a genuine prompt routinely carries an appended `<system-reminder>` and discarding it would lose what the user really typed - a test pins both directions. THE STRIP RUNS BEFORE THE UNCLOSED-TAG TEST for the same reason: the open-tag check exists for a truncated block, and applying it first discarded any record that merely OPENS with a closed one. `<command-args>` IS THE ONE TAG THIS LIST DELIBERATELY DISAGREES WITH recall's `cleanText` ON, and the divergence is recorded at both ends so nobody reconciles it: `/commit please credit me@example.org` is stored as `<command-message>`, `<command-name>` and `<command-args>` in one user string, and only the first two are the harness naming the command - the third is the user typing. recall drops all three because it summarizes INTENT, for which arguments are noise; this module keeps the third because it adjudicates PROVENANCE, for which they are the evidence. Dropping it read an address the user typed verbatim as unsourced. IT FAILS SAFE IN EVERY DIRECTION, since a false block here denies a turn over a correct commit: no repository, no readable history, no transcript path, or a transcript larger than the 8 MB scan window all mean "cannot tell", and `userTyped` returns null rather than false for exactly that reason - absence is only evidence once you have read everything. THE RANGE IS HEAD, ONLY WHILE HEAD IS UNPUSHED, AND ONLY IF ITS COMMITTER DATE FALLS INSIDE THIS SESSION (`log -n 1 HEAD --not --remotes` with `%cI` in the `--format`). Three conditions, each carrying its own reason, and none of them sufficient alone. It is emphatically NOT `branchPoint..HEAD` - the branch point resolves to HEAD itself when the work sits directly on the default branch, so a `base..HEAD` range is empty and the check saw nothing at all on the workflow that commits straight to main, which is the reason a naive base-diff was rejected and still is. It is not the whole unpushed RANGE either (`HEAD --not --remotes` with no `-n 1`, which is what shipped first): THE REMEDIATION THIS CHECK PRESCRIBES IS AN AMEND, AND AN AMEND ONLY REACHES HEAD, so a finding on any older commit would be ordering an interactive rebase - a rewrite of history, the exact outcome the check exists to prevent. A finding it cannot offer a safe fix for is better not raised at all. THE UNPUSHED CONDITION IS THE SECOND, and the first round overstated what HEAD-only bought by claiming it removed the no-remote false block outright: it does not, because an old honest trailer can BE HEAD. What unpushed adds is that any tip which ARRIVED FROM THE REMOTE is out of scope - the provenance evidence is PER SESSION while a commit is not. The case that makes it concrete - keep it, it is what makes the reason obvious to whoever reads the code next - is a pulled GitHub squash-merge: it carries a `Co-authored-by` whose address is in neither `%ae` nor `%ce`, since squashing discards the co-author's own commits, so an honest trailer was blocked twice a session and told to amend already-shared history. `--not --remotes` also costs nothing extra, since it rides in the same `git log` that reads the message, and it excludes nothing in a repository with no remote configured - correctly, since that history is all local and all amendable. THE COMMITTER DATE IS THE THIRD, and it exists because the second one was in turn overstated as scoping the check "to what this turn can still fix" - amendable is not the same as authored here. An unpushed feature branch whose HEAD carries an honest trailer the user typed in an EARLIER session satisfies both conditions above: nothing was pushed so `--not --remotes` excludes nothing, a co-author who has never committed is in neither `%ae` nor `%ce` across `--all` nor in `HEAD:.mailmap`, and the current session's transcript has never heard of the address - so the turn was denied over work it had not touched, and the remedy amended someone else's commit. `%cI` rides in the same `--format` for no extra subprocess, and the session clock comes from the transcript itself (`sessionStartedAt`, in `claude-transcripts.ts`): the first TOP-LEVEL `timestamp` in its opening 256 KB, falling back to the file's birthtime. Top-level because a `file-history-snapshot` record carries a NESTED `snapshot.timestamp` that is not its own time; the record rather than birthtime first because the file is created when the first prompt is submitted, over a minute after the SessionStart record it already holds; and birthtime only when the filesystem recorded one, since a zero would read as "the session began at the epoch" and put the whole repository inside it. WHAT THE THREE CONDITIONS ACTUALLY BUY, written out rather than summarised, because summarising is how the two overstatements above happened: HEAD-only makes the prescribed amend reachable, unpushed keeps a tip that came from the remote out, and the date keeps a tip this session did not create out. THE ACCEPTED LOSS, recorded here and in the code so it is not read as an oversight. Missed detections: an invented trailer on a commit that is no longer HEAD, on one already pushed, or on one committed before the session started; and one more via cannot-tell, since no readable transcript means no session start and the check stands down rather than guess. ONE FALSE BLOCK ALSO REMAINS, and it is not zero: an operation that rewrites a committer date without rewriting the trailer - `pull --rebase`, `cherry-pick`, an amend of someone else's commit - stamps this session's clock onto a trailer sourced outside it, which reads as invented here. That is what the escape hatch is for, and it is the residual after three rounds of narrowing rather than a case nobody looked at. Checked BEFORE the code checks because it is the one finding that gets permanently worse if the turn ends: one amend now, a rewrite of shared history later. Escape hatch `enigma:allow-unsourced-trailer` in the commit message, and THE BLOCK MESSAGE SEPARATES THE ROUTES BY WHAT THEY CAN ACTUALLY DO, which the first wording blurred by listing all three as if they were equivalent: what the user told you and `git log --all --author` CLEAR the check, while `gh api users/<login>` cannot by construction - its answer arrives as a tool result, which `userTyped` ignores on purpose, and a freshly looked-up address is by definition not in `%ae`/`%ce` or `.mailmap` yet. Looking it up is the CORRECT behaviour, so the lookup and the marker are named in the same breath rather than leaving the marker as a trailing conditional; an agent that does precisely the right thing must not spend both of its two available blocks discovering that the right thing is not enough. ITS OWN BUDGET CHANNEL (`mayBlock(..., "source")`) for the same reason the conventions sweep has one, plus a sharper one: the detail leads with the commit sha, so an issue key hashed from it changed on every amend and handed the same unfixed finding a fresh `MAX_BLOCKS_PER_ISSUE` allowance each round while draining the shared session ceiling the completion-claim and stop-short gates depend on - about five amends silently stood the primary gate down. The gap therefore carries an explicit `key` (`VerifyGap.key`, preferred by `issueKey` over the detail) keyed on the lowercased ADDRESS, with the sha left in the message text where it is useful. COST: one extra `git log` per turn-end invocation and nothing else - literally one, since the `inGitRepo` probe that used to guard it was dropped as redundant (that same `log` call fails identically outside a repository and before the first commit, and its null is already the answer, which the fail-open test asserts). The file's cost model is why it stops there - a repository whose unpushed commits carry no trailer (nearly all of them, since git-policy forbids the AI ones) pays that and nothing else; the history walk, `.mailmap` and the transcript read all happen lazily, only once a trailer is actually found. That one subprocess is also what made `a run that was aborted or failed vouches for nothing` need an explicit 20s timeout - it drives the hook nine times, far more than a real turn does. TIER 2 is git-policy's "An Attribution Trailer Carries An Identity You Were Given" (a username is not an email; source it from the user, `git log --all --author` - `--all` there too, since the HEAD-only default has the same blind spot the check itself had - or `gh api users/<login>`; the GitHub no-reply address is `ID+LOGIN@users.noreply.github.com` only for accounts created after 18 July 2017 and `LOGIN@users.noreply.github.com` for older ones with email privacy, so its form depends on an id and a signup date the model cannot know - it is looked up, never assembled), and TIER 3 is one kernel line stating the general invariant, since it is not a git rule: a value you cannot source - an email, a version, an id, a URL, a price - is asked for or left out, never guessed, and fixture data is the one exception.
