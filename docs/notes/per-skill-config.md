# Per-skill config (config-in-skill standard)

- WHY it exists: a config value that only matters when ONE skill is active (e.g. `logo-color-policy` <-> `logo-sourcing-policy`, `minimal-code` <-> `anti-overengineering-policy`) must NOT live in the always-on memory file - that bloats context every session even when irrelevant, and it does not scale to many skills x configs. Instead the value renders INTO the skill's deployed `SKILL.md`, so it is in context only when the skill activates (progressive disclosure), with zero runtime latency (baked at deploy, no tool call to read config). This is the config counterpart of the memory-marker mechanism; the DISTINCTION is: skill-scoped config -> render into the skill; cross-cutting always-on behavior (`output-style`, `parallel-subagents`, `recall`, `gate`) -> stays in memory, because it must apply regardless of which skill loads (putting `output-style` in a skill would break it - it must shape EVERY reply).
- MECHANISM: `skill.json` declares `config: ["<enigmaConfigKey>", ...]` (camelCase `.enigma.json` keys). `SKILL.md` carries a delimited block `<!-- enigma:config:start -->...<!-- enigma:config:end -->`. Inside it, two renderings (both by `renderSkill(srcSkillMd, keys)` in skills.ts at DEPLOY time, `deploySkill(src, dest, meta)` = cpSync + render): (1) `{{<key>}}` placeholders bind to the current value; (2) `<!-- enigma:case:<key>=<value> -->...<!-- enigma:case:end -->` blocks keep ONLY the case whose value matches the current config and drop the rest (and all case markers). WHY case blocks: the deployed skill must describe ONLY the user's active option, never the others (the agent has no reason to know what the unselected options do) - so the per-option prose lives in cases, not a full table. Case blocks MUST live inside the enigma:config block (that whole block is what the hash strips); a case block outside it would make the rendered deployment hash differently and read as tampered. The SEAL/HASH is invariant to the value: `computeContentSha` (util.ts) STRIPS the `enigma:config` block from `SKILL.md` before hashing (via `SKILL_CONFIG_BLOCK`), so seal-on-template and status-on-rendered-deployment hash IDENTICALLY - a config choice never reads as "tampered", while any edit OUTSIDE the block still does. skills-remote verification and `enigma check` both use the same stripped hash, so they agree.
- RE-RENDER ON CHANGE: because the block is hash-excluded, `skillStatus` reports a config-changed skill as "identical", so `syncTarget` alone would skip it. Two things force the re-render: `skillConfigDrifted(sk, destDir)` (deployed `SKILL.md` != rendered) drives an in-place rewrite inside `syncTarget`'s identical branch, and `applySkillConfig(scope)` (the config-in-skill twin of `applyMemoryToggles`) re-renders every deployed config skill on a config write. A setting flags itself with `affectsSkills: true` (parallel to `affectsMemory`); all three settings surfaces honor it: `settings.ts` (`applySkillChange`), `dashboard-settings.ts` (restartNote), `tui/opentui.ts` (`skillScopes`). `enigmaChoice` gained an `affectsSkills` trailing param.
- ADDING ANOTHER skill-scoped config: declare the key in the skill's `skill.json` `config`, add the `enigma:config` block with `{{key}}` to its `SKILL.md`, set `affectsSkills: true` on the setting (drop any `affectsMemory`), and do NOT add a memory block. Test: `tests/skill-config.test.ts` pins the hash-exclusion invariant. The value default still lives in `config.ts` `CONFIG_DEFAULTS`.
- MIGRATION history: `logo-color-policy` and `minimal-code` were originally memory-marker blocks ({{logo-color-policy}}/{{minimal-level}}); they were moved to their skills and their memory blocks deleted. If you see a stale `{{...-level}}` reference in an OLD deployed memory, a sync re-renders it out.
