# Local OpenAI-compatible API for the coding agents (`src/api-server.ts` + `src/api-agents.ts` + `enigma api`)

- WHAT: a native, dependency-free (`node:http` + `node:child_process`) local HTTP server that exposes the LOCAL coding agents over an OpenAI-compatible API - `/v1/chat/completions` (stream + non-stream), `/v1/messages` (Anthropic shape, stream + non-stream), `/v1/models`, `/v1/sessions` (list) + `DELETE /v1/sessions/:id`, `/health`, `/`. Any OpenAI client library points at `http://127.0.0.1:8000/v1`. Study clone: `references/repos/claude-code-openai-wrapper` (Python/FastAPI over the Python `claude-agent-sdk`, MIT, Claude-only) - DELIBERATELY NOT ported 1:1: enigma is zero-runtime-deps + a Bun binary, so no Python/FastAPI/SDK. Instead every request SPAWNS a local agent CLI in headless mode with the resolved account's config-dir env injected, and translates its output into OpenAI/Anthropic responses. KEY INSIGHT: Claude Code's stream-json output is the SAME message stream the Python SDK yields (the SDK is a thin CLI wrapper), so a native TS parser gets ALL Claude capabilities (tools, skills, MCP, sessions, existing auth) with nothing to install. It is NOT a network proxy to Anthropic (unlike `proxy.ts`) - it drives the real local agent.
- MULTI-AGENT (the "podría ser opencode o cualquier otra a la vez" requirement): ONE server backs SEVERAL agents concurrently, routed PER REQUEST by the OpenAI `model` field. `src/api-agents.ts` owns the per-agent ADAPTERS (each agent has a different headless invocation + output format, so an adapter isolates "how to run it" + "how to read it" behind `AgentAdapter{tool, models, mode:"stream-json"|"plain", build(prompt,opts)->{args,stdin}, parseLine?}`). Adapters: (1) CLAUDE (verified) - `-p --output-format stream-json --verbose`, prompt via stdin, `--model`(claude ids/aliases only, foreign dropped), `--append-system-prompt`, `--resume`, `--permission-mode` (default; `bypassPermissions` only when `enable_tools` AND global `permissionBypass`); `parseClaudeLine` (system/init, assistant text blocks, result+usage). (2) CODEX (documented `codex exec --json` ThreadEvent schema, NOT verified live - not installed on the dev machine) - `exec --json [-m model] <prompt-positional>`, system folded into the prompt (no verified exec system flag); `parseCodexLine` (thread.started->init, item.completed+item.type=="agent_message"->text, turn.completed->usage, turn.failed/error->isError). (3) OPENCODE (documented flags, JSON event schema NOT publicly documented so mode="plain" = stdout IS the answer, the honest reliable surface) - `run [-m provider/model] <prompt>`, system folded in, no parseLine, usage estimated. `resolveAdapter(model, defaultTool)` routing: a model naming a tool (`codex`/`opencode`) or with a `tool:`/`tool/` prefix (`codex/gpt-5`, `opencode/anthropic/claude`) -> that adapter; a `claude*`/alias -> claude; else the default tool (`--tool`, default claude). `availableAdapters()` filters by `agentAvailable(tool)` (binary resolvable via env/toolPaths/resolveBin) so `/v1/models` + `/health` list ONLY installed agents (honest). `stripToolPrefix` strips the routing prefix before passing the real model to the CLI.
- SHARED HTTP CORE (`api-server.ts`): `messagesToPrompt` (single user turn verbatim; multi-turn -> `Human:`/`Assistant:` transcript; last system message wins), `contentToText`, `streamChunk`. `runAgent(adapter,...)` is the generic spawn+drive (stream-json -> line parse; plain -> collect+trim stdout; Windows shell:true + local `quoteWinArg` when binary not `.exe`; binary resolved like `launchTool`: `ENIGMA_<TOOL>_BIN` > `toolPaths` > `resolveBin` > bare; reuses `getTool`/`resolveConfigDir`/`resolveLaunchAccount`). Sessions: in-process `Map`, request `session_id` -> `--resume` (claude), captured+tracked+listed. Streaming is MESSAGE-level (stream-json is message-not-token granular; plain agents stream raw stdout chunks) - honest, not fake token streaming. A not-installed backend spawn-errors -> graceful 502, never crashes the server (verified with `model:"codex"`).
- SECURITY: 127.0.0.1-bound ALWAYS. Optional bearer key from `--api-key`/`ENIGMA_API_KEY` (NOT persisted - a secret in plaintext config is worse); `/v1/models`, `/health`, `/` open, every other `/v1` route needs the token. 4MB body cap.
- WIRING: `enigma api` in COMMANDS + `runApiCli` (dynamic-imports api-server + api-agents), dispatched in `run()`; flags `--port`/`--api-key` in parseArgs/CliOptions (+ `--tool` = default backend). Foreground, Ctrl+C (no daemon - YAGNI). Config `apiPort:number` (default 8000) + settings.ts numeric branch (`enigma config api-port`, CLI-only) + `dashboard-config-io.ts` NUMERIC_KEYS. Dashboard: "Local API server" row shows the port + a brand-logo per backend (`agentSvg`) from `systemsStatus().api{port,agents}` (dashboard-status.ts imports `availableAdapters`); demo-mock + screenshot STATUS gained `api:{port,agents}`; dashboard `0.1.73`. Docs: `concepts/api.mdx` (order 35, multi-agent section) + `reference/commands.mdx`/`configuration.mdx` + landing card + README card/commands line.
- TESTS: `tests/api-server.test.ts` (bun, 12 tests; PURE helpers + routing + claude/codex parsers only - spawn/HTTP verified manually, not CI) in ci.yml. VERIFIED end-to-end on the dev machine against the real `claude`: health/models (lists only installed = claude), a real `/v1/chat/completions` via model routing (content+usage+session id), OpenAI SSE streaming, `/v1/messages`, `/v1/sessions`, 401 auth, and `model:"codex"` -> graceful 502 (not installed). Codex/OpenCode adapters are documentation-based (unverified live) - marked as such in api-agents.ts; verify + tweak flags on a machine that has them.
- DEFAULT MODEL + VISION/MULTIMODAL (added after the first release). DEFAULT MODEL: `DEFAULT_MODEL = "claude-opus-4-8"` (api-agents.ts); the claude adapter always passes `--model` (a named Claude model wins, else opus - so a bare `claude`/foreign id -> opus), and both handlers + `completeOnce` default `body.model` to `DEFAULT_MODEL`. IMAGES: `ImageBlock` (Anthropic content-block shape, base64 or url source) on `CompletionOptions`/`CompleteParams`; `extractImages(messages)` (api-server.ts) reads BOTH OpenAI `image_url` parts (a `data:` URL -> base64 source, an `http(s)` URL -> url source) AND native Anthropic `image` blocks (pass-through), so either request format carries vision. The claude adapter, when `opts.images.length`, switches to `--input-format stream-json` and writes ONE user message `{"type":"user","message":{"role":"user","content":[{type:text},...imageBlocks]}}\n` to stdin (the reliable headless vision path - VERIFIED: `claude -p --input-format stream-json --output-format stream-json --verbose` accepts image content blocks and the model reads them; a 1x1 image errors "could not be processed" but a real 32x32 PNG is described correctly). Other agents ignore images (text only - honest, documented). VERIFIED e2e: OpenAI `image_url` data URL -> "Blue", Anthropic native `image` block -> "Green", playground inproc -> "Yellow"; default model (no model field) -> response `model: claude-opus-4-8`. Dashboard playground gained an image `<input type=file>` (read as a data URL, sent as `imageDataUrl`; `userContent`/`buildRequestBody` fold it into content parts per format; `buildCurl` truncates the base64 to `base64,<base64 image data omitted>` for readability) and the "Enable agent tools" control is now the `data-kind="bool"` SWITCH (not a checkbox) DEFAULT ON. Tests: DEFAULT_MODEL fallback, images-> stream-json input, extractImages (both formats), buildRequestBody image parts, buildCurl truncation.
- TO ADD AN AGENT: append an `AgentAdapter` to `ADAPTERS` in api-agents.ts (models list + build + mode + parseLine for stream-json, or plain). The HTTP layer, routing, /v1/models and spawn are all generic. To add an endpoint: extend `startApiServer`'s handler switch; a request param: map it in the adapter `build` + `CompletionOptions`.
- ACCOUNT/PROFILE/PACK CONTEXT (the "usar la API con perfiles, accounts, packs como Helio" ask): every request can run under a specific enigma account, a profile's mapping, or a pack's isolated context. `runAgent` resolves the config dir via `resolveContextDir(tool, opts)` (api-server.ts): `pack` -> `ensurePackContext(id, tool, account?)` (NEW export in packs.ts = launchPack's prep WITHOUT the spawn: resolvePackAccount + ensurePackInstalled + enablePack + deployPack + seedCredentials + reconcilePackSession -> returns the context dir; the pack path is dynamic-imported so the common case never loads packs.ts); else `account` (explicit) -> `resolveConfigDir`; else `profile` -> `listProfiles()` mapping for the tool -> account; else `resolveLaunchAccount` (the previous default = active account). `CompletionOptions`/`CompleteParams` gained `account`/`profile`/`pack`. Server DEFAULTS via `enigma api --account`/`--profile`/`--pack` (CliOptions `apiAccount`/`apiProfile`/`apiPack` -> `ApiServerOptions` -> `ServerDefaults`); PER-REQUEST override via `account`/`profile`/`pack` fields in the JSON body (`contextOf(body, defaults)` merges, request wins - ignored by standard OpenAI clients so they are safe extension fields). `/health` + `/` report `defaultContext`. So ONE server serves several accounts/packs at once. PERSISTED DEFAULT (settable from the DASHBOARD too, the "por defecto desde el dashboard" ask): config `apiAccount`/`apiProfile`/`apiPack` (strings, default ""); `runApiCli` = flag `??` config, so `enigma api` with no flag uses the saved default. CLI: `enigma config api-account|api-profile|api-pack <name|none>` (string branch `API_CONTEXT` in settings.ts; `none`/empty clears - NOT `-`, which cli.ts parseArgs rejects as an unknown option). Dashboard: `playgroundInfo().defaults` returns them; `setApiDefaults({account,profile,pack})` (dashboard-playground.ts) persists globally; the `/api/playground` POST branches on `body.op === "set-defaults"` vs a run. Playground UI pre-selects the context selectors to the saved default on load and has a "Save context as enigma api default" button + a "Current default: ..." note. Round-trips via config export/import (STRING_KEYS in dashboard-config-io.ts). VERIFIED e2e: server `--account default` (health defaultContext + real completion under it), per-request `account:"ByteHide"` override, unknown account/pack -> graceful 502 with a clear message; CLI `config api-account default` read by a flag-less `enigma api`; bridge setApiDefaults round-trip; headless UI pre-selection + Save updating the note. The pack happy-path reuses the already-tested pack machinery (deployPack/seedCredentials/reconcilePackSession) + `launchInDir`-equivalent spawn, so it is structurally sound; only the unknown-pack error was exercised live (Helio not fetched to avoid a live npm install). Docs: `concepts/api.mdx` "Accounts, profiles and packs" section.
- DASHBOARD PLAYGROUND (`src/dashboard-playground.ts` + `#/playground`, dashboard `0.1.74`): a browser tester for the API. `completeOnce(params)` (exported from api-server.ts) runs ONE completion IN-PROCESS via the adapters (resolveAdapter by model, messagesToPrompt, runAgent) - so the playground drives the real local agent with NO `enigma api` process and NO CORS. The bridge (dynamic-imported like the other `dashboard-*` bridges) has PURE helpers (tested in `tests/api-playground.test.ts`, no spawn): `formatPath` (openai->/v1/chat/completions, anthropic->/v1/messages), `buildRequestBody` (per-format client body), `shapeResult` (in-process result -> OpenAI/Anthropic envelope), `buildCurl` (reproducible curl, adds auth only when keyed), `isLoopbackTarget` (SSRF guard). `runPlayground(req)` has TWO modes: "inproc" (completeOnce + shapeResult) and "http" (forward to a RUNNING server via `forwardHttp`, restricted to loopback hosts - the auth key is passed through, never logged/stored). Route `/api/playground` in dashboard.ts (GET info = installed agents+models+apiPort; POST run), origin-guarded like the other write surfaces. UI: a "Playground" tab (format/backend/mode selects, base URL + auth key shown only in http mode, system+message, enable-tools, Send; renders response text + meta + raw JSON + curl with a copy button); demo-mock stubs `/api/playground` (client-side fetch shim, so a server-side curl to it returns `{}` - only the browser shim answers). VERIFIED: bridge e2e (inproc drives real claude, http forwards to a real `enigma api`, SSRF guard rejects non-loopback) + headless Playwright (tab renders, model dropdown populated, Send shows response/meta/curl, http mode reveals base/auth fields, no JS errors). The enhanced `<select>` (progressive-enhancement dropdown) HIDES the native select, so a Playwright `selectOption` fails - set `.value` + dispatch `change` instead. CONTEXT SELECTORS (dashboard `0.1.75`): the playground also has Account / Profile / Pack selects (`playgroundInfo` returns `accounts` per tool + `profiles` + `packs{id,label,installed}`; `runPlayground`/`buildRequestBody` fold them into the request via `applyContext`, so inproc passes them to `completeOnce` and http adds them to the forwarded body). So the playground can drive any account/profile/pack (e.g. Helio) exactly like the CLI.
