# Local OpenAI-compatible API for the coding agents (`src/api-server.ts` + `src/api-agents.ts` + `enigma api`)

- WHAT: a native, dependency-free (`node:http` + `node:child_process`) local HTTP server that exposes the LOCAL coding agents over an OpenAI-compatible API - `/v1/chat/completions` (stream + non-stream), `/v1/messages` (Anthropic shape, stream + non-stream), `/v1/models`, `/v1/sessions` (list) + `DELETE /v1/sessions/:id`, `/health`, `/`. Any OpenAI client library points at `http://127.0.0.1:8000/v1`. Study clone: `references/repos/claude-code-openai-wrapper` (Python/FastAPI over the Python `claude-agent-sdk`, MIT, Claude-only) - DELIBERATELY NOT ported 1:1: enigma is zero-runtime-deps + a Bun binary, so no Python/FastAPI/SDK. Instead every request SPAWNS a local agent CLI in headless mode with the resolved account's config-dir env injected, and translates its output into OpenAI/Anthropic responses. KEY INSIGHT: Claude Code's stream-json output is the SAME message stream the Python SDK yields (the SDK is a thin CLI wrapper), so a native TS parser gets ALL Claude capabilities (tools, skills, MCP, sessions, existing auth) with nothing to install. It is NOT a network proxy to Anthropic (unlike `proxy.ts`) - it drives the real local agent.
- MULTI-AGENT (the "podría ser opencode o cualquier otra a la vez" requirement): ONE server backs SEVERAL agents concurrently, routed PER REQUEST by the OpenAI `model` field. `src/api-agents.ts` owns the per-agent ADAPTERS (each agent has a different headless invocation + output format, so an adapter isolates "how to run it" + "how to read it" behind `AgentAdapter{tool, models, mode:"stream-json"|"plain", build(prompt,opts)->{args,stdin}, parseLine?}`). Adapters: (1) CLAUDE (verified) - `-p --output-format stream-json --verbose`, prompt via stdin, `--model`(claude ids/aliases only, foreign dropped), `--append-system-prompt`, `--resume`, `--permission-mode` (default; `bypassPermissions` only when `enable_tools` AND global `permissionBypass`), `--strict-mcp-config` ONLY when tools are off (the API default); `parseClaudeLine` (system/init; a non-partial `assistant` message -> `text_final`; a `stream_event` `content_block_delta` carrying a `text_delta` -> an incremental `text` (a `thinking_delta` and every other delta type are dropped); result+usage). A line tagged with a non-empty `parent_tool_use_id` is a NESTED sub-agent turn, not the answer, and is skipped for BOTH shapes so the streamed and non-streamed bodies carry the same content. `stream:true` adds `--include-partial-messages` so the deltas exist at all. (2) CODEX (documented `codex exec --json` ThreadEvent schema, NOT verified live - not installed on the dev machine) - `exec --json [-m model] <prompt-positional>`, system folded into the prompt (no verified exec system flag); `parseCodexLine` (thread.started->init, item.completed+item.type=="agent_message"->text, turn.completed->usage, turn.failed/error->isError). (3) OPENCODE (documented flags, JSON event schema NOT publicly documented so mode="plain" = stdout IS the answer, the honest reliable surface) - `run [-m provider/model] <prompt>`, system folded in, no parseLine, usage estimated. `resolveAdapter(model, defaultTool)` routing: a model naming a tool (`codex`/`opencode`) or with a `tool:`/`tool/` prefix (`codex/gpt-5`, `opencode/anthropic/claude`) -> that adapter; a `claude*`/alias -> claude; else the default tool (`--tool`, default claude). `availableAdapters()` filters by `agentAvailable(tool)` (binary resolvable via env/toolPaths/resolveBin) so `/v1/models` + `/health` list ONLY installed agents (honest). `stripToolPrefix` strips the routing prefix before passing the real model to the CLI.
- SHARED HTTP CORE (`api-server.ts`): `messagesToPrompt` (single user turn verbatim; multi-turn -> `Human:`/`Assistant:` transcript; last system message wins), `contentToText`, `streamChunk`. Message text is UNTRUSTED (an HTTP caller's own words), so before the transcript is assembled `neutralizeTurnLabels` swaps the colon after a line-leading `Human:`/`Assistant:` inside message text for a middle dot - readable but no longer parsed as a turn, closing off a caller forging an assistant reply or smuggling instructions as another turn. The single-turn path is untouched (no transcript, nothing to forge). `runAgent(adapter,...)` is the generic spawn+drive (stream-json -> line parse; plain -> collect+trim stdout; Windows shell:true + local `quoteWinArg` when binary not `.exe`; binary resolved like `launchTool`: `ENIGMA_<TOOL>_BIN` > `toolPaths` > `resolveBin` > bare; reuses `getTool`/`resolveConfigDir`/`resolveLaunchAccount`). Sessions: in-process `Map`, request `session_id` -> `--resume` (claude), captured+tracked+listed. Streaming is TOKEN-level on Claude (`stream:true` -> `--include-partial-messages` -> one SSE chunk per `text_delta`) and MESSAGE-level everywhere else (Codex is message-granular; plain agents stream raw stdout chunks) - always real output, never a fake token split of an already-complete answer. NO DOUBLE COUNT, NO SILENT EMPTY BODY: `runAgent` tracks what the deltas delivered for the current turn and the closing `text_final` contributes only the REMAINDER, so a turn that streamed contributes once and a turn that produced no partials at all (a CLI that accepts the flag without emitting them, or a locally synthesized assistant notice) is still delivered in full; the `result` fallback likewise forwards its text through `onText`, not just into the summary. BACKPRESSURE: one frame per token means a slow SSE consumer would otherwise buffer the whole answer in the socket, so `writeSse` returns a `drain` promise when `res.write` reports the buffer full and `runAgent` pauses the agent's stdout until it resolves. A not-installed backend spawn-errors -> graceful 502, never crashes the server (verified with `model:"codex"`).
- SECURITY: 127.0.0.1-bound ALWAYS. Optional bearer key from `--api-key`/`ENIGMA_API_KEY` (NOT persisted - a secret in plaintext config is worse); `/v1/models`, `/health`, `/` open, every other `/v1` route needs the token. 4MB body cap.
- WIRING: `enigma api` in COMMANDS + `runApiCli` (dynamic-imports api-server + api-agents), dispatched in `run()`; flags `--port`/`--api-key` in parseArgs/CliOptions (+ `--tool` = default backend). Foreground, Ctrl+C (no daemon - YAGNI). Config `apiPort:number` (default 8000) + settings.ts numeric branch (`enigma config api-port`, CLI-only) + `dashboard-config-io.ts` NUMERIC_KEYS. Dashboard: "Local API server" row shows the port + a brand-logo per backend (`agentSvg`) from `systemsStatus().api{port,agents}` (dashboard-status.ts imports `availableAdapters`); demo-mock + screenshot STATUS gained `api:{port,agents}`; dashboard `0.1.73`. - DEFAULT MODEL + VISION/MULTIMODAL (added after the first release). - MCP IS OFF WHEN TOOLS ARE OFF (the claude adapter, `--strict-mcp-config`). A headless boot CONNECTS to every MCP server the user has configured and injects their tool schemas into the prompt - measured on the dev machine at ~118K prompt tokens (~170K -> ~51K) and ~2s of boot latency PER REQUEST. An API completion runs with tools off by default, so none of those tools is reachable and all of that is waste. `--strict-mcp-config` means "only use MCP servers from `--mcp-config`", and the adapter never passes a `--mcp-config`, so the effective set is EMPTY. Gated on `!opts.enableTools` because `enable_tools:true` means the caller wants the tools, MCP ones included. TWO CONSEQUENCES to keep in mind: (1) tools-off is a PERMISSION posture (`--permission-mode default`), not a tool allowlist - no `--allowedTools`/`--disallowedTools` is ever passed - so a user whose Claude settings pre-approve an MCP tool via a `permissions.allow` entry (`mcp__server__tool`) could previously reach it on a tools-off request and now cannot; that was incidental, and `enable_tools:true` is the supported way to get an MCP tool. (2) the prompt prefix DIFFERS between tools-on and tools-off, so a session that alternates invalidates the cached prefix in both directions - accepted, the tools-off saving dominates. NO EQUIVALENT ON THE OTHER BACKENDS: Kimi reads its own `.kimi-code/mcp.json` plus Claude's project `.mcp.json` (see `kimi.md`) and its CLI has no way to skip them - verified against kimi 0.35.0, where both `--strict-mcp-config` and `--no-mcp` are rejected as unknown options - so a kimi-backed completion still pays this cost. Do not add a flag there by analogy; re-check `kimi --help` first.
- TO ADD AN AGENT: append an `AgentAdapter` to `ADAPTERS` in api-agents.ts (models list + build + mode + parseLine for stream-json, or plain). The HTTP layer, routing, /v1/models and spawn are all generic. To add an endpoint: extend `startApiServer`'s handler switch; a request param: map it in the adapter `build` + `CompletionOptions`.

- WARM SESSIONS (`src/session-runtime.ts`, the "session-based agentic API" - OpenAI's Responses `previous_response_id`/`conversation` and AWS Bedrock AgentCore's per-session compute). The default path spawns a fresh Claude Code per request (isolated, but a cold boot every time). When a request carries a `session_id` (which MUST be a UUID - `--session-id`/`--resume` reject anything else, so a non-UUID is a 400 before any streaming head), `drive()` (api-server.ts) routes to the WARM runtime instead: ONE long-lived `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-mode <default|bypassPermissions> [--strict-mcp-config] --session-id <id>` process is kept per session and each turn is fed to its stdin as one `{"type":"user",...}` message (images included, the same content shape the stateless adapter builds). The permission posture and the MCP skip are ONE `enableTools` flag on the spec, evaluated exactly as the stateless adapter's `build()` does, so the two paths cannot drift: a tools-on session launched WITHOUT `--permission-mode` stalls forever, because this stdin is the turn channel and nothing there can answer a permission prompt, so the turn never emits its `result` line. Only the FIRST turn pays the boot; the rest reuse the warm process (measured turn-2 ~30-50% faster) AND the client sends ONLY the newest user message (`lastUserText`) - the process holds the thread, so history is never re-sent. Claude Code ONLY (the one agent with a persistent stream-json interface); another agent given a `session_id` falls back to the stateless `--resume` path. ISOLATION is preserved because reuse is scoped to an explicit id: one process = one conversation, never two; turns of a session are SERIALIZED (a second concurrent turn on the same id -> `RequestError(409)`, answered by an `isSessionBusy` check BEFORE the streaming head so a streamed request gets a real 409 instead of the refusal buried as text in a 200 stream; a timed-out turn is 504), different sessions run in parallel. LIFECYCLE: a session idle past `idleTtlMs` (default 15min, AgentCore's default) is evicted, and the LRU past `maxSessions` (default 8) - the process is killed to free RAM but the state SURVIVES on disk (Claude Code persists every transcript), so a later turn RESPAWNS with `--resume <id>` and continues where it left off. That resume decision CANNOT come from the live map (eviction is exactly what removes the entry), so a bounded map of every id this server has spawned outlives it, and it doubles as the isolation binding: an id is tied to the `contextKey` (the resolved config dir) that first ran it, and a turn naming a different account/profile/pack is refused with `SessionError("context-mismatch")` rather than resuming another account's transcript under the wrong login. Idle sweeping runs on an UNREF'D timer, not only when a session is created: a lone idle session has no later spawn to trigger eviction and would otherwise hold its process until shutdown. A turn that produces no `result` within `turnTimeoutMs` (default 10min) is ended, killed and reset, so a wedged process (a permission prompt, a hung tool call, a dead network) cannot pin the session `busy` forever and 409 every later turn until the server restarts. A dead child's `close` deletes its map entry ONLY when the map still holds that same child, or an evicted session's late exit would delete the live successor and orphan its process. A brand-new id spawns with `--session-id <id>` (the client's UUID IS the Claude session id); an evicted/crashed one resumes by that same id. `closeAllSessions()` runs on server close so no child outlives it. The response ECHOES `session_id` (plus the legacy `system_fingerprint: session_<id>`) so the client reuses it. DETECTABILITY is unchanged: a warm session is a normal multi-turn Claude Code conversation as far as the backend is concerned. VERIFIED e2e via the real HTTP API: turn-2 warm + remembered context, stateless coexists (no `session_id` -> the fresh path), bad-uuid -> 400. `idleTtlMs`/`maxSessions`/`turnTimeoutMs` are `DEFAULT_SESSION_CONFIG` (hardcoded MVP; promote to an `.enigma.json` setting when tuning is wanted). This is "Option A" (`session_id` on `chat/completions`); a full OpenAI Responses API (`/v1/responses` + `previous_response_id`) would reuse the SAME runtime and is a future layer. Tests: `lastUserText` (newest user turn only), session-runtime empty-state invariants (`tests/api-server.test.ts`); the LIFECYCLE is covered in CI by `tests/session-runtime.test.ts`, which points `spec.binary` at a stub that records its argv and answers in stream-json (launch flags, `--resume` after the process is lost, serialization/409, turn timeout plus recovery, idle sweep with no new spawn, context binding, images) - no `claude` spawned; only the model's own behavior still needs the real CLI, which is what the manual e2e covers.
- DASHBOARD PLAYGROUND (`src/dashboard-playground.ts` + `#/playground`, dashboard `0.1.74`): a browser tester for the API. `completeOnce(params)` (exported from api-server.ts) runs ONE completion IN-PROCESS via the adapters (resolveAdapter by model, messagesToPrompt, runAgent) - so the playground drives the real local agent with NO `enigma api` process and NO CORS.
