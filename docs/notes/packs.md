# Isolated agents, formerly "packs" (`src/packs.ts` + `enigma agent`/`enigma <agent>`; `enigma pack` = deprecated alias)

- WHAT/WHY: a "pack" is an optional harness bundle (skills + commands + sub-agents + MCP) for a focused domain, installed ON DEMAND from a marketplace and deployed ONLY into a DEDICATED, isolated agent context - NEVER into the user's normal agent. First pack = HELIO (TPEOficial/helio, a Python bug-bounty harness: 13 skills, ~20 commands, 10 sub-agents, 2 MCP). Motivation (user): keep cyber skills/tools out of the everyday Claude so they don't overload context (progressive disclosure keeps every skill's name+description always-loaded; 13 security skills would mis-trigger on normal coding) or collide with policy skills. Packs are a THIRD skill kind alongside policy skills (enigma's own, global, sealed) and autoskills (community, project-local) - distinct from both.
- DELIVERY = asset-only npm package per pack (`@enigmax/helio`, `packages/helio`), the @enigmax/dashboard model. Helio is VENDORED into `packages/helio/assets` by `scripts/sync-helio.mjs` (`npm run sync:helio` - shallow-clone a PINNED commit from `.source.json`, denylist `.git/tests/docs/install.*/.claude`, replace the whole tree to propagate deletions, re-pin; Node builtins + git CLI, MAINTAINER tool, assets are COMMITTED like dashboard's). Decision was "republish as npm" (provenance) NOT "fetch the helio repo at runtime". `publish.yml` has a version-guarded `@enigmax/helio` step (twin of dashboard's). The pack package applies Apache-2.0 + attributes TPEOficial (helio itself has no LICENSE - add one upstream).
- ISOLATION = the accounts.ts config-dir-injection mechanism, reused. `enigma helio` -> `launchPack` (packs.ts) -> fetch bundle if absent (on-demand npm into `~/.enigma/packs/helio/pkg`, `ENIGMA_PACKS_DIR` overrides) -> `deployPack` -> seed credentials -> `launchInDir(tool, contextDir)`. `launchInDir` (NEW export in accounts.ts) spawns the tool with its config-dir env pointed at `~/.enigma/packs/helio/context/<tool>` (which holds ONLY helio's content), bypassing account resolution. Refactor: the measuring-proxy block was extracted to `maybeStartProxy(toolName, env, cfg)` and shared by `launchTool` + `launchInDir` (no dup). Default tool = claude (DEFAULT_TOOL); `enigma helio [tool]` accepts a tool positional.
- DEPLOY (`deployPack`, version-gated via a `.enigma-pack-version` marker so re-launch is a cheap no-op unless the pack version changed): copies `assets/skills/*` -> `accountTarget(ctx).skills`, the tool's command set (`commands/claude-code` for claude, `commands/<tool>` else, flat `commands/` fallback) -> `accountTarget(ctx).commands`, `assets/agents/*` -> `<ctx>/agents` (Claude subagents, claude-only), and writes the harness memory file (`assets/AGENTS.md` else root `SKILL.md`) as `<ctx>/CLAUDE.md` (claude) / `AGENTS.md` (else). Reuses `getTool(tool).accountTarget(dir)` for tool-agnostic dest paths. GOTCHA: `deployPack` deploys ONLY skills/commands/agents/memory - NOT `assets/rules/*`, and the launched agent's CWD is the user's target repo, so any `rules/foo.md` relative reference (helio's AGENTS.md/commands point at `rules/hunting.md`, `rules/reporting.md`, `rules/source-audit.md`) is DANGLING at runtime. Behavior that must actually reach the agent has to be inlined into `assets/AGENTS.md` (the always-on `<ctx>/CLAUDE.md`); the `rules/*.md` files are human/dev docs + standalone-helio only. (This is why the `docs/vulnerabilities/` white-box ledger workflow is inlined in AGENTS.md, with the long-form copy in source-audit.md.)
- CREDENTIALS SEEDED (user decision "seed creds, frictionless"): `seedCredentials(id, tool, account)` copies THAT account's auth file(s) into the context so the isolated agent shares the login with no re-auth - claude `.credentials.json`, codex `auth.json`, opencode `xdg-data/opencode/auth.json` (CRED_FILES map). Best-effort, claude-first; never copies project history, only the well-known auth file.
- ACCOUNT/PROFILE PER PACK (user follow-up "packs must work with any profile/account, settable default"): a pack seeds from a RESOLVED account, not always the active one. `resolvePackAccount(id, tool, explicit?)` = explicit (validated, throws on a typo so it never seeds the wrong login) > the pack's pinned default `getPackAccount` > `resolveLaunchAccount(tool)` (active profile mapping > tool-active). Per-pack default in `EnigmaConfig.packAccounts: Record<"<packId>:<tool>", account>` via `setPackAccount` (config.ts, merge-write like setToolPath; null clears); `setPackDefaultAccount(id, tool, account|null)` validates the account exists. `launchPack(id, tool, passthrough, account?)` resolves up-front and prints which account it seeds with. Surfaces: CLI `enigma <pack> [account] [--tool t]` (positional = account now, NOT tool) + `enigma pack use <id> <account|->` (pin/clear) + `run <id> [account]`; PackView gained `tool`/`defaultAccount`/`resolvedAccount`/`accounts[]`. Dashboard: per-pack account `<select>` posting `set-account` (value "" clears); `applyPackAction(id, action, value?)`, body `{id,action,value?}`. A NEW account uses the normal flow (`enigma account add` then pin/launch). Tests: resolution/default/clear + launchPack rejecting an unknown explicit account (returns 1 pre-spawn) in packs.test.ts; a set-account case in dashboard.test.ts.
- SEEDING A CLAUDE LOGIN INTO AN ISOLATED CONFIG-DIR IS THREE LAYERS, NOT ONE (hard-won; this caused a long debugging saga). A separate `CLAUDE_CONFIG_DIR` (the pack context) is treated by Claude Code as a SEPARATE INSTALL, so copying just the token is NOT enough. `seedCredentials(id, tool, account)` must get all three right: (1) TOKEN - copy `.credentials.json` from the account, BUT (a) never PLANT a non-usable/blanked token (when the account's real token lives in the OS keychain the file is blanked; an empty file BLOCKS the agent's own resolution - copy only when `hasUsableToken(from)`), and (b) never CLOBBER the context's own token when it is the SAME account's (a fresh in-place OAuth rotation; re-copying the account's older token breaks the next refresh). (2) IDENTITY/STATE - the context's `.claude.json` must mirror the account's: a per-context `.enigma-pack-account` MARKER distinguishes a same-account rotation (keep) from an account SWITCH (re-seed token + state); on a switch/first-seed, `syncContextAccountState` copies the account's `.claude.json` (minus `projects`, keeping the pack's `mcpServers`). (3) ONBOARDING FLAG - the killer bug: without `hasCompletedOnboarding` in the context `.claude.json`, Claude Code runs its ONBOARDING WIZARD (which asks to log in) and IGNORES a perfectly valid token. `syncContextAccountState` brings `hasCompletedOnboarding` (+ the rest of the account state), and runs on EVERY launch when the context already holds the account's token (not only when copied), so a context seeded by an older enigma gets the missing flag on the next run. NET RULE: an access token past `expiresAt` but WITH a refresh token is "ok" (the session refreshes - sessions last months, not the access-token's hours); `accountTokenState` returns ok/expired(no-refresh)/empty/absent. DEBUG NEXT TIME: compare the account's `.claude.json` keys vs the context's (`hasCompletedOnboarding`, `userID`, `machineID`, `oauthAccount`) - a missing onboarding/identity field, not the token, is the usual "login despite valid token" cause. enigma writes ONLY the pack context, NEVER the account dir.
- PERMISSION BYPASS ON BY DEFAULT FOR THE PACK (user request): `ensurePackBypass(dir, tool)` writes `permissions.defaultMode: "bypassPermissions"` into `<ctx>/settings.json` (claude only; the format `enableClaudeBypass` uses in claude.ts). Called at the TOP of `deployPack` BEFORE the version-gate early-return so existing contexts get it too on the next launch (idempotent, merges into any settings). Honors the global `config.permissionBypass` opt-out. A security harness issues many tool calls, so per-action prompts would be unworkable.
- MCP (`setupPackMcp`, gated behind `enigma pack setup` NOT the default launch): registers the pack's SELF-CONTAINED Python MCP servers into `<ctx>/.claude.json` mcpServers (claude-only). Helio's hackerone server (public, no key) is registered; its Burp client is config-only (a separate Java server needing Burp + a jar + API key) so it is NOT in `PackDef.mcp` - `existsSync(script)` guards anyway. Gated because MCP servers need Python + the pack's tooling, which would break the fast default launch if missing.
- CONFIG: `EnigmaConfig.packs: string[]` (default `[]`) = the durable record of added packs (the npm bundle presence under `~/.enigma/packs` is the fetch state). `enablePack`/`disablePack` toggle it; disable also `rm -rf`s the managed pack dir + context. NO `enigma config packs` toggle (managed via `enigma pack`/the dashboard).
- SURFACES: CLI `enigma pack <list|install|remove|update|setup|run> <id>` (`runPackCli`) + shortcut `enigma <pack>` (e.g. `enigma helio`) dispatched BEFORE the `pack`/`account` branch in `run()`; COMMANDS includes `pack`,`packs` + `...PACKS.map(p=>p.id)`; printHelp documents both. Dashboard: a "Packs" tab (`#/packs`) + origin-guarded `GET/POST /api/packs` (bridge `dashboard-packs.ts`, dynamic-imported like dashboard-skills); the browser CANNOT spawn an agent, so the "launch" action returns the `enigma <id>` COMMAND (copied to clipboard) - mirrors accounts' "Log in..." pattern. demo-mock stubs `/api/packs`; dashboard `0.1.65`. Web: `apps/web/src/content/docs/concepts/packs.mdx` (order 33) + a `reference/commands.mdx` `pack` entry + a landing "Marketplace packs" feature card.
- TESTS: `tests/packs.test.ts` (bun; temp HOME + `ENIGMA_CONFIG_HOME` + `ENIGMA_PACKS_DIR` + `ENIGMA_HELIO_ASSETS`=vendored assets, all set BEFORE import; verifies deploy lands ONLY in the context dir and the normal `~/.claude` is untouched, version-gated no-op, enable/disable toggles config + removes the tree, MCP setup writes into the context only - spawn-free/network-free) + a `/api/packs` case in `tests/dashboard.test.ts`. Both wired into ci.yml.
- TO ADD A PACK: append one entry to `PACKS` in packs.ts (id/label/pkg/description/tags/homepage/optional mcp), create `packages/<id>` (asset-only, mirror packages/helio) + a sync script if vendored, add a `publish.yml` step, add demo-mock data. The rest (lifecycle, isolation, dashboard tab, CLI) is generic.
- ORION (second pack, `packages/orion`, authored here, not vendored): hunts what looks finished but is not - broken flows, slow loads, unbounded queries, scaling limits, searches that never say "no results" - with evidence for every finding. Skills `bug-hunt`, `perf-audit`, `scale-audit`, `search-quality`; commands `/sweep`, `/flow`, `/perf`, `/scale`; agents `flow-breaker`, `perf-profiler`, `scale-auditor` (the two browser agents carry no `tools` line, so they inherit the MCP tools). `PackDef.mcp` gained a `builtin: "browser"` form: a server enigma launches itself (`browserInvocation` from mcp-deploy.ts), registered by `deployPack` on every launch (`registerPackMcp(id, tool, true)`) only while the `browser` toggle is on (off removes it from the context on the next launch; an unparseable context `.claude.json` is left untouched, same as `applyJsonEntry`), while shipped scripts (`relArgs`, Helio's python server) stay behind `enigma pack setup`. Verified by launching `enigma orion -p` on a test page: the agent opened it in Chrome, ran the three-query search check and reported the 404 and the missing empty state planted in it. `orion` is reserved in `command-names.ts` `PACK_COMMANDS` (a test fails when a pack is added without it). Publishing: its own version-guarded step in `publish.yml`.
- RENAMED "PACK" -> "AGENT" (user: "pack ... vaya nombre espantoso"). User-facing surface only: `enigma agent <list|install|remove|update|setup|cli|use|run>` + `agents`; `enigma pack`/`packs` keep working and print a one-line deprecation notice on stderr; help, completion (both words), dashboard tab/copy ("Agents"), API body field `agent` (alias of `pack`), session-source labels. DELIBERATELY UNCHANGED for compatibility: the code names (`packs.ts`, `PackDef`, `launchPack`), config keys `packs`/`packAccounts`/`apiPack` (`api-pack`), the managed root `~/.enigma/packs`, the `pack:<id>` session-source id (now also `agent:<id>`), the dashboard route `#/packs` and `/api/packs`, and `api --pack` - `--agent` is ALREADY the install-target flag (`-a/--agent claude`), so it cannot be the API alias.
- VEGA = the third agent, built on REA (morluto/rea, MIT), and the first with an ENGINE. Named Vega by the user (not "REA"); upstream identity stays: `rea-agents` package, `rea` bin/CLI verbs and the `rea` MCP server name (the vendored skill and `rea doctor` expect it). `packages/vega` (@enigmax/vega) ships REA's `reverse-engineer-anything` skill vendored by `scripts/sync-vega.mjs` (`npm run sync:vega -- --version <x.y.z>`) from the PUBLISHED npm tarball of `rea-agents@<pin>` (never repo main: main's skill describes tools the release lacks), plus `assets/engine.json` {package, version} - the same pin - and enigma's own AGENTS.md + six commands mapping REA's six MCP prompts (investigate, compare, trace-crash, reconstruct, unknowns, capture). No sub-agents on purpose: one stateful REA session per agent; parallel calls on one open target are what #3509 loses.
- ENGINE (`src/agent-engine.ts`, `PackDef.engine` + an `mcp` entry with `builtin: "engine"`): `ensureEngine` npm-installs the exact pinned version into `<agentRoot>/engine` (version-gated; both fields validated by regex before reaching npm's shell) at `agent install`/launch/`enigma update`; the MCP entry is `<node> <engine>/node_modules/rea-agents/scripts/rea.mjs mcp` - NOT REA's own `cmd.exe /d /c npx -y rea-agents@x mcp`: no per-start package resolution, no cmd/console window, and `pickNode` chooses a node satisfying the engine's `engines.node` (^22.19 || ^24.11 || >=26) from PATH + nvm/nvm-windows dirs, so a shell defaulting to Node 20 still gets a server that starts (verified: v20 first on PATH -> picks nvm v26). REA's own `doctor --client claude_code` reports this registration HEALTHY. Measured 2026-10-14: initialize ~1 s, 207 tools, 6 prompts.
- ENGINE LOCK + API: `sync-vega.mjs` also writes `assets/engine-lock.json` (npm lockfile for a host `{ name: "enigma-agent-engine-host", dependencies: { rea-agents: <pin> } }`, checked against the registry integrity); `readEngineSpec` accepts it only when it locks that exact pin with an integrity hash (else the spec is invalid), and `installEngine` then runs `npm ci`, so transitive deps never float on user machines. `ensurePackContext` (local API path) NEVER installs the engine: it fails fast with `enigma agent setup <id>`, because a sync npm install would freeze the API event loop. `registerPackMcp` reports a server only when `hasContextServer` finds it written (an unparseable config is refused, not reported). `pickNode` treats only a runtime flagged `onPath` as the PATH node, and probes runtimes once per process.
- MULTI-TOOL MCP: `registerPackMcp` now writes every agent server through `applyContextServer` (mcp-deploy.ts) in the tool's own format (claude/codex/opencode/kimi), not only claude. It REWRITES command/args/timeouts and KEEPS fields it does not own (env from `rea setup` provider discovery, kimi `enabledTools`, a codex `env`/`env_vars` line or `[mcp_servers.<n>.env]` table). Timeouts (#3509: a long Ghidra analysis is cut by the client and restarts from scratch): claude `timeout` 6 h (also lifts the 30-min stdio idle cut), codex `tool_timeout_sec` 21600 (default 60 s) + `startup_timeout_sec` 30 (REA's own), opencode `timeout` 30000 (tool-list fetch only, default 5 s), kimi `toolTimeoutMs`/`startupTimeoutMs`.
- `enigma agent setup vega [--tool t] [-- <rea setup flags>]`: installs the engine, deploys, runs REA's interactive `setup --client <id>` with the tool's config-dir env pointing at the agent context (REA honors CLAUDE_CONFIG_DIR, CODEX_HOME, KIMI_CODE_HOME, XDG_CONFIG_HOME), re-registers (restores enigma's launcher, keeps setup's env), then `doctor`. `enigma agent cli vega -- <args>` runs the REA CLI on the same install + node. The dashboard's Setup only registers (setup is interactive) and copies the terminal command.
