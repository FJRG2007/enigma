# Runtime config (.enigma.json) and behavior carve-outs

- User-facing runtime toggles live in `.enigma.json`, read by `src/config.ts` with precedence: built-in defaults -> `~/.enigma.json` -> repo `.enigma.json` (nearest wins). It is NOT gitignored, so a team can commit it (same intent as `.githooks/enigma-guard.json`). Managed via the `enigma config <key> <on|off>` subcommand (mirrors the guard-config pattern, not a new prompt flow).
- First toggle: `commitEmoji` (CLI key `commit-emoji`, default on). It enables the gitmoji map in `git-policy` SKILL.md, AND the gate's own commit subjects (`gate/pipeline/steps/commitMessage.ts`) - the gate commits into the same history, so a setting that only reached the agent left half the commits looking different. See `docs/notes/gate.md`. THIRD commit site, and the one the toggle cannot reach: this repo's own GitHub Actions workflows. A workflow runs against a checkout but never reads `.enigma.json`, so `.github/workflows/screenshot.yml` writes the emoji literally into its preview-refresh subject (git-policy's `chore` emoji). `tests/gate/commit-message.test.ts` pins it - it scans every `git commit -m` in `.github/workflows/` and checks the subject's emoji against the type-to-emoji map parsed out of `git-policy` SKILL.md, so a new workflow that commits without one fails the suite.
- Permission bypass is DEFAULT ON (security downgrade by deliberate user choice): `permissionBypass` (CLI `permission-bypass`, default true) plus `bypassDisabled: string[]` in `.enigma.json`. `resolveBypassSelection` (permissions.ts): `--no-bypass` -> none; explicit `--bypass` wins; else if `permissionBypass` is on, default = all `BYPASS_SUPPORTED` agents (claude, codex, opencode) MINUS `bypassDisabled`, applied in `--yes` runs too (interactive still shows a review multiselect preselected to the defaults). Per-agent opt-out persists: `setBypass(name, ..., off)` calls `config.setBypassDisabled(name, true)` (writes the GLOBAL `.enigma.json` list), so a deliberate off is never auto-re-enabled by a later install; `on` clears it. So "install Codex after enigma -> next install bypasses it" works, while "disabled manually before/after" sticks. Every enable is logged loudly (`applyBypass` warns "approval prompts are now OFF"). `setEnigmaValue` accepts `string[]` for the array. If you change this posture, update permissions.ts header, both READMEs, and cli.ts help.
- `parallelSubagents` (CLI key `parallel-subagents`, default OFF, opt-in) is a DIFFERENT kind of toggle than `commitEmoji`: it does NOT add an opt-out note the model reads at runtime - it physically adds/removes a section in the DEPLOYED memory file. The section is authored in BOTH memory files (`assets/memory/{CLAUDE,AGENTS}.md`) wrapped in `<!-- enigma:parallel-subagents:start -->`/`<!-- enigma:parallel-subagents:end -->` markers (blank line each side). `skills.ts` no longer copies memory verbatim: `renderMemory` strips the marked block when the toggle is off, `memoryStatus` compares the RENDERED source (not raw bytes), and the install write uses `writeFileSync(renderMemory(...))` not `cpSync`. `applyMemoryToggles(scope)` (exported) re-renders already-deployed memory files (existsSync-guarded; never creates a new deployment) and returns the changed agents. Both surfaces call it after a memory-affecting write: `runConfigCli` (then prints a restart notice via `runningStatus`) and the TUI `persistPending`. Setting carries `affectsMemory?: boolean`. Because the file content changes, the user MUST restart the agent (memory loads at startup) - that is why this toggle prints/needs a restart and `commitEmoji` does not. Subtask DECOMPOSITION (the always-on part) lives OUTSIDE the markers and is never stripped. To add another memory-gated toggle, reuse the marker + `renderMemory` pattern and set `affectsMemory: true`.
- `outputStyle` (CLI key `output-style`, default `off`) is the first CHOICE (enum) setting, not a boolean: values `off|lite|full|ultra` (type `OutputStyle` in config.ts). It reuses the memory-marker mechanism: the `<!-- enigma:output-style -->` block (both memory files) carries a `{{output-level}}` placeholder; `renderMemory` strips the block when `off`, else replaces the placeholder with the level AND resolves the per-level `enigma:case` blocks (see below), so the deployed file describes only the selected level. The settings registry models choice settings WITHOUT breaking the boolean TUI/CLI: `enigmaChoice` gives a boolean FACE (`read` = value != off; `write(true)` = enabledDefault `full`, `write(false)` = off) PLUS `choices`/`readChoice`/`writeChoice` for exact values. So the TUI shows on/off (on=full) and `enigma config output-style <off|lite|full|ultra>` (or on/off) both work; `runConfigCli` branches on `setting.choices`. `enigmaToggle`'s `field` is now constrained to `BooleanConfigKey` (a mapped type) so a string field can't be passed to it. Install-time: `--output-style <v>` flag + an interactive `p.select` in `resolveOutputStyle` (skills.ts) writes the config at scope BEFORE the plan, so `memoryStatus`/`renderMemory` reflect it (writing before the plan is required - else a stale `identical` status would skip the memory update; cost is that aborting the install keeps the chosen preference). The deployed block documents only LIFTING the compression ("normal mode"), not switching between levels: since the case blocks leave exactly one level described, an in-block example naming a level the file never explains would be dead copy - a level CHANGE goes through `enigma config output-style <level>` (plus the restart every memory edit needs). Reference clone for study: `references/repos/caveman` (gitignored) - the name stays OUT of enigma's own assets, docs and site copy.
- WHAT THE BLOCK HAS TO SAY, learned from the report "I have it on full and the output looks the same". The first version listed the three levels and their word-level edits (drop filler, drop articles) and nothing else, which fails twice: (1) it is advisory-shaped, so the model reads it once and drifts back to normal prose a few turns in - the block now opens with the persistence clause (active on EVERY response; unsure -> it still applies) and carries a Not/Yes example pair, the anchor that actually moves behavior; (2) word-level edits are not where the tokens are. A reply is long because of its SHAPE - four essays for a four-part question, a heading on a three-line answer, restating the request, narrating the route, listing what was never touched - so the block now rules on answer shape first and filler second. That omission rule is deliberately SCOPED: process narration and ruled-out alternatives go, but work left unfinished, unverified or blocked is an outcome the kernel's Task Execution rules require reporting, so the bullet exempts it - a rule that silenced it would make this block cause exactly the failure its own opening sentence forbids. It also states the boundary in the other direction: this compresses the ANSWER, never the thinking, the tool calls, the verification or the scope, because a short reply that skipped a check is the one failure the rule could cause.
- PER-LEVEL CASE BLOCKS IN MEMORY: `applyCaseBlocks` (skills.ts) is shared by `renderSkill` and `renderMemory`, so the memory file uses the same `<!-- enigma:case:KEY=VALUE -->` mechanism as a skill - a deployed memory never spends context describing the two levels the user did not pick. Consequence for the byte budget: `checkMemoryBudget` measures `budgetedBytes(content)`, not the file size, dropping the markers and charging the worst case a user can SELECT. Getting that right needs both axes, because the two are not the same grouping: every block carrying the selected value deploys together, so bytes are SUMMED per `key=value`, and only then is the MAX taken per key (the values are what the user chooses between). Keying the max by bare KEY - the first cut - underbills any key with two blocks sharing one value, letting a file over budget pass. Headroom against `MEMORY_BUDGET_BYTES` is now a few dozen bytes: the next kernel line has to pay for itself by removing another, which is the pressure the budget exists to apply. Covered by `tests/memory-output-style.test.ts` (one level rendered, no markers or placeholder left, a case block for every selectable level, budget accounting). The anchor Not/Yes pair is SPLIT across the boundary: the bad prose stays shared (it is level-independent) and each case carries its own rewrite of it, so an `ultra` deployment does not demonstrate `full`-shaped prose right under the `ultra` rule. AUTHORING GUARD: `applyCaseBlocks` compares against `String(cfg[key])`, so a mistyped KEY reads as `"undefined"` and an unselectable VALUE never matches - either one DELETES the block and its body from every deployed file with no error, which on the always-on kernel means always-on guidance silently vanishes. `checkCaseBlocks` (skills.ts, run by `enigma check` over both memory files AND every skill's SKILL.md) rejects a key absent from `CONFIG_DEFAULTS` and a value outside `conf.CONFIG_CHOICES[key]` (booleans: `true`/`false`; free-form keys are existence-checked only). `CONFIG_CHOICES` (config.ts) is the one place the enum arrays are mapped to their config keys - add a new choice setting there too.
- `minimalCode` (CLI key `minimal-code`, default `full` = ON; deliberate behavior choice - the laziest-solution-that-works discipline is a baseline, opt OUT with `minimal-code off`) is the SECOND choice (enum) setting, built as an exact clone of the `outputStyle` mechanism but for code minimalism (anti-overengineering) instead of prose compression. NOTE this is the one place it diverges from `outputStyle`/the opt-in toggles: its default is ON, not off. Type `MinimalCode`/`MINIMAL_CODE_LEVELS` in config.ts; `<!-- enigma:minimal-code -->` block in both memory files with a `{{minimal-level}}` placeholder; `renderMemory` strips when `off` else binds the level; `enigmaChoice("minimal-code", "minimalCode", ..., MINIMAL_CODE_LEVELS, "full", true)` in the registry; install-time `--minimal-code` flag + `resolveMinimalCode` (skills.ts, called right after `resolveOutputStyle`). The detailed rules live in the `anti-overengineering-policy` SKILL (the always-on memory block is the compact intensity switch + ladder summary, pointing at the skill), so this is the canonical example of the memory-toggle + policy-skill split: outputStyle was memory-only, minimalCode pairs a memory toggle WITH a policy skill. WHY two parallel settings rather than generalizing: each binds a distinct placeholder/block and prompts independently at install; the shared plumbing is `enigmaChoice` + the marker mechanism, already reused. The on-demand TOOLS (review of a diff, repo-wide audit, debt-marker ledger) ship as ONE companion skill `anti-overengineering-review` (a skill, not a slash command - it must auto-trigger on the review/audit/debt phrases, which a `/command` cannot; commands are reserved for explicitly-invoked actions like `/improve`. enigma now distributes skills+memory AND slash commands - see the command-distribution note below - but model-triggered policy still belongs in a skill). It owns complexity-only review (tags delete/stdlib/native/yagni/shrink, `net: -N lines` scoring, the `grep -rnE '(#|//) ?enigma:'` debt-marker ledger - deliberate code shortcuts are flagged with an `enigma:` comment naming the ceiling + upgrade path) and defers correctness/security/perf to code-review-policy; the always-on build discipline stays in anti-overengineering-policy. So the minimal-code feature is: 1 setting (`minimalCode`) + 2 skills (policy = build-time, review = inspect-time) + `docs/examples/`. WHY a custom `enigma:` code-comment marker (not the deployed `<!-- enigma:NAME -->` memory markers): different context (source-code comments vs memory HTML); the ledger grep is anchored to `#`/`//` line comments so it never matches the HTML markers.
- `gate` (CLI key `gate`, default ON, still experimental) is BOTH a command-deploy toggle AND a memory-marker toggle. Being on by default is what makes DELIVERY the interesting part: `bundledCommands` filters `gate.md` by the toggle and `syncTarget` copies commands, so `enigma update` -> `syncDeployed` carries both effects (command + re-rendered memory block) into an EXISTING deployment - no separate re-assert like `verify`/`statusline`/`claudeTrust` needed, only the one-time notice, which `syncDeployed` derives by sampling `existsSync(gate.md)` before the copy loop and after it. Note the asymmetry: the copy loop never PRUNES a command dropped from the set, so removal stays `applyGateToggle`'s job at toggle time (a sync will not re-add it, since the filter excludes it). The `enigma gate` CLI family still refuses to run when the toggle is off, and its message now reads as "you switched this off" (global or the project's own `.enigma.json`) rather than "opt in". The toggle is also reachable FROM the agent: `assets/commands/gate.md` maps `/gate on|off|status` onto `enigma config gate ...`, defaulting to `-l` (this project) because a chat-issued switch should be the narrow reversible one, `-g` only when the user says "everywhere". That status read is why a bare `enigma config <boolean-key>` now PRINTS the effective value instead of erroring with "Missing value" - list and value settings already answered when called bare, booleans were the odd one out. The command side (`applyGateToggle` in command-deploy.ts, called by the custom `setGate` in settings-registry.ts) deploys/removes the `/gate` slash command immediately (the verbatim-file-copy twin of `applyCompressToggle`). The NEW behavior side: `gate` now also carries `affectsMemory: true`, so toggling re-renders the deployed memory via `applyMemoryToggles` (all three surfaces - CLI settings.ts, dashboard-settings.ts, TUI opentui.ts - already honor `affectsMemory` generically). Both memory files have an `<!-- enigma:gate:start/end -->` block (no placeholder, plain strip - like `recall`/`parallel-subagents`, not the `{{...}}`-bound `output-style`/`minimal-code`); `renderMemory` strips it when `!cfg.gate`. WHY a memory block and not just the skill/command: skills/commands are SKIPPABLE (the model decides to load them), so "auto-drive the gate without being asked" must live in the always-on memory channel. The block encodes the chosen behavior: auto-drive AFTER finishing a code task whose changes are COMMITTED (not every edit) on ANY branch, auto-run `enigma gate init` once if uninitialized, authorize `auto-fix`/`no-op` findings, ESCALATE every `ask-user` verbatim, NO `--yes`, never auto-merge (leave the PR ready). PER-PROJECT opt-out is a RUNTIME check the block tells the agent to make - a repo `.enigma.json` `gate: false` (nearest-wins via config.ts precedence) makes the agent skip auto-driving there; at project (`local`) scope `renderMemory` also strips the block outright since it reads nearest-wins config. The detailed command reference stays in the `/gate` command/gate skill; the memory block is the compact "when + how autonomous" switch. Docs: `apps/web/.../concepts/gate.mdx` ("Automatic driving" section) + the `gate` row in `reference/configuration.mdx`.
- `gateProtectedBranches` (CLI key `gate-protected-branches`, default EMPTY, `kind: "list"`) is the ONLY branch restriction the gate has. It replaced a hardcoded refusal in `preflightGuard` (gate/cli/axiDrive.ts) that rejected the repo's default branch outright; the pipeline itself never needed that guard - `rebase.ts` already drops both rebase targets when `branch === defaultBranch`, `pr.ts` skips PR creation there, and the CI step then finds no PR URL and skips too, so a default-branch run is review/test/document/lint plus a push that lands straight on the branch. That last part is the reason the setting exists: a repo whose default branch must only be reached through review lists it here, and `axi run` refuses it with the `enigma config gate-protected-branches remove <branch>` escape in the help. Matching is EXACT (trimmed, no globs) - a pattern typo would silently widen the rule to branches the user never meant to protect. It is the first non-`globalOnly` list setting, hence `updateEnigmaList`/`readEnigmaList` in config.ts (the scoped generalization of `updateGlobalList`, which now delegates); both read and write ONE scope's own file, never the merged view, so a project list is not seeded by the global one - while `preflightGuard` reads the MERGED config, which is what makes a repo's `.enigma.json` override the global list. Caveat: the TUI's list editor writes `global` unconditionally (opentui.ts), so a project-scoped list is set from the CLI (`-l`) or the dashboard.
- `claudeTrust` (CLI key `claude-trust`, default ON, `globalOnly`) retires Claude Code's "Is this a project you trust?" prompt for ANY path. The mechanism is Claude's user-global `.claude.json` (NOT settings.json): `projects[<key>].hasTrustDialogAccepted`. Two client behaviors dictate the shape (both read out of the shipped binary, `V4_`/`Xur`/`EEe`): (1) when cwd IS the home directory the accept handler only sets SESSION trust (`homedir()===cwd() ? sessionTrust : persist`), which is why that folder asks forever no matter how often you accept; (2) trust is inherited by walking parents up to the filesystem root, but the SECOND form of the prompt (the gated-grants backstop) is skipped only when the workspace's OWN entry is trusted, and it fires whenever project/local settings carry `permissions.allow` rules or `additionalDirectories` - i.e. most repos with a `.claude/settings.local.json`. So `trustClaudeWorkspaces` (claude.ts) writes BOTH: the filesystem root (blanket, covers home + every new folder) and the workspace key. The workspace key must match the client exactly - `normalize(gitRoot ?? resolve(dir))` with forward slashes (`claudeWorkspaceKey`, reusing `findGitRoot` moved to util.ts so claude.ts does not import clack-heavy security.ts); a linked worktree is the one case the client keys differently (main repo root) and falls back to the inherited root trust. Same intent/effect split as `statusline` (flag = intent, `.claude.json` = effect) so a deliberate off is not re-applied by the next install/sync; `untrustClaudeWorkspaces` clears ONLY the root entries, never per-workspace ones (those are indistinguishable from a user's own accept, and clearing them would re-ask for every project they already trusted). Applied at three points: install (`applyClaudeConfig`), `syncDeployed` (which is what makes it path-agnostic - and covers `enigma update` + the hub's "update now" for free, since `runUpdateCli` calls it: every `enigma <tool>` launch and update re-asserts, so the directory being opened gets its own entry, and the notice is gated on `!getClaudeTrust()` so it prints once instead of per new folder; locked by `tests/sync-trust.test.ts`), and `mirrorClaudeTrust` from `mirrorAccountSettings` (a managed account has its own `.claude.json`). Deliberate security downgrade, same family as `permissionBypass` - it lives in the Permissions category for that reason.
- `autoSync` (CLI key `auto-sync`, default ON) makes `enigma <tool>` / `enigma account run` refresh deployed skills/memory before spawning the tool (`autoSyncForLaunch` in cli.ts -> `syncDeployed` in skills.ts). CONSENT BOUNDARY: a CLAUDE.md/AGENTS.md merely EXISTING proves nothing (users author their own - including this repo's root CLAUDE.md, which is claude's LOCAL memory target), so every memory write goes through `writeMemory`, which records the content sha in `~/.enigma/state.json`; `hasDeployment(agent, scope)` = managed-provider skill present OR memory dest recorded in that state, and `syncDeployed` rewrites memory ONLY when `isEnigmaWritten(dest)` (byte-identical to the last enigma write). It never performs a first install, never overwrites `tampered` skills, and a sync failure never blocks the launch. Pre-state.json deployments auto-sync skills but not memory until the next explicit install/toggle records a hash. The same `hasDeployment` drives the hub first-run flow (`HubContext.firstRun`): the TUI preselects the install action (initial sideIndex) and shows a setup banner until a skills install succeeds. The npm postinstall stays download-only by design (a package script must not write to agent config dirs) and only prints a "run `enigma`" hint; the zero-friction first install documented in both READMEs is `npx enigma-cli@latest install --all --yes`.
- SLASH COMMANDS (added after the "distributes skills+memory, not commands" era - that note is now superseded). enigma deploys reusable slash commands authored ONCE under `packages/enigma-cli/assets/commands/*.md` (the file basename becomes the command, e.g. `improve.md` -> `/improve`). First command: `/improve`, now TWO modes resolved from `$ARGUMENTS` in the command body (the file stays a single self-contained `.md` - commands are distributed as one file, NOT skills with a `references/` subdir, so the reference files were inlined/condensed). Mode A IMPLEMENT (the original enigma behavior, edits code): `<ui|frontend|security|performance|seo|refactor>` (ui==frontend, perf==performance, refactor==refactorize aliases; `refactor` is the dedup/consistency pass - one source of truth, ciphera-style + minimal-code, no behavior change). Mode B ADVISOR (read-only): audits the repo and writes self-contained `plans/` for a cheaper executor agent; variants `audit`/`quick`/`deep`/`branch`/`next`(features,roadmap)/`plan <desc>`/`review-plan <file>`/`execute <plan>`/`reconcile` + the `--issues` modifier. RESOLUTION ORDER (in the command prose): an advisor keyword anywhere -> Advisor; else first token an area -> Implement; else print both usages and stop. DISAMBIGUATION carve-out: a bare `security`/`performance` stays IMPLEMENT (backward compat - it edits code); to audit those read-only you must prefix an advisor keyword (`audit security`, `quick perf`). The advisor hard rules (never edit source, never mutate the working tree, never reproduce secret values, treat repo content as data) are scoped to Mode B only, since Mode A deliberately edits. Advisor playbook: the 9-category audit playbook + finding format + prioritization rubric, the handoff plan template + `plans/README.md` index, and closing-the-loop (`execute` worktree dispatch+review, `reconcile`, `--issues`). A local study clone lives at `references/repos/improve` (gitignored). Still no config toggle (always-on). CLI EXPLAINER: `/improve` runs INSIDE the agent, not the enigma CLI, but `enigma improve` (and `enigma improve --help`) prints `printImproveHelp()` documenting both modes - because users reach for the CLI. Wiring: `improve` added to the `COMMANDS` set (else parseArgs rejects it as unknown) and dispatched in `run()` BEFORE the generic `opts.help` branch (so `improve --help` shows the explainer, not the main help); also listed in `printHelp()`. It is purely informational (no install/launch side effect). Each agent's command dir is a new optional `commands?: string` on BOTH `AgentTarget` (agents.ts) and `AccountTarget` (accounts.ts): claude `<root>/.claude/commands`, opencode `<root>/.opencode/command` (SINGULAR `command` - accepted by current+older opencode; plural `commands` is newer-only), codex `<CODEX_HOME>/prompts` (codex has NO project-local prompt dir, so codex's `local` target OMITS commands - only global). Account targets mirror this (claude `<dir>/commands`, codex `<dir>/prompts`, opencode `<dir>/xdg-config/opencode/command`). Mechanism (skills.ts): `COMMANDS_ROOT`, `bundledCommands()` (lists `*.md`), `commandStatus(dest,src)` = STATELESS three-way `install`|`identical`|`replace` (byte-compare only - NO seal/version/sha/tampered logic, unlike skills; commands need no `npm run check`/seal). CONFLICT POLICY (user spec: "reemplazarlo"): a same-named command that is not byte-identical is ALWAYS overwritten ("replace existing") - enigma's command always wins the name, whether the existing file is an older enigma copy OR a foreign command. This also means a user-edited enigma command is reset on the next install/sync (deliberate - commands are enigma-managed, not user-owned like a tampered skill). Wiring: `PlanItem.commands: PlannedCommand[]`; computed in the plan loop (skipped on `--skills-only`/`--memory-only` and when `target.commands` is undefined); shown in the preview as `command /improve`; written in the install loop (mkdir + `writeFileSync(readFileSync(src))`, verbatim copy); folded into `changedAgents` for the restart notice. Sync: `syncTarget` gained a `commands: CommandEntry[]` param (after `skills`, before `createMemory`) and a trailing replace-on-drift loop; both call sites pass `bundledCommands()` (`syncDeployed` and `syncAccount`), so auto-sync and account-sync keep `/improve` current. WHY a command FILE not a skill: Claude merged commands into skills (`.claude/skills/x/SKILL.md`==`/x`), but opencode/codex do NOT reliably expose a skill as `/x`; the command/prompt FILE with `$ARGUMENTS` is the only mechanism all three document, giving uniform `/improve ui`. Command source frontmatter is minimal (`description`+`argument-hint`) so it is valid for claude+codex and harmlessly ignored by opencode. `assets` is already in package.json `files`, and `COMMANDS_ROOT=join(ASSETS,"commands")` rides the existing `ENIGMA_ASSETS_DIR` wiring (no new env override needed for the compiled binary). NO config toggle (always-on by default per spec); add one later via the `enigmaToggle` registry if needed. To add another command: drop a `*.md` in `assets/commands/` - no other change.
- `remoteSkills` (CLI key `remote-skills`, default ON): skills update from the GitHub repo WITHOUT an npm release. `src/skills-remote.ts` pins `main` to a commit (`repos/.../commits/main`), lists the recursive git tree (2 API calls total when nothing changed), and stores per-skill `{sig, version}` records in `~/.enigma/skills-cache/remote.json` - `sig` hashes the tree's (path, blob sha) pairs, so an unchanged skill costs ZERO raw fetches even when it was version-gated rather than adopted. A skill is adopted only when its remote sealed version is STRICTLY newer than max(bundled, cached); downloads are verified (managed provider + `computeContentSha` == sealed sha) and land via atomic tmp-dir swap under `~/.enigma/skills-cache/skills/`. `inspectSkills` (skills.ts) overlays that cache over the bundled assets, so `enigma install`, the TUI install AND `syncDeployed`/auto-sync all deploy it; a corrupt/tampered cache entry silently falls back to bundled. Memory files are deliberately NOT remote-updated (coupled to `renderMemory` markers/placeholders - package-versioned only). Fault-tolerance contract: every fetch is timeout-bounded (8s), any failure degrades to bundled/cached, one broken skill never blocks the rest, and the attempt is stamped up-front so an offline machine is throttled (10 min) like a success. Layering: `skills-remote.ts` must NOT runtime-import `skills.ts` (cycle); bundled versions are passed in by `refreshSkillsFromGitHub` (skills.ts), and `parseVersion`/`isNewer`/`listFilesRel`/`computeContentSha` moved to util.ts for that reason. Surfaces: `enigma install` (throttled check + spinner), the `enigma update` command and the hub's "update now" exit action (both `runUpdateCli` in cli.ts: forced skill refresh -> `syncDeployed` -> npm self-update only when `checkLatestNow` reports newer), and the detached `__update-check` child (background refresh, so plain launches auto-sync fresh skills). Tests: `tests/skills-remote.test.ts` (bun test, stubbed global fetch, per-test temp HOME via USERPROFILE/HOME env - the module resolves paths lazily per call to allow this); CI runs it via oven-sh/setup-bun.
  - PINNED REF (`install --ref <tag|sha>` / `ENIGMA_SKILLS_REF`, for a reproducible run). A pin is AUTHORITATIVE: it decides what is ADOPTED, not only which ref is read, so the strictly-newer gate is bypassed under a pin (pinning to an equal or older tag is the ordinary reproducibility case, and "fetched nothing" is the wrong answer to it) while the unpinned path keeps the gate that stops an install going backwards. The cache is scoped per ref (`skills-cache/skills@<ref>/` + `remote@<ref>.json`), so a pinned run's older skills can never be picked up by a later unpinned one, and `skillsOrigin` reports a commit only when the stamp's ref matches. That scoping needs RECLAMATION: `pruneRefCaches` keeps the 5 most recently stamped ref trees (ordered by stamp mtime - one stat per ref, never a tree walk) and drops the rest with their stamps, best-effort; the default branch's unsuffixed tree is not a candidate, so unpinned use never re-downloads. A ref is VALIDATED before it reaches an API URL or a directory name: `REF_RE`'s character class is not enough on its own because `.` and `/` are both legal in a ref, so `isSafeRef` also rejects any `.`/`..`/empty segment, and `pinnedRef` THROWS naming `--ref` or `ENIGMA_SKILLS_REF` rather than silently resolving to the default branch (a pin asked for and quietly ignored is the same class of bug as a dropped `--range`).
  - The `Skills source:` line install prints must state what was INSTALLED, never what was merely resolved or merely cached. A cache entry is not an adoption: `resolveSkills()` overlays one only when it is unbundled, pinned, or strictly newer, and a run inside the 10-minute check throttle performs no refresh and therefore no `pruneCache`, so entries the bundle has caught up with survive on disk. The count comes from `adoptedRemoteSkills()` - the same decision, not a `readdir` of the cache - and a ref that resolved but yielded no adopted skill is reported as a bundled install.
  - DISCOVERY MANIFEST (origin indirection, level-1 OSS pattern - Terraform `.well-known`, rustup `RUSTUP_DIST_SERVER`, Go vanity `go-import`): the skills ORIGIN (`repo`/`ref`/`skillsPrefix`/`apiBase`/`rawBase`) is NO LONGER hardcoded into the binary as the source of truth. The only baked-in origin is `DEFAULT_MANIFEST_URL` = a raw URL to `packages/enigma-cli/assets/skills-manifest.json` on `main` (fetched over raw = no API key, no rate limit, redirect-following so a GitHub repo/account rename still resolves). `resolveSource()` fetches that manifest, overlays validated fields onto the baked `DEFAULT_*` (`applyManifest`: https-only URLs, `REPO_SLUG_RE` repo, `isSafePrefix` prefix/no traversal, `REF_RE` ref; env `ENIGMA_SKILLS_REF` always wins the ref), caches the last-good manifest at `~/.enigma/skills-cache/manifest.json`, and falls back cache->defaults on any failure (same fault-tolerance contract - a 404/offline manifest just uses the bundled defaults, so updates never break). Every API/raw call in `refreshRemoteSkills`/`downloadSkill`/`groupTreeBySkill` now takes the resolved `SkillSource` instead of module consts. WHY level-1 (no signing): the manifest lives in the SAME repo as the skills and is served over HTTPS from GitHub, so controlling it == controlling the repo == already able to ship malicious skills - the indirection does not widen the trust surface. Level-2 (sign the manifest with an offline Ed25519 key baked as the trust anchor, rustup `.asc`/TUF-style) is the upgrade path if the origin ever moves OFF GitHub to an untrusted host. Override the manifest URL for dev/mirrors/tests with `ENIGMA_SKILLS_MANIFEST_URL`. To relocate the source after a repo move: edit `assets/skills-manifest.json` (`source.repo`/`skillsPrefix`) - already-installed CLIs follow it; GitHub's rename redirects bridge the transition window. The test stub serves a `*/skills-manifest.json` endpoint (NOT counted as a raw download) and there is a relocation test proving a manifest repoints commit/tree/raw to a renamed repo+prefix.
