# A failed write must never surface as a save (`ApplyResult.error`)

- `ApplyResult` is `{path?, changed, error?}`. `changed:false` means "already that value"; `error` means "could not". WITHOUT the error field there is no way to tell them apart, and both `applySetting` (dashboard-settings.ts) and `runConfigCli` (settings.ts) re-read the value after a write - so a write that never happened reported `ok`/"Saved"/the value merely asked for. Any setting backed by ANOTHER tool's config (today only `gh-telemetry`) can refuse for reasons outside enigma; those go through a `write` that returns `error`, and both surfaces must propagate it (the CLI also exits non-zero).
- gh telemetry: `gh config get` EXITS NON-ZERO on a key it does not know, which is what every gh predating the `telemetry` setting does (distro packages lag many releases). `getGhTelemetry` folding that into `value !== "disabled"` reported a read that never happened as telemetry ENABLED, the write failed the same silent way, and `revalidate()`'s `if (code === 0)` kept the stale `true` in `~/.enigma/cache.json` forever. Rule: an unreadable value is `null` (unknown), never a guess. `ghTelemetryBlocker()` names the cause; `readChoice` separates "not installed" from "unavailable" (gh present but unable to answer) - the merged label sent people looking for a gh sitting on their PATH.
- Dashboard `apiJson(path, init)` (index.html) is the ONE place an `/api/*` call becomes parsed JSON or an Error naming the cause. Do NOT go back to bare `fetch(...)` + `res.json()` in a try/catch: `res.json()` throws on ANY non-JSON reply (an empty 405, a reverse proxy's HTML error page), and the catch then blamed an unreachable server - the one explanation that is wrong in exactly those cases.
- TESTING GOTCHA (cost a real side effect on the user's machine): a temp `HOME`/`ENIGMA_CONFIG_HOME` does NOT sandbox a setting whose state lives outside enigma's home. Driving `applySetting("gh-telemetry", true)` from a "isolated" repro wrote to the REAL `%AppData%\GitHub CLI\config.yml` and turned the user's telemetry on. Use the tool's own override (`ENIGMA_GH_BIN`) - `tests/github.test.ts` points it at a nonexistent path, which is exactly what "gh cannot answer" looks like, so it needs neither gh nor a network.
