# Cleaning up finished branches (`enigma branches`, `src/git-tidy.ts`)

- THE ASK: an agent or a gate run creates a working branch locally and on the remote, the work lands, and the checkout is left on a branch nobody will touch again while the branch piles up on both sides. enigma puts the checkout back on the default branch and removes the dead branch - "pero obviamente no debe borrar cosas que no sepa o que borren cambios que no esten en main". That second half is the feature; the deletion is the easy part.

- WHAT PROVES A BRANCH IS FINISHED, and why one check is not enough. `git branch --merged` and `git branch -d` both decide by ANCESTRY, so they answer "not merged" about every squash-merged branch - which is the common case in a PR workflow, and exactly the case this exists to clean up. `containedIn` therefore tries two proofs: ancestry first (`merge-base --is-ancestor`, settles merge commits and fast-forwards), then CONTENT. The content proof is the one that took a wrong turn first: the initial cut used the three-dot diff (`base...branch`) and it is WRONG here, because that measures from the MERGE BASE, which a squash merge does not move - a perfectly merged branch still showed its own files as added, and the squash test failed. What actually answers the question is: take the files the branch touched (merge-base vs branch), then compare exactly those files between base and the branch tip. Empty means base's copy of every file the branch changed is byte-identical to the branch's. That framing also defeats the case a patch-id check (`git cherry`) would wave through - base merged the branch and then REVERTED it, where the content is only on the branch and the patch-id still matches. Base moving on and editing one of those files also refuses; a false refusal costs a branch left behind and never a line of work, which is the right side to be wrong on.

- EVERY OTHER STATE IS A REFUSAL, and each one is REPORTED rather than silently skipped: a dirty working tree blocks the whole repository (nothing is touched, not even branches that would pass), a stash entry based on the branch, the branch checked out in another worktree, a protected name (`main`, `master`, `develop`, `development`, `trunk`, `release`, `stable`) or the resolved default branch, a remote copy that is AHEAD of what base contains, and a remote copy that could not be READ. That last one is the one worth stating: unverifiable is not the same as absent, so an unreadable remote keeps its branch and only the local copy goes. A git call that throws counts as "not contained" - the safe answer to a question we could not put is never "go ahead and delete".

- THE FORCED DELETE, AND WHY IT IS NOT A WEAKENING. `git branch -d` runs first so git's own check sits on top of ours. When it refuses, that is usually NOT new information - it refused on ancestry, about a squash merge the content proof already cleared - so insisting on `-d` would make the feature refuse nearly everything it was built for (measured: the first end-to-end run against a real squash-merged branch printed `kept feat/done: git refused to delete it`). So a refusal falls back to `-D`, but only after RE-PROVING containment against the live repository. That re-check is the actual value of the fallback: it costs one git call and closes the window between planning and deleting, where a concurrent commit or fetch could have made the plan stale. `tests/git-tidy.test.ts` pins both halves - the squash branch is deleted, the reverted one is kept.

- NOTHING IS DELETED THAT CANNOT BE RESTORED. The tip SHA goes into `~/.enigma/deleted-branches.json` (newest 200) BEFORE the deletion, and a write failure ABORTS that branch's deletion rather than being logged - the ledger is what makes the removal reversible, so a branch is never deleted while it cannot be written down (`tests/git-tidy.test.ts` puts a directory where the file belongs and asserts the branch survives). Every report line carries `git branch <name> <sha>`, and the test runs that exact command to prove it restores the branch. `git reflog` keeps the same commit reachable independently.

- THE LEDGER PATH RESOLVES THROUGH `enigmaHome()`, NOT the os home helper, and this is the bug CI caught that Windows could not. Bun on Linux resolves `homedir()` from the OS account and IGNORES a reassigned `$HOME` (the same trap documented for `sec-operator-env-leak`), so on the runner the ledger was written to `/home/runner/.enigma` while the test had blocked a path under its temp home. Every assertion still passed except the one that matters - "nothing is deleted while the undo ledger cannot be written" - because the write it was supposed to break succeeded somewhere else entirely, and the branch was deleted. The test now sets `ENIGMA_CONFIG_HOME` alongside HOME/USERPROFILE. Lesson for the next `~/.enigma` path: there is one way to resolve it and it is in util.ts.

- ORDER OF OPERATIONS in `tidy`: switch to the default branch first when the checkout is on a branch being removed (a failed checkout ABORTS everything - the tree is no longer in the state the plan was built from), then per branch: record, delete local, delete remote. Local before remote so a failed remote push leaves the branch recoverable from the ledger rather than gone from both.

- SURFACES. `enigma branches` reports every branch with its verdict and touches nothing; `enigma branches tidy [branch...]` performs it (`--dry-run`, `--no-remote`, `--target <remote>`). Automatic after a gate run via `GateExecutor.tidyFinishedBranches`, gated on `gateTidyBranches` (default ON, `enigma config gate-tidy-branches off` to stop it) and never fatal - the run is already completed and reported by then, and a repository this cannot tidy is one it must leave alone anyway. It reads `readConfigAt(repo.workingPath)`, NOT `readConfig()`: the daemon's cwd is not the user's repository, so a project-local `.enigma.json` only reaches it when the path is named. NOTE what the automatic pass does NOT do: the run that just finished has not landed yet, so it never touches the branch it was validating - what it clears is the PREVIOUS ones, whose PRs have since merged.

- The tests build real git repositories rather than mocking git, one per refusal. A refusal that only holds against a fake is worth nothing, and two of the bugs above (the three-dot diff, the `-d` ancestry refusal) were only visible against a real one.
