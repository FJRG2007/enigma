# Cleaning up finished branches (`enigma branches`, `src/git-tidy.ts`)

- THE ASK: an agent or a gate run creates a working branch locally and on the remote, the work lands, and the checkout is left on a branch nobody will touch again while the branch piles up on both sides. enigma puts the checkout back on the default branch and removes the dead branch - "pero obviamente no debe borrar cosas que no sepa o que borren cambios que no esten en main". That second half is the feature; the deletion is the easy part.

- WHAT PROVES A BRANCH IS FINISHED, and why one check is not enough. `git branch --merged` and `git branch -d` both decide by ANCESTRY, so they answer "not merged" about every squash-merged branch - which is the common case in a PR workflow, and exactly the case this exists to clean up. `containedIn` therefore tries two proofs: ancestry first (`merge-base --is-ancestor`, settles merge commits and fast-forwards), then CONTENT. The content proof is the one that took a wrong turn first: the initial cut used the three-dot diff (`base...branch`) and it is WRONG here, because that measures from the MERGE BASE, which a squash merge does not move - a perfectly merged branch still showed its own files as added, and the squash test failed. What actually answers the question is: take the files the branch touched (merge-base vs branch), then compare exactly those files between base and the branch tip. Empty means base's copy of every file the branch changed is byte-identical to the branch's. That framing also defeats the case a patch-id check (`git cherry`) would wave through - base merged the branch and then REVERTED it, where the content is only on the branch and the patch-id still matches. Base moving on and editing one of those files also refuses; a false refusal costs a branch left behind and never a line of work, which is the right side to be wrong on.

- EVERY OTHER STATE IS A REFUSAL, and each one is REPORTED rather than silently skipped: a stash entry based on the branch, the branch checked out in another worktree, a protected name (`main`, `master`, `develop`, `development`, `trunk`, `release`, `stable`) or the resolved default branch, a remote copy that is AHEAD of what base contains, and a remote copy that could not be READ. That last one is the one worth stating: unverifiable is not the same as absent, so an unreadable remote keeps its branch and only the local copy goes. A git call that throws counts as "not contained" - the safe answer to a question we could not put is never "go ahead and delete".

- A DIRTY WORKING TREE REFUSES ONE BRANCH, NOT THE REPOSITORY, and the blanket it replaced is the reason this feature did nothing for months. Uncommitted changes protect exactly one thing: the branch that is CHECKED OUT here, because that is the only branch whose deletion needs the checkout moved off it - `git branch -d <other>` never reads or writes the working tree. Blocking the whole repository therefore bought no safety and cost everything: measured on the author's machine, 95 of the 96 automatic cleanups the gate had logged were skipped for exactly this reason and one for another, because a repository an agent is working in is dirty nearly all the time. "Clean tree" meant "never". The verdict is `dirty-worktree` and `tests/git-tidy.test.ts` pins both halves - a merged branch that is not HEAD is tidied with the tree dirty and the uncommitted file untouched, and the same branch checked out is kept.

- THE FORCED DELETE, AND WHY IT IS NOT A WEAKENING. `git branch -d` runs first so git's own check sits on top of ours. When it refuses, that is usually NOT new information - it refused on ancestry, about a squash merge the content proof already cleared - so insisting on `-d` would make the feature refuse nearly everything it was built for (measured: the first end-to-end run against a real squash-merged branch printed `kept feat/done: git refused to delete it`). So a refusal falls back to `-D`, but only after RE-PROVING containment against the live repository. That re-check is the actual value of the fallback: it costs one git call and closes the window between planning and deleting, where a concurrent commit or fetch could have made the plan stale. `tests/git-tidy.test.ts` pins both halves - the squash branch is deleted, the reverted one is kept.

- NOTHING IS DELETED THAT CANNOT BE RESTORED. The tip SHA goes into `~/.enigma/deleted-branches.json` (newest 200) BEFORE the deletion, and a write failure ABORTS that branch's deletion rather than being logged - the ledger is what makes the removal reversible, so a branch is never deleted while it cannot be written down (`tests/git-tidy.test.ts` puts a directory where the file belongs and asserts the branch survives). Every report line carries `git branch <name> <sha>`, and the test runs that exact command to prove it restores the branch. `git reflog` keeps the same commit reachable independently.

- THE LEDGER PATH RESOLVES THROUGH `enigmaHome()`, NOT the os home helper, and this is the bug CI caught that Windows could not. Bun on Linux resolves `homedir()` from the OS account and IGNORES a reassigned `$HOME` (the same trap documented for `sec-operator-env-leak`), so on the runner the ledger was written to `/home/runner/.enigma` while the test had blocked a path under its temp home. Every assertion still passed except the one that matters - "nothing is deleted while the undo ledger cannot be written" - because the write it was supposed to break succeeded somewhere else entirely, and the branch was deleted. The test now sets `ENIGMA_CONFIG_HOME` alongside HOME/USERPROFILE. Lesson for the next `~/.enigma` path: there is one way to resolve it and it is in util.ts.

- ORDER OF OPERATIONS in `tidy`: switch to the default branch first when the checkout is on a branch being removed (a failed checkout ABORTS everything - the tree is no longer in the state the plan was built from), then per branch: record, delete local, delete remote. Local before remote so a failed remote push leaves the branch recoverable from the ledger rather than gone from both.

- SURFACES. `enigma branches` reports every branch with its verdict and touches nothing; `enigma branches tidy [branch...]` performs it (`--dry-run`, `--no-remote`, `--target <remote>`). Automatic after a gate run via `GateExecutor.tidyFinishedBranches`, gated on `gateTidyBranches` (default ON, `enigma config gate-tidy-branches off` to stop it) and never fatal - the run is already completed and reported by then, and a repository this cannot tidy is one it must leave alone anyway. It reads `readConfigAt(repo.workingPath)`, NOT `readConfig()`: the daemon's cwd is not the user's repository, so a project-local `.enigma.json` only reaches it when the path is named. NOTE what the automatic pass does NOT do: the run that just finished has not landed yet, so it never touches the branch it was validating - what it clears is the PREVIOUS ones, whose PRs have since merged.

- The tests build real git repositories rather than mocking git, one per refusal. A refusal that only holds against a fake is worth nothing, and two of the bugs above (the three-dot diff, the `-d` ancestry refusal) were only visible against a real one.

## Proving against the remote, and the merge no-op proof

Measured in two of the author's repositories, the automatic tidy removed almost nothing for a reason no refusal reported: `main` was 560+ commits behind `origin/main`, so a branch merged through a PR was never "contained" in the base it was checked against. Three changes:

- `planTidy` fetches the default branch from the remote and proves against `<remote>/<default>` (`TidyPlan.baseRef`), falling back to the local branch offline. A branch counts as contained in EITHER the remote or the local default (`containedInAny`): the local one can be ahead after a merge not yet pushed, the remote after a PR merged elsewhere, and a failed fetch leaves no way to tell. The fetch is the one write a plan makes, and it only moves a remote-tracking ref.
- `containedIn` gained a third proof after ancestry and content: `git merge-tree --write-tree base branch` clean AND equal to `base^{tree}` - merging the branch would add nothing. It accepts a squash-merged branch whose files the base edited since (the content proof refuses those) and still refuses any branch with work the base lacks, conflict or not. git older than 2.38 fails the command and reads as "not contained".
- `tidy` runs `git worktree prune` first (not on a dry run): a worktree whose directory is gone no longer pins its branch as "checked out elsewhere". A worktree that still exists is never removed, clean or not, since it may belong to a live agent session.

## What was actually leaving branches behind (measured in polaris)

The complaint was "agents always leave dead branches". The first `enigma branches` there said "Nothing can be cleaned up here: the working tree has uncommitted changes" - the installed CLI was 1.54.4, from before the per-branch dirty-tree fix (1.55.0). With current code the plan showed what the rest was:

- **Abandoned worktrees pin their branches.** 34 of 41 local branches were "checked out elsewhere": agents create a worktree per task (`.claude/worktrees`, session scratchpads, sibling directories) and leave it. `tidy` now removes a linked worktree when it is clean (untracked files count as work), holds nothing the base lacks, is not locked, is not the gate's own, and has not been touched for 6 hours (`WORKTREE_IDLE_MS`: directory, HEAD, index and reflog mtimes). `git worktree remove` without `--force` re-checks the clean half. Then the plan is rebuilt and the freed branches are judged like any other. In polaris 7 qualified; the rest were dirty, fresh or unmerged, and stay.
- **The `origin/*` "branches" were stale tracking refs.** 40 of them stood for 4 real branches; the gate's mirror remotes added 279. `tidy` runs `git remote prune` per remote, which deletes only tracking refs whose branch is gone - no work anywhere.
- **Remote-only branches** are now in scope: deleted on the remote only when the local tracking ref matches the remote sha, the content is contained in the base, `gh pr list` shows no open PR on it, AND a merged PR from this repository had it as head at that very sha. Containment alone is not proof: a shared branch (staging, a deploy branch, a teammate's branch pushed before its first commit) is contained in the default branch every time it is fast-forwarded. A branch that is LONG-LIVED is kept too: one that was ever the base of a PR, or the head of more than one merged PR (staging, production, next, a `release/x` merged repeatedly through release PRs) - a single merged-PR-at-tip match is what a dead feature branch looks like, and either of those says this one keeps coming back. `gh pr list` reads only the most recent 1000 PRs, so a long-lived branch whose PRs all fall outside that window is not caught by this check, but the merged-PR-at-tip requirement above still has to hold for it. An unreadable PR list (no gh, not GitHub) keeps all of them and reports it as a note, not a failure. The tip is recorded in the undo ledger first.
- **Nothing ran outside a gate run.** The turn-end hook now schedules `enigma branches tidy --keep-current` in a detached child at most once an hour per repository (`claimBackgroundTidy`, marker under `~/.enigma/tidy/`), behind `gateTidyBranches`; `ENIGMA_NO_BACKGROUND_TIDY` turns it off for a process (the verify tests set it). `--keep-current` keeps the checked-out branch: a branch an agent just created has no commits, so it is contained in the default branch, and switching the checkout under a live session would land its next commit on main. The end-of-run pass also covers the run's own branch now that the ci step closes the run within seconds of the merge.

## The gate mirror and dead remotes (what was still left)

After all of the above the author still saw dead branches in this repository, and every one was a family `tidy` never looked at:

- **The gate's own bare mirror** (`~/.enigma/gate/repos/<id>.git`, remote `gate`) keeps every run branch forever - 7 `feat/*`/`fix/*` here, all landed - and `git fetch` mirrors them back as `remotes/gate/*`. `remote prune` cannot help: the branches still exist in the mirror. `tidyGateMirror` deletes a mirror branch when its tracking ref here is at the mirror's tip, that tip is contained in the base (same `containedInAny` proof), and its ref has not moved for 6 h (`MIRROR_IDLE_MS`; a run lasts minutes, and a branch a run still has checked out is refused by git itself). The delete runs INSIDE the bare repository (`git branch -D`), never as `git push gate --delete`: a push to the gate remote is how runs start. Only a `gate` remote that resolves under enigma's own gate dir is touched - a user's remote that happens to be called `gate` is not. Restore: `git --git-dir=<bare> branch <name> <sha>`, printed and ledgered (`gate/<branch>`). An aborted run's fixes are not contained in the base, so they stay (the recovery path in memory relies on that).
- **Tracking refs of a remote that no longer exists** (`refs/remotes/gatebare/main` here, from a renamed remote): `remote prune` cannot reach a remote that is gone. `tidyOrphanRefs` removes one only when contained in the base - with its remote gone the ref may be the last pointer to its commits - and reports the rest as a note. Ledgered under the full ref name; restore with `git update-ref <ref> <sha>`.

Both run inside `tidy`, so the hourly background pass, the gate's end-of-run pass and `enigma branches tidy` all get them; `--dry-run` lists them.

## Why the mirror still kept every branch (2026-10-14)

`tidyGateMirror` removed nothing in this repository for three independent reasons, each enough on its own:

- **Idleness read the shared `packed-refs` mtime.** Packed branches have no loose ref file, and git rewrites `packed-refs` on every ref change, so every packed branch looked touched minutes ago. `refTouched` now reads the branch's own reflog (`logs/refs/heads/<b>`), then its loose ref, then its tip's commit time - never `packed-refs`.
- **It required the local tracking ref to equal the mirror tip.** Nothing fetches `gate/*` after a run pushes its last fix, so 7 of 14 lagged one commit and were skipped forever. `fetchTip` fetches the lagging branch first. `remoteOnlyBranches` had the same requirement against `origin` and now fetches too; its delete is leased to the proved tip (`--force-with-lease=<b>:<sha>`).
- **Content containment cannot prove a squash-landed run branch.** The gate squash-merges and the base keeps editing the same lines (version bumps, CITATION), so a landed release branch is never "contained". A merged PR whose head was this branch at this exact tip is the proof now (no open PR on it), with containment as the fallback when PRs cannot be listed. All 10 landed mirror branches here matched a merged PR head (#123-#134).

## Local and remote branches landed by a squash-merged PR

Measured after a day of gate runs: every local branch the gate had merged (#135-#138) was reported "origin/main does not contain all of its work", and their copies on origin stayed. The gate pushes fix commits on top of the branch, squash-merges, and later commits edit the same files, so the content proof can never hold. `landedByPR` (git-tidy.ts) is the second proof, now used by the local plan, the remote copy check and the forced-delete re-check: exactly one merged PR from this repository on the branch, merged into the default branch (a PR into an integration branch proves nothing about the default one), no open PR, the branch is not a PR base, and the tip is that PR's head or an ancestor of it (`merge-base --is-ancestor`, the head fetched first). Every commit of the branch is then inside the merged PR, so no work is lost. A branch the gate REBASED with conflicts (its local commits rewritten, not ancestors of the PR head) has no mechanical proof and is kept - measured: 3 of 4 landed, the rebased one kept. Remote-only branches now need only the merged-PR-at-tip proof (the content check after it failed on the same squash shape). Remote deletes are leased to the proved remote tip. `tidy` reads the PR list once (`prsNow`) and passes it to `planTidy`; `enigma branches` (report) does the same via the exported `prHeads`.

## Worktrees of squash-merged branches, and one throttle per repository (2026-10-21)

Measured in polaris: 333 local branches, 263 of them pinned by linked worktrees agents left in session scratchpads and `.claude/worktrees` (100 from a single session); `enigma branches` reported "Nothing to clean up". Two causes:

- **`idleWorktrees` proved landing by containment only**, so a squash-merged branch's worktree was kept forever, and with it the branch. It now also accepts `landedByPR`. Of the 203 worktrees with a merged PR, 120 had a tip that is an ancestor of the PR head.
- **`landedByPR` gained a patch-equivalence fallback** (`patchesLanded`): when the gate rebased the branch, its commits are rewritten and no longer ancestors of the PR head, but `git cherry <prHead> <tip>` shows each has an equivalent patch there. 58 of the remaining 83 qualified. Refused when the range holds a merge commit (cherry skips merges; a conflict resolution is work) or any commit whose patch changed (25 kept, by design).
- **The hourly background throttle was keyed by worktree root**, so one repository with 42 worktrees could start 42 concurrent tidies over the same refs. `sharedRepoKey` reads the worktree's `.git` file and keys by the main repository instead.
- **The undo ledger was capped at 200 entries.** The first real cleanup with the fixes above (polaris: 334 -> 151 branches, 265 -> 114 worktrees) filled every slot and evicted the restore points of every other repository. It now keeps 90 days (git's reflog window), with 20 000 entries as a hard ceiling only.
- **Concurrent tidies reported vanished branches as problems.** Sessions still on the per-worktree throttle ran several tidies over polaris at once (67 branches ledgered two or three times), and the slower one reported 84 "moved since it was checked" plus "branch not found" from `-D`. A branch that no longer exists when its delete comes is a note ("already deleted"), not a problem.
