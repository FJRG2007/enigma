# Shell completion (`enigma completion`)

- `src/completion.ts` renders a completion script for bash, zsh, fish or PowerShell and `runCompletionCli` (cli.ts) prints it to STDOUT. It never writes to a shell profile: a CLI that edits someone's rc file on their behalf is exactly the surprise enigma does not do, so the help text tells the user where to put it (`eval "$(enigma completion zsh)"`, a file under `fpath`, `~/.config/fish/completions/`, `>> $PROFILE`). With no argument `detectShell()` guesses from `$SHELL` - and from `PSModulePath` on Windows when `$SHELL` is absent, which is the only signal a native PowerShell session gives.

- THE WORD LISTS ARE DERIVED, WHICH IS THE WHOLE POINT. Top-level commands come from cli.ts's own `COMMANDS` set (passed in, so `completion.ts` does not import the CLI back) and config keys from `ALL_SETTINGS` in the settings registry. Add a command or a setting and it completes with no second edit - the failure mode this avoids is a completion script that quietly offers a command the CLI removed two releases ago.

- THE ONE HAND-WRITTEN LIST IS TESTED AGAINST THE HELP. `SUBCOMMANDS` maps a command to its subcommands, and there is no way to derive those (they are `if (sub === "...")` branches scattered through cli.ts, with aliases). So `tests/completion.test.ts` slices each command's `COMMAND_HELP` entry out of the cli.ts source and asserts every subcommand offered appears in it. That test EARNED its place on the first run: it caught `pack add`, a subcommand that never existed (`pack` takes `install`, not `add`). A command whose subcommands the help does not document is left out of the map entirely rather than guessed at - `ssh` is the one such case, and it is absent for that reason.

- PowerShell's script is a `Register-ArgumentCompleter -Native` block; the bash one is validated with `bash -n` and by sourcing it and driving `_enigma_completion` with a fake `COMP_WORDS`/`COMP_CWORD`, the PowerShell one by `[System.Management.Automation.Language.Parser]::ParseFile`. Do that again after touching a template - a generated script that fails to parse breaks the user's shell startup, and nothing in a TS test suite would notice.
