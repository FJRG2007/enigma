## Repo Operating Notes (Self-Improvement Log)

Non-obvious lessons for working in THIS repo. Keep this section concise; add only what is not already derivable from the code or README.

### Skills are skippable by design (architecture)

- Claude Code, Codex, and opencode all load skills via progressive disclosure: only each skill's `name` + `description` is always in context; the SKILL.md body loads only if the model decides to activate it.
- Therefore a rule that lives ONLY in a SKILL.md can be skipped. The only guaranteed always-on channel is the memory file (`packages/enigma-cli/assets/memory/CLAUDE.md`, `.../AGENTS.md`).
- Consequence: non-negotiable rules must also be restated in the memory file's "Operating Contract" / "Always-On Rules" block, not only in a skill. When adding a hard rule, update both.

### Monorepo + CLI layout

- Workspaces monorepo. Publishable package: `enigma-cli` under `packages/enigma-cli` (command `enigma`). Source is TypeScript in `src/` (entry `src/bin/enigma.ts`; modules: cli, agents, skills, security, guard, config, claude, util). DISTRIBUTION MODEL (SINGLE npm package; opencode's *mechanism* but NOT its per-platform packages). The app is a Bun-compiled standalone binary per OS (`scripts/build-binaries.ts` -> flat `dist-bin/enigma-<os>-<arch>[.exe]` + `.sha256`), but the binaries are NOT npm packages - they are uploaded as assets on the GitHub Release `v<version>` and fetched at install time. The main package's `bin` is a thin Node launcher (`bin/enigma.mjs`). Three shared bin scripts (Node-builtins only) drive delivery: `bin/platform.mjs` (platform key + `assetName()` + `binTargetPath()` + `loadChecksums()`), `bin/download.mjs` (HTTPS download from the release, SHA256-verify against `bin/checksums.json`, atomic install to `bin/enigma-bin[.exe]`), `bin/postinstall.mjs` (best-effort at install; never fails `npm install`; skips when no checksums.json = source checkout). The launcher resolves `ENIGMA_BIN_PATH` -> installed binary -> lazy download (covers `npm i --ignore-scripts`). Integrity chain: npm tarball (provenance-signed) -> `bin/checksums.json` (inside it) -> downloaded binary. WHY NOT per-platform npm packages (the old v1.4.0 attempt): npm spam-detection blocks brand-new unscoped `enigma-cli-<plat>` names, and the user wants only `enigma-cli` to exist. `bin/checksums.json` is generated by CI from the `.sha256` sidecars and shipped ONLY in the tarball (gitignored; npm's `files` allowlist still packs it - verified via `npm pack --dry-run`). tsup builds ONLY `dist/guard.js`. `dist/` and `dist-bin/` are gitignored. Build: `npm run build` (guard via tsup), `npm run build:binaries` (host binary via Bun). Full dev/build/publish guide: `docs/developers/`.
- The compiled binary cannot see on-disk files via `import.meta.url` (its `__dirname` is Bun's virtual fs). The launcher passes `ENIGMA_ASSETS_DIR` (assets/), `ENIGMA_GUARD_PATH` (dist/guard.js) and `ENIGMA_VERSION` from the main package; `skills.ts`/`security.ts`/`cli.ts` read those env-first with the `__dirname` path as the dev/tsx fallback. If you add a new on-disk asset the binary needs, wire a matching env override. The launcher SETS these unconditionally (`=`, not `??=`): shells/tools spawned by an older enigma inherit the old values, and honoring them made a nested `enigma` report a stale version after an update (the "Update available 1.6.8 -> 1.9.0 while 1.10.0 is installed" bug). The only honored override is `ENIGMA_BIN_PATH`. Corollary: the compiled binary cannot run `node -e` scripts either (its execPath IS the binary; `-e` parses as a CLI flag), so the update notifier's detached child re-invokes the CLI with the hidden `__update-check` command (handled in cli.ts BEFORE parseArgs); only the node/tsx dev path keeps the classic update-notifier `-e` child, and bun-on-source re-runs `argv[1]`. If you add another self-spawning background job, use the same hidden-command pattern, never `-e`.
- Skills/memory are authored once under `packages/enigma-cli/assets/{skills,memory}` and deployed to every agent. Never create per-agent copies of a SKILL.md.
- After editing any SKILL.md or skill.json content, run `npm run seal` (or `enigma seal`) to refresh the `sha`, or the installer will not detect the change. Bump the skill's `version` for real content changes.
- Validate with `npm run check`; preview installs with `npm run enigma -- install --local --all --yes --dry-run` (runs the CLI from TS via tsx; must list claude, codex, opencode). To exercise the BUILT binary end-to-end (launcher -> compiled binary -> env-asset wiring), `npm run build:binaries` then `npm run dev -- --built install --local --all --yes --dry-run`.

### Runtime config (.enigma.json) and behavior carve-outs

- User-facing runtime toggles live in `.enigma.json`, read by `src/config.ts` with precedence: built-in defaults -> `~/.enigma.json` -> repo `.enigma.json` (nearest wins). It is NOT gitignored, so a team can commit it (same intent as `.githooks/enigma-guard.json`). Managed via the `enigma config <key> <on|off>` subcommand (mirrors the guard-config pattern, not a new prompt flow).
- First toggle: `commitEmoji` (CLI key `commit-emoji`, default on). It enables the gitmoji map in `git-policy` SKILL.md.
- Permission bypass is DEFAULT ON (security downgrade by deliberate user choice): `permissionBypass` (CLI `permission-bypass`, default true) plus `bypassDisabled: string[]` in `.enigma.json`. `resolveBypassSelection` (permissions.ts): `--no-bypass` -> none; explicit `--bypass` wins; else if `permissionBypass` is on, default = all `BYPASS_SUPPORTED` agents (claude, codex, opencode) MINUS `bypassDisabled`, applied in `--yes` runs too (interactive still shows a review multiselect preselected to the defaults). Per-agent opt-out persists: `setBypass(name, ..., off)` calls `config.setBypassDisabled(name, true)` (writes the GLOBAL `.enigma.json` list), so a deliberate off is never auto-re-enabled by a later install; `on` clears it. So "install Codex after enigma -> next install bypasses it" works, while "disabled manually before/after" sticks. Every enable is logged loudly (`applyBypass` warns "approval prompts are now OFF"). `setEnigmaValue` accepts `string[]` for the array. If you change this posture, update permissions.ts header, both READMEs, and cli.ts help.
- `parallelSubagents` (CLI key `parallel-subagents`, default OFF, opt-in) is a DIFFERENT kind of toggle than `commitEmoji`: it does NOT add an opt-out note the model reads at runtime - it physically adds/removes a section in the DEPLOYED memory file. The section is authored in BOTH memory files (`assets/memory/{CLAUDE,AGENTS}.md`) wrapped in `<!-- enigma:parallel-subagents:start -->`/`<!-- enigma:parallel-subagents:end -->` markers (blank line each side). `skills.ts` no longer copies memory verbatim: `renderMemory` strips the marked block when the toggle is off, `memoryStatus` compares the RENDERED source (not raw bytes), and the install write uses `writeFileSync(renderMemory(...))` not `cpSync`. `applyMemoryToggles(scope)` (exported) re-renders already-deployed memory files (existsSync-guarded; never creates a new deployment) and returns the changed agents. Both surfaces call it after a memory-affecting write: `runConfigCli` (then prints a restart notice via `runningStatus`) and the TUI `persistPending`. Setting carries `affectsMemory?: boolean`. Because the file content changes, the user MUST restart the agent (memory loads at startup) - that is why this toggle prints/needs a restart and `commitEmoji` does not. Subtask DECOMPOSITION (the always-on part) lives OUTSIDE the markers and is never stripped. To add another memory-gated toggle, reuse the marker + `renderMemory` pattern and set `affectsMemory: true`.

### Context compression engine + MCP (native, dependency-free)

- `src/compress/` is a native TypeScript port of the BEST of the headroom optimization engine (study clone at `references/repos/headroom`, Apache-2.0; the user owns the source account). It is NOT a 1:1 port of headroom's ~36k-LOC Rust core - only the high-value, self-contained subset, Node-builtins only (enigma has zero runtime deps, so NO `@modelcontextprotocol/sdk` and NO tokenizer/ONNX/embedding deps). DELIBERATELY UN-BRANDED per user instruction: no "headroom" name anywhere user-facing - everything is enigma-native (`enigma compress`, `enigma mcp`, tools `enigma_compress/retrieve/stats`, marker `<<enigma:ccr:HASH N_rows_offloaded>>`). Modules: `tokens.ts` (~4 chars/token estimate), `detect.ts` (heuristic content type: json confirmed by parse, plus log/diff/code/markdown/text - the Magika ML detector is intentionally NOT ported), `crusher.ts` (SmartCrusher: statistical JSON-array crush - per-field type/uniqueness/anomaly analysis, crushability gate `maxUniq<0.3 || hasSignal` with the safety carve-out that unique-entities-with-no-signal are left intact, keep-set = head/tail anchors + error rows + numeric anomalies(>2 sigma) + structural outliers + dedup + stride fill capped at maxItems=15), `logs.ts` (template-collapse repeated lines, keep error/warn verbatim), `text.ts` (head+tail truncation; code/diff/markdown pass through - no safe lossy transform without a parser), `ccr.ts` (Compress-Cache-Retrieve: reversible file-per-hash store under `~/.enigma/ccr`, sha256 12-char key, newest-500 retention cap, `stats.json`), `index.ts` (universal `compress()`: detect -> route -> if lossy store original + append CCR marker -> CompressResult). Paths resolve `homedir()` LAZILY per call so tests can point HOME/USERPROFILE elsewhere (`tests/compress.test.ts`).
- `src/mcp.ts` is a HAND-ROLLED stdio JSON-RPC 2.0 MCP server (no SDK). `handleMcpRequest(req, version)` is a PURE function (exported, unit-tested in `tests/mcp.test.ts` without real stdio); `runMcpServer` is the thin newline-delimited stdin/stdout loop. stdout is the protocol channel -> ALL diagnostics go to stderr, and `enigma mcp` is dispatched in cli.ts `run()` BEFORE any clack intro/parse noise (same early-dispatch slot as the hidden `__update-check`/`__lint-install`). Tools: `enigma_compress` (content + optional content_type -> compressed, carrying the CCR marker when lossy), `enigma_retrieve` (hash -> original), `enigma_stats`. Protocol version echoed from the client else `2025-06-18`; `notifications/*` get no reply.
- `enigma compress [file]` (`runCompressCli` in cli.ts): reads a file or stdin (`readFileSync(0)`), prints compressed to STDOUT and the savings line to STDERR (so output stays pipeable); `--retrieve <hash>`, `--stats`, `--type <t>` flags added to `parseArgs`/`CliOptions`. Both `compress` and `mcp` added to the `COMMANDS` set and `printHelp()`.
- DEPLOYMENT (`src/mcp-deploy.ts`) registers the MCP server in each managed agent's OWN config, gated by the `compress` toggle (config.ts `EnigmaConfig.compress`, default OFF/opt-in like `parallelSubagents` - adding an MCP server to a user's agents is a consent-worthy change). This is the "MIRROR SETTINGS" pattern (read-merge-write preserving other keys, mirror presence AND absence), NOT the verbatim command-copy pattern, because each agent uses a different file+format: claude `mcpServers.enigma` in `~/.claude.json` (global) / `.mcp.json` (local) / `<accountDir>/.claude.json`; codex `[mcp_servers.enigma]` TOML in `~/.codex/config.toml` / account `config.toml` (NO project-local - local scope is a no-op, matching commands); opencode `mcp.enigma` JSON in `~/.config/opencode/opencode.json` / `./opencode.json` / `<accountDir>/xdg-config/opencode/opencode.json`. "enigma"` + `["mcp"]`. Tests: `tests/mcp-deploy.test.ts`.
- To add another compressor content-type: add a branch in `index.ts` routing + a module returning `{ compressed, offloaded }`; keep it reversible (offloaded>0 triggers the CCR store + marker). To add another MCP tool: extend the `TOOLS` array + `callTool` switch in `mcp.ts` (the schema is inline JSON Schema). The compiled-binary asset wiring needs NO change (no on-disk assets - the engine is bundled into the binary; `enigma mcp` runs inside it).

### Autoskills: detect a project's stack and install matching skills (`enigma autoskills`)

- WHAT: a native port of the DETECTION core of `midudev/autoskills` (study clone `references/repos/autoskills`, MIT). `enigma autoskills [path]` scans the project, maps the detected technologies to community skills, and installs them SEPARATE from enigma's policy skills. These are DISTINCT skill kinds: policy skills (enigma's own, in `assets/skills`, global, sealed/provider'd) vs stack skills (third-party, project-local, fetched on demand). They never mix.
- DATASET (bundled, small): `assets/autoskills/skills-map.json` (~43KB, 98 technologies + 25 combos + frontend bonus + agent folders), GENERATED from the upstream `skills-map.ts` by a one-off tsx converter (RegExp->source string, Set->array). Rides the existing `ENIGMA_ASSETS_DIR`/`assets`-in-`files` wiring; `src/autoskills.ts` resolves it env-first exactly like skills.ts. Detection MUST be offline, so the map is bundled (never fetched). To refresh the map: re-run the converter against an updated clone.
- DETECTION (`src/autoskills.ts`, zero-dep, faithful port of upstream `lib.ts`): `detectTechnologies(projectDir)` scans npm/deno packages (`dependencies`+`devDependencies`+`npm:`/`jsr:` imports), `configFiles`, `fileExtensions`, Ruby `gems` (Gemfile), and `configFileContent` patterns (incl. `scanGradleLayout`/`scanDotNetLayout` multi-module scanning), across pnpm/npm/deno WORKSPACES, with per-dir caches. Returns detected techs + cross-tech `combos` + `isFrontend`. `collectSkills` flattens to deduped `owner/repo/skill` refs (+frontend bonus). `detectAgents` lists agents by their skills folder. Tested network-free in `tests/autoskills.test.ts` (synthetic temp-dir fixtures; in ci.yml).
- CONTENT ORIGIN = midudev's registry, fetched ON DEMAND (NOT vendored - 40MB/219 skills/~100 authors would bloat git + drag licensing). `src/autoskills-install.ts` `installStackSkills` fetches `index.json` from `raw.githubusercontent.com/midudev/autoskills/main/packages/autoskills/skills-registry` (cached 24h at `~/.enigma/autoskills/index.json`, `ENIGMA_AUTOSKILLS_DIR` override), resolves each skill NAME (last path segment) -> registry entry, downloads each file, verifies per-file `sha256` AND the whole-skill `bundleHash`, caches under `~/.enigma/autoskills/cache/<bundleHash>/<skill>`, then copies into the project's per-agent skill dirs (`AGENT_DIRS` map: `.claude/skills`, etc.; defaults to `.claude` = enigma's primary). Tracks installs in `<project>/.enigma/autoskills-lock.json` (carries no enigma provider, so enigma's own sync/prune ignores them). FAULT-TOLERANCE: a missing entry/failed download/hash mismatch fails only that one skill (reported), never throws out of `installStackSkills`; offline degrades to a stale cache. Verified e2e against the live registry (bun project -> the `bun` skill).
- WIRING: `autoskills` in the `COMMANDS` set + dispatch in `run()` + `printHelp`; `runAutoskillsCli` (cli.ts) prints detected techs/combos/skills, honours `--dry-run` and `-a <agent>`, then calls the installer. ### Marketplace packs: optional ISOLATED harness bundles (`src/packs.ts` + `enigma pack`/`enigma <pack>`)

- WHAT/WHY: a "pack" is an optional harness bundle (skills + commands + sub-agents + MCP) for a focused domain, installed ON DEMAND from a marketplace and deployed ONLY into a DEDICATED, isolated agent context - NEVER into the user's normal agent. First pack = HELIO (TPEOficial/helio, a Python bug-bounty harness: 13 skills, ~20 commands, 10 sub-agents, 2 MCP). Motivation (user): keep cyber skills/tools out of the everyday Claude so they don't overload context (progressive disclosure keeps every skill's name+description always-loaded; 13 security skills would mis-trigger on normal coding) or collide with policy skills. Packs are a THIRD skill kind alongside policy skills (enigma's own, global, sealed) and autoskills (community, project-local) - distinct from both.
- DELIVERY = asset-only npm package per pack (`@enigmax/helio`, `packages/helio`), the @enigmax/dashboard model. Helio is VENDORED into `packages/helio/assets` by `scripts/sync-helio.mjs` (`npm run sync:helio` - shallow-clone a PINNED commit from `.source.json`, denylist `.git/tests/docs/install.*/.claude`, replace the whole tree to propagate deletions, re-pin; Node builtins + git CLI, MAINTAINER tool, assets are COMMITTED like dashboard's). Decision was "republish as npm" (provenance) NOT "fetch the helio repo at runtime". `publish.yml` has a version-guarded `@enigmax/helio` step (twin of dashboard's). The pack package applies Apache-2.0 + attributes TPEOficial (helio itself has no LICENSE - add one upstream).
- ISOLATION = the accounts.ts config-dir-injection mechanism, reused. `enigma helio` -> `launchPack` (packs.ts) -> fetch bundle if absent (on-demand npm into `~/.enigma/packs/helio/pkg`, `ENIGMA_PACKS_DIR` overrides) -> `deployPack` -> seed credentials -> `launchInDir(tool, contextDir)`. `launchInDir` (NEW export in accounts.ts) spawns the tool with its config-dir env pointed at `~/.enigma/packs/helio/context/<tool>` (which holds ONLY helio's content), bypassing account resolution. Refactor: the measuring-proxy block was extracted to `maybeStartProxy(toolName, env, cfg)` and shared by `launchTool` + `launchInDir` (no dup). Default tool = claude (DEFAULT_TOOL); `enigma helio [tool]` accepts a tool positional.
- DEPLOY (`deployPack`, version-gated via a `.enigma-pack-version` marker so re-launch is a cheap no-op unless the pack version changed): copies `assets/skills/*` -> `accountTarget(ctx).skills`, the tool's command set (`commands/claude-code` for claude, `commands/<tool>` else, flat `commands/` fallback) -> `accountTarget(ctx).commands`, `assets/agents/*` -> `<ctx>/agents` (Claude subagents, claude-only), and writes the harness memory file (`assets/AGENTS.md` else root `SKILL.md`) as `<ctx>/CLAUDE.md` (claude) / `AGENTS.md` (else). Reuses `getTool(tool).accountTarget(dir)` for tool-agnostic dest paths.
- CREDENTIALS SEEDED (user decision "seed creds, frictionless"): `seedCredentials(id, tool, account)` copies THAT account's auth file(s) into the context so the isolated agent shares the login with no re-auth - claude `.credentials.json`, codex `auth.json`, opencode `xdg-data/opencode/auth.json` (CRED_FILES map). Best-effort, claude-first; never copies project history, only the well-known auth file.
- ACCOUNT/PROFILE PER PACK (user follow-up "packs must work with any profile/account, settable default"): a pack seeds from a RESOLVED account, not always the active one. `resolvePackAccount(id, tool, explicit?)` = explicit (validated, throws on a typo so it never seeds the wrong login) > the pack's pinned default `getPackAccount` > `resolveLaunchAccount(tool)` (active profile mapping > tool-active). Per-pack default in `EnigmaConfig.packAccounts: Record<"<packId>:<tool>", account>` via `setPackAccount` (config.ts, merge-write like setToolPath; null clears); `setPackDefaultAccount(id, tool, account|null)` validates the account exists. `launchPack(id, tool, passthrough, account?)` resolves up-front and prints which account it seeds with. Tests: resolution/default/clear + launchPack rejecting an unknown explicit account (returns 1 pre-spawn) in packs.test.ts; a set-account case in dashboard.test.ts.
- SEEDING A CLAUDE LOGIN INTO AN ISOLATED CONFIG-DIR IS THREE LAYERS, NOT ONE (hard-won; this caused a long debugging saga). A separate `CLAUDE_CONFIG_DIR` (the pack context) is treated by Claude Code as a SEPARATE INSTALL, so copying just the token is NOT enough. `seedCredentials(id, tool, account)` must get all three right: (1) TOKEN - copy `.credentials.json` from the account, BUT (a) never PLANT a non-usable/blanked token (when the account's real token lives in the OS keychain the file is blanked; an empty file BLOCKS the agent's own resolution - copy only when `hasUsableToken(from)`), and (b) never CLOBBER the context's own token when it is the SAME account's (a fresh in-place OAuth rotation; re-copying the account's older token breaks the next refresh). (2) IDENTITY/STATE - the context's `.claude.json` must mirror the account's: a per-context `.enigma-pack-account` MARKER distinguishes a same-account rotation (keep) from an account SWITCH (re-seed token + state); on a switch/first-seed, `syncContextAccountState` copies the account's `.claude.json` (minus `projects`, keeping the pack's `mcpServers`). (3) ONBOARDING FLAG - the killer bug: without `hasCompletedOnboarding` in the context `.claude.json`, Claude Code runs its ONBOARDING WIZARD (which asks to log in) and IGNORES a perfectly valid token. `syncContextAccountState` brings `hasCompletedOnboarding` (+ the rest of the account state), and runs on EVERY launch when the context already holds the account's token (not only when copied), so a context seeded by an older enigma gets the missing flag on the next run. NET RULE: an access token past `expiresAt` but WITH a refresh token is "ok" (the session refreshes - sessions last months, not the access-token's hours); `accountTokenState` returns ok/expired(no-refresh)/empty/absent. DEBUG NEXT TIME: compare the account's `.claude.json` keys vs the context's (`hasCompletedOnboarding`, `userID`, `machineID`, `oauthAccount`) - a missing onboarding/identity field, not the token, is the usual "login despite valid token" cause. enigma writes ONLY the pack context, NEVER the account dir.
- PERMISSION BYPASS ON BY DEFAULT FOR THE PACK (user request): `ensurePackBypass(dir, tool)` writes `permissions.defaultMode: "bypassPermissions"` into `<ctx>/settings.json` (claude only; the format `enableClaudeBypass` uses in claude.ts). Honors the global `config.permissionBypass` opt-out. A security harness issues many tool calls, so per-action prompts would be unworkable.

### Recall: local session memory (`src/recall/` + `enigma recall`)

- WHAT: a de-branded, lean port of the CORE of `thedotmack/claude-mem` (study clone `references/repos/claude-mem`, Apache-2.0; the upstream is a ~36k-LOC plugin with a worker HTTP service, Chroma vectors, a web viewer and LLM-written observations). enigma ports only the durable core: transcripts -> structured observations + per-session summaries -> a local SQLite store -> search + retrieval, surfaced in the CLI/TUI/Dashboard and exposed to agents over MCP. DELIBERATELY UN-BRANDED per user instruction: nothing user-facing says "claude-mem"; the feature is "recall" (distinct from enigma's existing "agent memory" = the `CLAUDE.md`/`AGENTS.md` editor in `dashboard-memory.ts`, which is unrelated). ### System resources / process killer (`src/resources.ts` + `enigma resources`)

### Tool launch-path repair (`src/tool-path.ts` + `enigma fix-path`)

- THE BUG it fixes: a coding-agent CLI (esp. Claude Code) can be installed but NOT on the shell PATH (native installer -> `~/.local/bin`, `~/.claude/local`; npm-global, bun/volta shims), so `launchTool` falls back to a bare command name the OS can't spawn. `enigma fix-path [tool]` (no tool = all) does an OS-agnostic search of well-known install dirs (`candidateBinDirs()` - homedir-based dirs + env-derived `APPDATA`/`LOCALAPPDATA`/`ProgramFiles`/`NVM_BIN`; POSIX `/usr/local/bin` etc.), and when a binary is found OFF PATH persists its absolute path to `EnigmaConfig.toolPaths[tool]` (a `Record<string,string>`, `setToolPath` merges per-tool). It contemplates "not installed" (reports an install hint) and "already works" (env override / on PATH / already-fixed -> no write, idempotent).
- CONSUMPTION: `launchTool` (accounts.ts) resolution order is now `process.env[tool.binEnv]` > `cfg.toolPaths?.[tool]` > `resolveBin(tool.bin)` > bare name. The persisted path is the only NEW link; everything else was already there. tool-path.ts imports accounts (getTool/TOOL_NAMES) but launchTool does NOT import tool-path (reads config directly) - no cycle. `resolveBinIn(bin, dirs)` was factored out of `resolveBin` in util.ts and is the shared directory-scoped lookup (PATHEXT-aware).
- SURFACES (the user wanted it from the TUI AND dashboard, not only the CLI): (1) CLI `enigma fix-path` (`runFixPathCli`); (2) TUI: a third `ACTION_ITEM` `fix-path` reusing the existing checklist/`runChosen`/result-panel machinery - `ActionRequest.action` widened to `"skills"|"security"|"fix-path"` (alias `ActionKind` in opentui.ts), `HubContext.toolPaths` carries per-tool `{name,label,status}` rows, `runAction` in cli.ts buildCtx handles the `fix-path` branch (selected tools or all). Because the 3rd action shifts the sidebar layout, `tests/tui.hub.test.ts` identity index is now `CATEGORIES.length + 4` (categories + usage + 3 actions); (3) dashboard: origin-guarded `POST /api/fix-path` (`serveFixPath`, dynamic-imports tool-path+accounts), a "Fix tool paths" button + a "Tool launch paths" status row (`s.tools` from `systemsStatus().tools`) in `packages/dashboard/assets/index.html`.
- BARE-COMMAND vs `enigma <tool>` (the second-pass fix): persisting `toolPaths` only fixes `enigma <tool>` (the launcher reads it); the bare shell command (`claude`) depends on the OS PATH. So fix-path ALSO puts the binary's directory on the persistent USER PATH via `src/path-env.ts` `addDirToUserPath` (Windows: per-user PATH in the registry through `[Environment]::SetEnvironmentVariable('Path',...,'User')`, with the dir passed via the `ENIGMA_PATH_ADD` env so a spacey path can't inject into the PowerShell `-Command`; POSIX: a marked `export PATH=...` / `fish_add_path` line in the `$SHELL`-matched profile). User scope only (no admin), idempotent, best-effort (a failure leaves the config fix intact), and changes apply to NEW terminals only (never the current shell). `ensureLaunchable(tool)` (tool-path.ts) = `fixToolPath` + the PATH step when the dir is not already on PATH; the CLI (`runFixPathCli`), TUI `runAction` and dashboard `serveFixPath` all call `ensureLaunchable`, while `fixToolPath` stays PURE (config only) so the unit test never mutates the real PATH. Escape hatch `ENIGMA_NO_PATH_EDIT=1` skips the system write.
- Tests: `tests/tool-path.test.ts` (bun; temp HOME set before import; sets `ENIGMA_TOOL_PATH_DIRS` to pin discovery to one controlled dir and `ENIGMA_NO_PATH_EDIT=1` so neither the host filesystem nor the real PATH is touched; covers not-installed / off-PATH-persist-idempotent / on-PATH-no-write - the on-PATH case uses a never-fixed tool, NOT a mid-test HOME switch, because `os.homedir()` does not re-read `$HOME` mid-process on POSIX, only Windows re-reads `USERPROFILE`). Wired into ci.yml. To add another candidate location, edit `candidateBinDirs()` (or set `ENIGMA_TOOL_PATH_DIRS` to override discovery entirely).
