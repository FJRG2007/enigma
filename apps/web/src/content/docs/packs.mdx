An **agent** is an optional harness bundle - skills, slash commands, sub-agents and MCP servers for a focused domain - that you add on demand from the marketplace. Unlike enigma's built-in policy skills, an agent is **never** deployed into your normal agent. It runs in a **dedicated, isolated agent context**, so its skills and commands do not load into - or overload - the agent you use for everyday coding.

## Available agents

- <a href={docHref("helio/overview")}><strong>Helio</strong></a> - a bug-bounty and offensive-security harness: recon, vulnerability hunting, web2/web3 audit, Active Directory, cloud, triage and report writing. Created in collaboration with the Dymo Intelligence Team.
- <a href={docHref("orion/overview")}><strong>Orion</strong></a> - hunts what looks finished but is not: broken flows, slow loads, unbounded queries, scaling limits and searches that never say "no results" - each finding proved with a trace, a number or a failing input, in a real browser via the built-in Chrome DevTools MCP server.
- <a href={docHref("vega/overview")}><strong>Vega</strong></a> - reverse engineering on REA (Reverse Engineer Anything): one MCP server and skill to reverse native binaries, Electron/JavaScript apps, .NET, Android, firmware, websites and captures, every claim backed by the evidence it came from.

More agents are on the way; each gets its own section in this sidebar.

## Why isolation matters

Agents keep every installed skill's name and description in context at all times (progressive disclosure). Adding a dozen security skills to your normal agent would sit in every session and risk mis-triggering on ordinary coding tasks. An agent avoids that: it is fetched as an asset-only package into a managed directory and deployed **only** into its own context directory, which the agent reads via its config-dir environment variable. Your normal `enigma claude` stays clean.

## Install and launch

<Cmd name="enigma agent <subcommand>" ex={["enigma agent list", "enigma agent install helio", "enigma helio", "enigma orion", "enigma agent use helio work", "enigma agent setup helio", "enigma agent remove helio"]}>
`list` shows every agent and its install state. `install <id>` fetches the agent. `enigma <id>` (e.g. `enigma helio`, `enigma vega`) launches it in its isolated context. `use <id> <account>` pins which login seeds the agent. `setup <id>` registers the agent's MCP servers. `update`/`remove` keep or delete it.
</Cmd>

You can also manage agents from the dashboard's **Agents** tab (install, update, remove, pick the seeding account, and copy the launch command).

## Which account an agent uses

An agent runs under one of your configured logins, seeded into its isolated context so you do not log in again. You can use **any account or profile** you have set up - or a brand-new one:

<Cmd name="enigma <agent> [account]" ex={["enigma helio", "enigma helio work", "enigma agent use helio work", "enigma agent use helio -", "enigma account add pentest", "enigma helio pentest"]}>
`enigma <agent>` uses the pinned account if you set one, otherwise your active profile's account (or the tool's active account). `enigma <agent> <account>` overrides it for one launch. `enigma agent use <agent> <account>` pins a per-agent default (`-` clears it). To use a new login, create it with `enigma account add <name>` (and log in), then point the agent at it. Target Codex/OpenCode with `--tool`.
</Cmd>

This lets an agent run under a different identity than your everyday agent - for example a dedicated account for authorised security testing - without touching your normal `enigma claude` setup.

## How it works

- **Delivery** - each agent ships as an asset-only npm package (e.g. `@enigmax/helio`) fetched on demand into `~/.enigma/packs/<id>`, the same on-demand model as the dashboard UI. A workspace checkout is used directly in development.
- **Isolation** - launching an agent deploys its skills, the agent's command set and its sub-agents into `~/.enigma/packs/<id>/context/<tool>`, then spawns the agent pointed at that directory. The context holds only the agent's content.
- **Shared login** - your chosen account's credentials are seeded into the context, so the isolated agent is already authenticated.
- **MCP and tooling** - an agent can ship MCP servers, registered in the agent's context for whichever tool you launch it with (Claude Code, Codex, OpenCode, Kimi Code). A server that needs Python and the agent's own tooling is registered only by `enigma agent setup <id>`, heavier than the default skills-and-commands launch. A server enigma can launch itself, like Orion's Chrome DevTools server, is registered automatically on every launch instead, following the same <code>browser</code> toggle used everywhere else - no setup step needed.
- **Engines** - an agent can pin a runtime its MCP server runs on. Vega pins the `rea-agents` release its skill was written for; enigma installs that exact version once into `~/.enigma/packs/vega/engine` and starts it with a Node.js that meets REA's requirement, picked from the runtimes on your machine.

`enigma pack` (the former name) still works as a deprecated alias of `enigma agent`.
