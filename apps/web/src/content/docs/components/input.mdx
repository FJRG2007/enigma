Give it a field and it wires the buttons that live inside it. A `type="password"` field gets its reveal toggle for free, because a password the visitor cannot read back is the most common reason a sign-in fails on the first try.

## React

```jsx
import { useInput } from "@enigmax/primitives/react";

export function PasswordField() {
    const { inputRef, revealed } = useInput();

    return (
        <div className="field">
            <input ref={inputRef} type="password" autoComplete="current-password" />
            <span className="hint">{revealed ? "Visible" : "Hidden"}</span>
        </div>
    );
}
```

## Your own icon

The built-in is expressed as an ordinary action, so replacing it is the same as adding one. An icon is an HTML string or a DOM node - an inline SVG, a sprite reference, a font glyph, whatever you already use.

<Preview title="replaced icons and labels" hint="Same behaviour, nothing of the default left.">
    <InputDemo custom={true} />
    <div slot="code">
```js
createInput(field, {
    reveal: {
        showIcon: '<svg viewBox="0 0 24 24">...</svg>',
        hideIcon: myIconElement,          // a Node works too
        showLabel: "Let me read it",      // becomes aria-label AND title
        hideLabel: "Cover it up"
    }
});
```

To replace it wholesale rather than restyle it, pass an action named `reveal` and it wins over the built-in:

```js
createInput(field, {
    actions: [{
        name: "reveal",                    // same name -> replaces the built-in
        label: (state) => (state.revealed ? "Hide" : "Show"),
        icon: (state) => (state.revealed ? hideIcon : showIcon),
        pressed: (state) => state.revealed,
        onSelect: () => instance.reveal()
    }]
});
```

## Options

| Option | Default | Meaning |
|---|---|---|
| `reveal` | `true` | `false` removes the toggle. An object overrides its icons and labels. |
| `actions` | `[]` | Extra actions. One named `reveal` replaces the built-in. |
| `position` | `"end"` | Which side the container mounts on. |
| `container` | created | Mount the actions into your own element instead. |
| `onRevealChange` | - | Called whenever the password's visibility changes. |

The instance exposes `revealed`, `reveal(next?)`, `refresh()`, `update()` and `destroy()`.

## Why the obvious implementation is wrong

**A bare `<button>` inside a form submits it.** `<button>` defaults to `type="submit"`, so a hand-rolled toggle posts the half-filled sign-in form the moment someone looks at their password. Every action here is `type="button"`, and a test asserts the form never submits from it.

**Pressing it must not take focus off the field.** The visitor is mid-word. `preventDefault()` on `mousedown` keeps focus where it is, while keyboard users still tab to the button and keep focus there, which is what they expect.

**The caret is the hard one.** Assigning `input.type` inside a click handler resets the selection to 0 in Chromium - and does *not* when the same assignment runs outside an event. Worse, the reset lands one **macrotask** later: read it in the handler, or even in a microtask, and it still looks correct. So the selection is captured before the switch, restored after the render, and restored once more on the next task. This was reproduced in twenty lines with no library before a line of the fix was written.

**An action that should not show is removed, never `hidden`.** The `hidden` attribute works through a UA `display: none`, and any author rule setting `display` on the button beats it - which a theme styling these buttons always does. A headless primitive cannot lean on a UA default its consumers are expected to override.

And `destroy()` puts a revealed field back to `password`: leaving it as text would show the value to whoever sees the screen next.
